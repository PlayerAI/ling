# RFC-0001：零语言基础与 v0.0.1 Seed

> 状态：Draft  
> 类型：Standards Track  
> 创建日期：2026-08-17  
> 目标版本：v0.0.1  
> 依赖文档：`LANGUAGE.md`、`SEMANTICS.md`  
> 中文项目名：零  
> 英文名与 CLI：`zero`（内部占位，公开发布前必须更换）

---

## 1. 摘要

本 RFC 建议启动“零”语言的第一个可运行实现 `v0.0.1 Seed`。

该版本的目标不是实现完整的 GC、Ownership、Actor、GPU 或形式验证系统，而是验证三项基础假设：

1. F#/OCaml 风格的简洁人类源码可以自然支持中文 Unicode 标识符；
2. 源码可以稳定 Lower 为 AI 可查询、编译器可检查、人类可审计的 Semantic Graph；
3. Type、Effect 与 Capability 可以从第一版进入核心架构，而不让表层语法变得沉重。

v0.0.1 将由 Rust 实现，提供解释执行、REPL、中文标识符、局部类型推导、record、ADT、模式匹配、基础 Effect/Capability、结构化诊断和 Semantic Graph 输出。

---

## 2. 重大命名阻塞

2026 年 5 月，Vercel Labs 已公开发布 `Zerolang`：

- 项目定位为面向 AI Agent 的 graph-native 编程语言；
- 使用 `zero` 作为 CLI；
- 使用 Semantic Graph 作为程序数据库；
- 提供语义查询、受检 patch 和人类文本投影。

因此：

- 中文名“零”可以继续作为内部思想与项目代号；
- `zero` 命令只允许用于私有原型；
- 在公开仓库、包管理器或网站发布前，必须通过后续 RFC 选择新的英文名、命令、文件扩展名和命名空间；
- 本 RFC 中所有 `zero` 示例均视为可批量迁移的占位符；
- 实现中 CLI 名称必须集中定义，不允许散落硬编码。

该冲突不否定本语言的独立设计，但若继续使用相同英文名称和 CLI，会造成严重的用户、搜索、生态和潜在商标混淆。

## 3. 动机

现代语言通常迫使开发者在两类体验之间选择：

```text
F#/OCaml/Python
    快速、简洁、适合原型
            vs
Rust/C++/Zig
    高性能、可控制、适合系统
```

“零”的长期目标是：

```text
同一语言
├── Explore：GC/VM/快速迭代
├── Native：Ownership/Region/零成本抽象
└── Critical：有界内存/严格审计/证明与证据
```

同时，未来软件工程将大量由 AI Agent 完成。仅让 AI 生成文本代码不够；工具链必须向 AI 暴露：

- 稳定 Semantic ID；
- 已解析类型；
- Effect；
- Capability；
- 调用图；
- Ownership facts；
- Contract；
- 结构化错误；
- 可验证 Repair；
- Semantic Transaction。

本 RFC 先构建能承载这些目标的最小地基。

## 4. 目标

v0.0.1 必须做到：

- 可以编写、检查并运行一个完整程序；
- 可以使用中文标识符；
- 可以执行 `人物.血量 = 100`；
- 可以推导普通函数类型；
- 可以声明 record 与 ADT；
- 可以检查模式匹配穷尽性；
- 可以区分 `Pure` 与 `Console.Write`；
- 可以检查 `Console.Write` Capability；
- 可以输出稳定 Semantic Graph；
- 可以输出人类和 JSON 两种诊断；
- 可以通过 REPL 快速实验；
- 可以用自动化测试固定语义；
- 可以作为后续 Native/Actor/AI Tooling 的架构基础。

---

## 5. 非目标

v0.0.1 不实现：

- 生产级垃圾收集器；
- JIT；
- LLVM/Cranelift Native Backend；
- Rust 级 Borrow Checker；
- Trait；
- 用户自定义 Effect Handler；
- Structured Concurrency；
- Actor Runtime；
- Supervisor；
- Remote Actor；
- Node；
- Kernel；
- GPU/TPU；
- Contract Prover；
- Model Checker；
- Package Registry；
- Debugger；
- 热升级；
- 航空航天认证。

如果为完成 v0.0.1 而伪造上述能力，将被视为失败。

## 6. 规范决定

### 6.1 源码编码

采用 UTF-8。

标识符使用 Unicode UAX #31 `XID_Start/XID_Continue`，在名称解析前进行 NFC 归一化。

实现必须拒绝：

- ZWJ/ZWNJ；
- 双向格式控制；
- variation selector；
- 默认不可见格式字符；
- private use；
- noncharacter；
- unassigned code point。

实现必须至少在同一作用域中检测 UTS #39 Confusable。

### 6.2 中文标识符

以下程序必须合法：

```fsharp
type 人物 =
    { 姓名: Text
      mutable 血量: Int }

let 恢复生命 数值 人物 =
    人物.血量 = 人物.血量 + 数值
```

中文名称在：

- Lexer；
- Parser；
- Name Resolver；
- Type Checker；
- Semantic Graph；
- REPL；
- JSON Diagnostic

中必须保持完整。

### 6.3 关键字

v0.0.1 使用统一 ASCII 关键字，不提供中文关键字翻译：

```text
let mutable rec and
type of
match with
if then else
true false
module import as
```

### 6.4 Assignment 与 Equality

采用：

```text
=   binding / field initialization / assignment
==  equality
!=  inequality
```

上下文规则：

```fsharp
let x = 1                // binding
{ 血量 = 100 }           // field initialization
人物.血量 = 80           // assignment
人物.血量 == 80          // equality
```

赋值返回 `Unit`，禁止链式赋值。

### 6.5 默认不可变

只有：

```fsharp
let mutable x = ...
```

和声明为 `mutable` 的 record 字段可以直接赋值。

### 6.6 参数模式与自动 Borrow

若函数体修改参数指向的可变 Place，类型检查器可以推导该参数为短生命周期 `&mut T`。

```fsharp
let 受到伤害 伤害 人物 =
    人物.血量 = max 0 (人物.血量 - 伤害)
```

可推导为：

```text
Int -> &mut 人物 -> Unit
```

调用 `受到伤害 30 关羽` 时，若 `关羽` 是可变 Place，编译器插入仅覆盖本次调用的 reborrow。

v0.0.1 可以先实现受限版本：

- 只支持局部可变 binding；
- Borrow 不得逃逸；
- Borrow 不得保存到 closure；
- 不存在 suspension point；
- Audit/Semantic Graph 必须显示推导结果。

若推导不唯一，要求显式 `&mut` 或 `borrow mut`。

### 6.7 求值

采用严格 call-by-value，除显式并行结构外左到右求值。

### 6.8 类型

v0.0.1 类型：

```text
Unit
Bool
Int
f64
Text
'a
tuple
function
nominal record
nominal ADT
Option
Result
```

类型推导采用 HM 风格的约束生成与统一。

实现必须包含 Value Restriction 的数据结构，即使 v0.0.1 只实现简化规则。

### 6.9 Effect

v0.0.1 Effect：

```text
Pure
Console.Write
State<T>（仅用于解释局部可变语义，可暂不向普通用户完整展示）
```

函数类型内部必须保存 Effect Row。

### 6.10 Capability

`Console.write` 要求 `Console.Write` Capability。

入口模块可声明：

```fsharp
module Main
    requires Console.Write
```

若未声明，调用为编译错误。

### 6.11 Semantic Graph

每个成功检查的程序必须生成 Semantic Graph。

Graph 节点至少包括：

```text
Module
Type
Field
Variant
Binding
Function
Parameter
Pattern
Expression
Effect
Capability
```

Graph 引用必须使用已解析 ID，而不是仅保存名称字符串。

### 6.12 Semantic ID

v0.0.1 可使用 BLAKE3 或 SHA-256 实现实验性 ID，但必须：

- 对 alpha-renaming 稳定；
- 对空白和注释稳定；
- 对文件移动稳定；
- 对依赖实现变化敏感；
- 在输出中带 schema/version 前缀。

哈希算法正式冻结前，ID 必须标记：

```text
experimental
```

### 6.13 解释执行

v0.0.1 使用 AST/Core Interpreter。

可以使用 Rust：

- `Arc`；
- Arena；
- `Vec`；
- `HashMap`；
- Interpreter Cell

实现内部运行时。

这不等于语言已经选择最终 GC 或所有权实现。

### 6.14 结构化诊断

所有检查命令必须支持：

```bash
--format human
--format json
```

JSON 诊断至少包括：

```json
{
  "schema": "zero.diagnostic/0.1",
  "code": "Z-TYPE-0001",
  "severity": "error",
  "message_zh": "...",
  "message_en": "...",
  "primary_span": {
    "file": "main.zero",
    "start_byte": 0,
    "end_byte": 4
  },
  "semantic_id": null,
  "facts": {},
  "repairs": []
}
```

错误码必须稳定，不得根据自然语言消息生成。

## 7. 表层语法草案

### 7.1 Hello World

```fsharp
module Main
    requires Console.Write

let main () =
    Console.write "你好，零"
```

### 7.2 中文人物

```fsharp
module Main
    requires Console.Write

type 人物 =
    { 姓名: Text
      mutable 血量: Int
      最大血量: Int }

let 受到伤害 伤害 人物 =
    人物.血量 =
        max 0 (人物.血量 - 伤害)

let 状态文字 人物 =
    if 人物.血量 == 0 then
        "死亡"
    else
        "存活"

let main () =
    let mutable 关羽 =
        { 姓名 = "关羽"
          血量 = 100
          最大血量 = 100 }

    受到伤害 30 关羽
    Console.write (状态文字 关羽)
```

### 7.3 ADT 与 Match

```fsharp
type 生存状态 =
    | 健康
    | 受伤 of Int
    | 死亡

let 描述 状态 =
    match 状态 with
    | 健康 ->
        "健康"

    | 受伤 程度 ->
        Text.format "受伤 {}" 程度

    | 死亡 ->
        "死亡"
```

### 7.4 Pipeline

```fsharp
let 总伤害 人物列表 =
    人物列表
    |> map 计算伤害
    |> sum
```

`List/map/sum` 的标准库细节可以最小实现，Pipeline 语法必须在 Parser 中支持。

## 8. EBNF 草案

以下不是最终完整语法，但 v0.0.1 Parser 必须大体遵循。

```ebnf
program          = { module_decl | declaration };

module_decl      = "module", qualified_name,
                   [ capability_block ];

capability_block = newline, indent,
                   "requires", capability_list,
                   dedent;

declaration      = let_decl
                 | type_decl;

let_decl         = "let", [ "rec" ], [ "mutable" ],
                   pattern, { parameter },
                   [ ":", type_expr ],
                   "=", expression;

type_decl        = "type", identifier,
                   { type_parameter },
                   "=",
                   ( record_type | variant_type | type_alias );

record_type      = "{", field_decl, { field_decl }, "}";

field_decl       = [ "mutable" ], identifier, ":", type_expr;

variant_type     = variant_case, { variant_case };

variant_case     = "|", identifier,
                   [ "of", type_expr ];

expression       = let_expression
                 | if_expression
                 | match_expression
                 | assignment_expression;

let_expression   = let_decl, newline, expression;

if_expression    = "if", expression,
                   "then", expression,
                   "else", expression;

match_expression = "match", expression, "with",
                   match_case, { match_case };

match_case       = "|", pattern,
                   [ "when", expression ],
                   "->", expression;

assignment_expression
                 = equality_expression,
                   [ "=", expression ];

equality_expression
                 = comparison_expression,
                   { ( "==" | "!=" ), comparison_expression };

comparison_expression
                 = additive_expression,
                   { ( "<" | "<=" | ">" | ">=" ),
                     additive_expression };

additive_expression
                 = multiplicative_expression,
                   { ( "+" | "-" ), multiplicative_expression };

multiplicative_expression
                 = application_expression,
                   { ( "*" | "/" | "%" ),
                     application_expression };

application_expression
                 = postfix_expression,
                   { postfix_expression };

postfix_expression
                 = primary_expression,
                   { ".", identifier };

primary_expression
                 = literal
                 | identifier
                 | tuple_or_group
                 | record_literal
                 | list_literal;

pattern          = identifier
                 | "_"
                 | literal
                 | constructor_pattern
                 | tuple_pattern
                 | record_pattern;

type_expr        = function_type
                 | applied_type
                 | tuple_type
                 | type_variable
                 | qualified_name;
```

### 8.1 赋值歧义处理

Parser 可以先产生：

```text
EqualsExpression(lhs, rhs)
```

Name/Type Checker 决定它是：

- 非法；
- Assignment；
- 语法上下文中的 Binding/Initialization。

在普通表达式位置，只有可赋值 Place 才能使用单个 `=`。

## 10. 编译 Pipeline

```text
Source Bytes
    ↓
UTF-8 Decode
    ↓
Unicode Security Scan
    ↓
Lexer + Layout
    ↓
Concrete Syntax Tree
    ↓
AST
    ↓
Name Resolution
    ↓
HIR
    ↓
Type + Effect + Capability Inference
    ↓
Exhaustiveness / Place Checking
    ↓
Typed Core
    ↓
Semantic Graph + Semantic IDs
    ├── Interpreter
    ├── Audit Source
    └── JSON Query
```

禁止 Interpreter 直接在未解析 AST 上运行。

否则运行时行为可能绕开类型和语义图。

## 11. CLI 草案

> `zero` 是临时占位符。

### 11.1 `zero run`

```bash
zero run examples/人物.zero
```

流程：

```text
check -> build semantic snapshot -> interpret main
```

### 11.2 `zero check`

```bash
zero check src/main.zero
zero check --format json src/main.zero
```

成功不执行程序。

### 11.3 `zero repl`

```text
> let 人物 = { 姓名 = "曹操"; 血量 = 100 }
val 人物 : 人物

> 人物.血量
100
```

REPL 必须复用同一 Parser、Resolver、Type Checker 和 Interpreter，不允许建立第二套语言。

### 11.4 `zero semantic`

```bash
zero semantic src/main.zero
zero semantic --format json src/main.zero
```

输出：

- Graph Hash；
- definitions；
- types；
- effects；
- capabilities；
- resolved references。

### 11.5 `zero audit`

```bash
zero audit src/main.zero
```

输出规范化审计文本。

### 11.6 `zero fmt`

第一版可在 RFC 合并后实现，但若实现，必须是确定性的。

```json
{

  "language_version": "0.0.1",
  "unicode_version": "17.0.0",

    }
  ],
  "definitions": [
    {
      "id": "def:...",
```

- 不把 Source Span 当身份。

## 13. 诊断示例

## 14. 测试策略

### 14.1 Conformance Tests

每个语义规则必须有：

```text
positive test
negative test
diagnostic snapshot
semantic graph snapshot
```

### 14.2 Unicode Tests

至少覆盖：

- `人物`；
- `人物ID`；
- NFC 等价名称；
- Cyrillic/Latin confusable；
- ZWJ/ZWNJ；
- bidi control；
- hidden character；
- emoji/variation selector；
- Han/Kana/Hangul；
- 多文件名称解析。

### 14.3 Parser Fuzzing

对 Lexer/Parser 使用：

- arbitrary UTF-8；
- invalid byte sequence；
- nested comments；
- extreme indentation；
- deep pattern；
- long identifier；
- confusable combinations。

Parser 不得 panic。

### 14.4 Type Property Tests

测试：

- unification 对称性；
- substitution；
- generalization/instantiation；
- occurs check；
- alpha-renaming 不改变类型；
- Semantic ID 对 alpha-renaming 稳定。

### 14.5 Differential Tests

未来有第二个 evaluator 或 Core evaluator 后，使用 differential testing 比较执行结果。

```text
4   runtime Fault
```

## 16. Codex 开发治理

### 16.1 权威顺序

```text
Accepted RFC
    > SEMANTICS.md
    > LANGUAGE.md
    > tests
    > implementation
    > comments
```

冲突时，Codex 不得自行选择语义，必须：

1. 停止修改相关核心；
2. 创建设计问题或 RFC 草案；
3. 列出可选语义和后果；
4. 等待决策。

### 16.2 Codex 可以做什么

Codex 可以：

- 实现已接受规范；
- 写测试；
- 发现规范矛盾；
- 提出 RFC；
- 做性能实验；
- 重构实现；
- 改进诊断；
- 生成 fuzz target；
- 提交兼容性报告。

Codex 不可以：

- 为通过测试而偷偷改变语言语义；
- 在 Parser、Interpreter 和 Type Checker 中各自实现不同规则；
- 引入无 RFC 的关键字；
- 直接添加 `unsafe` 绕过设计；
- 将内部 Rust 行为当成语言语义；
- 用字符串替换伪造 Semantic Transaction。

### 16.3 推荐 Agent Workstream

```text
Agent A：Source/Unicode/Lexer
Agent B：Parser/CST/AST
Agent C：Resolver/HIR
Agent D：Type/Effect/Capability
Agent E：Semantic Graph/Hash/Audit
Agent F：Interpreter/REPL
Agent G：Diagnostics/Formatter
Agent H：Conformance/Fuzz/CI
```

共享接口必须先合并设计，不允许各 Worktree 先发明不兼容数据结构。

### 16.4 每个 PR 的必需信息

```text
RFC reference
semantic impact
diagnostic impact
Unicode impact
graph schema impact
tests
migration
AI-generated provenance
```

## 18. 验收标准

只有同时满足以下条件，才能标记 `v0.0.1`：

### 18.1 可运行

```bash
zero run examples/人物.zero
```

成功输出预期结果。

### 18.2 可检查

```bash
zero check examples/人物.zero
```

返回 0。

错误程序返回稳定错误码和 JSON。

### 18.3 中文完整性

以下名称在所有阶段不被损坏：

```text
人物
血量
最大血量
受到伤害
生存状态
```

### 18.4 类型

- 普通函数可推导；
- 错误类型被拒绝；
- record 字段检查；
- 非穷尽 match 被拒绝；
- immutable assignment 被拒绝。

### 18.5 Effect/Capability

- Pure 函数显示空 Effect；
- Console 调用显示 `Console.Write`；
- 未声明 Capability 时拒绝。

### 18.6 Semantic Graph

- 每个定义有实验性 ID；
- reference edge 已解析；
- 改空白不改变 Graph Hash；
- 改局部参数名不改变 BodyId；
- 改函数行为改变 BodyId；
- Graph JSON 通过 Schema 测试。

### 18.7 稳定性

- Parser fuzz 运行规定时间无 panic；
- 全部 conformance tests 通过；
- REPL 与文件执行共享同一 Core；
- Windows/Linux/macOS 至少构建通过。

## 19. 预计工作量

在规范保持稳定、Codex 多 Worktree 并行的情况下，v0.0.1 的工程量估计为：

```text
80–160 个有效 Agent-hours
```

合理的日历时间：

```text
技术尖峰：1 天内
可运行内核：2–4 天
达到本 RFC 验收标准：5–10 天
```

该估计包含：

- 实现；
- 测试；
- 诊断；
- 文档；
- Unicode 安全；
- 集成返工。

它不包含：

- 品牌与商标处理；
- Native Backend；
- Actor；
- GC；
- 完整 IDE；
- 形式证明。

最大的风险不是 Codex 写代码速度，而是语言语义反复变化导致多分支返工。

## 20. 风险

### 20.1 命名风险

`zero` 已被高度相似项目使用，属于发布阻塞项。

### 20.2 语义范围膨胀

若 v0.0.1 同时实现 Actor、GC、Ownership 和 GPU，项目极可能失去可验证核心。

### 20.3 Unicode 安全

仅“允许中文”而不实现 UAX #31、UTS #39/#55，会制造供应链和审计风险。

### 20.4 `=` 上下文复杂度

`=` 同时承担绑定、初始化与赋值，需要清晰 Parser/Checker 分层和优秀诊断。

### 20.5 Semantic Hash 过早冻结

若在 Core IR 尚未稳定时承诺永久 ID，会阻碍语言演化。因此 v0.0.1 ID 必须标为 experimental。

### 20.6 Interpreter 泄漏实现语义

Rust 内部使用 `Arc`、`HashMap` 或 arena，不得被误写成语言的最终内存模型。

### 20.7 AI 驱动的规范漂移

多 Agent 并行可能实现多个互不兼容的“小语言”。RFC 与 Conformance 必须是合并门槛。

## 21. 被拒绝的替代方案

### 21.1 先实现 Parser，语义图以后再加

拒绝。Semantic Graph 若不是第一版架构，后续会成为旁路索引，而不是程序语义核心。

### 21.2 第一版直接编译到 Rust

暂不采用。Transpile-to-Rust 对早期 Native 实验有价值，但会：

- 把 Rust 生命周期和错误模型泄漏到语言；
- 让解释/语义测试变慢；
- 模糊“零”的行为与 Rust 后端行为。

v0.0.1 先使用 Core Interpreter。

### 21.3 只允许 ASCII 标识符

拒绝。中文和其他自然语言标识符是正式设计目标，不是后续装饰。

### 21.4 提供中文关键字全集

暂不采用。会产生多套语法、文档和工具分裂。先支持高价值的中文领域标识符。

### 21.5 使用 F# 的 `<-` 赋值

拒绝于本 RFC。采用 `=` 赋值和 `==` 相等，以支持更自然的：

```fsharp
人物.血量 = 100
```

### 21.6 所有状态都放入 Actor

拒绝。Actor、Task、Node、Kernel 与 Value Function 有不同适用边界。

### 21.7 AI 直接编辑 JSON Graph

v0.0.1 不作为默认工作流。AI Transaction API 需要稳定 Schema 和事务检查；第一版先输出查询 Graph，修改协议后续 RFC 实现。
