# RFC-0005: Restricted Traits and Constraint Solving / 受限 Trait 与约束求解

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-21
> 目标版本：v0.1 Living
> 作者/Owner role：type-system-design
> 相关缺口：GAP-TRAIT-COHERENCE-001
> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC is Accepted as the v0.1 Trait design authority. It narrows the first
Trait slice so that cross-package behavior is deterministic and can be
represented in the existing checked pipeline. Implementation still requires the
conformance evidence listed below and must not change the v0.0.1 Seed surface.

## Summary

Ling Traits describe capabilities and constraints; they do not form an
inheritance hierarchy. This RFC proposes a deliberately restricted, nominal
Trait model with package-aware coherence, explicit obligations, deterministic
selection, and dictionary passing into Checked Core. The proposal is designed
to unblock the G1 Trait slice without prematurely adding specialization,
implicit dynamic dispatch, associated type families, or advanced type-level
programming.

## Normative changes

The following requirements become normative when this RFC is Accepted.

### 1. Declaration and implementation shape

1. A Trait declaration MUST have a nominal `TraitId`, a finite ordered member
   list, and explicit type parameters. Member names MUST be unique within the
   declaration.
2. The first accepted grammar uses `trait Name<'a> =` followed by indented
   `member: Type` lines and `impl Name Receiver =` followed by indented `let`
   member definitions. Type parameters use the existing apostrophe-name form
   inside angle brackets; no alternate `where` spelling is accepted.
3. An `impl` declaration MUST name exactly one Trait and one nominal receiver
   type, followed by implementations for every required member. Partial impls
   and structural member matching MUST be rejected.
4. Trait and `impl` syntax MUST preserve the original UTF-8 byte span for every
   declaration, member, type, and constraint. The parser MUST reject malformed
   declarations without interpreting an unchecked AST.
5. Trait declarations MUST be statically dispatched. A future trait-object
   boundary may opt into dynamic dispatch through a separate accepted RFC.

The concrete surface spelling is fixed for the first slice. Parser layout
productions and recovery diagnostics reuse the existing offside and source-span
decisions; no second grammar or localized keyword view is introduced.

### 2. Nominal identity and obligations

1. Generic function parameters use the existing apostrophe-name form in an
   angle-bracket list after the binding name. A `requires` clause follows the
   list and contains comma-separated Trait applications, for example
   `let render<'a> requires Renderable<'a> value = ...`. The clause is the only
   first-slice source of user-written Trait obligations.
2. Trait satisfaction is nominal: a type satisfies a Trait only through a
   declared, selected `impl`; matching member shapes alone MUST NOT create an
   implementation.
3. Type checking MUST collect normalized obligations before selecting an impl.
   Constraint collection MUST preserve the source-origin chain and MUST NOT use
   hash-map or filesystem order as a semantic tie breaker.
4. An obligation is solved only when exactly one legal candidate remains after
   package visibility, orphan, and overlap checks. Zero candidates and multiple
   candidates are distinct static failures.
5. Recursive obligations MUST terminate using the ordered tuple
   `(obligation depth, TraitId, receiver type head, canonical arguments)`. A
   repeated tuple is a cycle and MUST be rejected; an implementation resource
   limit of 64 nested obligations MUST be reported as a bounded static failure.

### 3. Coherence, orphan, and overlap

1. Within one `ProgramSnapshot`, the pair `(TraitId, receiver type head)` MUST
   have at most one applicable primary impl.
2. A package MAY define an impl when it owns the Trait or owns the receiver type
   head. An impl where both are foreign MUST be rejected (the orphan rule).
3. Two impls that can apply to the same receiver and Trait MUST be rejected;
   specialization and priority-based overlap resolution are not part of this
   RFC.
4. Generic impl declarations are outside the first accepted slice. A later RFC
   MAY add them only with a complete overlap proof; a candidate ordering used
   for diagnostics MUST NOT change the selected semantic result.
5. Package graph and lock identity MUST be inputs to coherence checking, while
   host paths, allocation addresses, and Rust map iteration order MUST NOT be
   observable.

### 4. Checked Core and Semantic Graph

1. A successful selection MUST lower to an explicit immutable dictionary
   witness with fields `(TraitId, ImplId, receiver type, ordered member
   definitions)` in Checked Core. Later backends MUST consume that witness and
   MUST NOT re-run Trait selection.
2. The resolved `TraitId`, `ImplId`, receiver type identity, and ordered member
   witness MUST be represented in the checked semantic projection. Unresolved
   obligations MUST never appear in executable Typed Core.
3. If implementation selection changes, the affected checked projection and
   dependent Semantic IDs MUST change. Whitespace, comments, source paths, and
   hash seeds MUST NOT change the selected witness or its canonical ordering.

### 5. Diagnostics and compatibility

1. This RFC allocates no diagnostic code and changes no current diagnostic
   schema. The implementation MUST allocate bilingual stable codes through
   `docs/ERROR-CODES.md` before any user-visible Trait diagnostic lands.
2. All future Trait diagnostics MUST retain original UTF-8 byte spans, identify
   the obligation/source chain, and distinguish missing, ambiguous, illegal
   orphan, and overlapping implementations.
3. Trait syntax and semantics MUST remain outside the v0.0.1 Seed support
   matrix. No CLI, LSP, package, bytecode, or protocol entry point may claim
   Trait support until its implementation slice has independent fixtures.

## Conformance plan

Acceptance requires executable evidence covering at least:

- positive declarations, impls, generic obligations, nested constraints, and
  dictionary lowering;
- negative duplicate members, missing members, foreign/foreign orphan impls,
  overlapping impls, unsatisfied obligations, and recursive non-termination;
- cross-package ownership, package graph changes, locked/offline resolution,
  and visibility boundaries;
- deterministic candidate selection and canonical witness bytes across process
  runs, hash seeds, source paths, filesystem order, CRLF, Unicode identifiers,
  and original UTF-8 spans;
- differential checked-interpreter/VM results after explicit witness lowering;
- migration vectors for any future rule or Semantic ID version change.

The intended suites are `tests/conformance/`, package graph fixtures, semantic
identity fixtures, and the checked-core/VM differential harness. Acceptance of
this RFC establishes the required evidence; it does not claim that the later
implementation fixtures already pass.

## Compatibility impact

- Source: new v0.1 syntax only; v0.0.1 remains unchanged.
- Binary/runtime: no current bytecode or runtime change; a future bytecode
  witness encoding needs a separate accepted versioned contract.
- CLI/LSP: none in this RFC; editor and command exposure require separate
  protocol decisions.
- Diagnostics: no allocation or schema change in this RFC; future codes must
  be registered and bilingual.
- Schema/Semantic ID: no current schema change; accepted implementation must
  version any new public projection and include resolved implementation identity.
- Data/migration: no migration is introduced by this RFC.
- Determinism/Unicode: proposed behavior preserves deterministic ordering and
  Unicode 17.0.0/original UTF-8 spans; no generated table changes.

## Unresolved alternatives

The following are explicitly deferred extensions and do not block acceptance of
the restricted first slice: associated types, default methods, supertraits,
negative impls, specialization, generic/blanket impls, trait objects, higher-
kinded types, and localized keyword views. Each requires a separate RFC with
cross-package compatibility and termination evidence.

Rejected for this RFC: alternate declaration punctuation, a `where` alias for
`requires`, specialization-based priority, structural duck typing,
foreign/foreign impls, implicit dynamic dispatch, and implementation-defined
candidate ordering. They would make package compatibility or deterministic
selection depend on non-local or unstable information.
