# RFC-0024: Project graph check Preview / 项目图检查 Preview

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-22
> 目标版本：v0.1 Preview
> 作者/Owner role：package-design
> 相关缺口：GAP-PROJECT-CLI-INTERFACE-001
> 生命周期记录：`docs/governance/lifecycle.toml`

RFC-0024 defines one bounded project command over the already accepted
`ling.manifest/1`, module-discovery, package-graph, and `ling.lock/1` library
boundaries. It is not the complete project CLI promised by the execution plan.

本 RFC 只定义一个受限的 `ling project check` Preview 命令：显式选择项目
manifest，离线验证模块图和锁文件，并提供不泄露主机路径的文本/JSON 结果。
它不定义语义编译、测试发现、构建产物或网络/注册表行为。

## Summary

The command gives automation a safe way to validate one explicit RFC-0002
project without silently searching parent directories or rewriting a lock file.
It reuses the production `ling-project` readers and graph resolver; it does not
create a second package-resolution pipeline.

## Status and scope

- Current lifecycle state: `Accepted`
- Stable implementation basis: `yes` for the Experimental
  `ling.project.check/0.1` command/report only
- In scope:
  - the exact command `ling project check`;
  - one required `--manifest-path <path>` option whose final component is
    `ling.toml`;
  - one required `--locked` option, which requires an existing byte-valid lock
    exactly matching the local RFC-0002 graph;
  - optional `--format human|json`, defaulting to human output;
  - root module discovery and recursive local package-graph validation;
  - path-free deterministic success output and the
    `ling.project.check/0.1` JSON report;
  - existing project diagnostics and the accepted Seed exit classes;
- Out of scope:
  - parent-directory manifest search, workspace manifests, registry/Git/URL
    dependencies, network access, or environment-based selection;
  - lock creation, lock rewriting, cache writes, source writes, or arbitrary
    build scripts;
  - semantic compiler checking, `run`, `test`, test discovery, build artifacts,
    backend selection, package publication, or installation;
  - changes to existing file-oriented `ling check`, `ling run`, `ling fmt`,
    `ling semantic`, `ling audit`, REPL, or LSP commands;
  - Stable 1.0 compatibility or a public JSON schema file;
- Normative documents and clauses affected:
  - RFC-0002 §§1–7 for manifest, discovery, local graph, and locked resolution;
  - DEC-0003 for command parsing and Preview CLI baseline;
  - DEC-0013 for process exit classes;
  - `docs/SEMANTICS.md`, `docs/LANGUAGE.md`, and `docs/ROADMAP-1.0.md` for
    `ling`/`.ling` naming and compatibility constraints.

## Normative changes

1. The command MUST be spelled `ling project check`. `project` without the
   `check` subcommand, unknown project subcommands, and unknown options MUST be
   rejected as invalid usage with exit code `2`.
2. `--manifest-path PATH` MUST appear exactly once. `PATH` MUST be a readable
   file whose final component is exactly `ling.toml`; no parent search,
   implicit default, path alias, or second positional path is permitted. The
   project root is the directory containing that manifest.
3. `--locked` MUST appear exactly once. The command MUST invoke the existing
   `ling-project` locked resolver and MUST fail when `ling.lock` is missing,
   malformed, non-canonical, or inconsistent with the complete local graph.
   The command MUST NOT create or rewrite a lock file.
4. Project checking is always local and offline. The command MUST perform no
   registry, Git, URL, network, shell, environment, or parent-workspace lookup.
   `--offline` is therefore not a second mode and MUST be rejected as an
   unknown option rather than suggesting that an online mode exists.
5. A successful check MUST validate the manifest, root module discovery, and
   complete recursive local package graph. It MUST NOT run the language
   parser/type/effect/evaluator pipeline and MUST NOT claim that source
   semantics or runtime behavior was checked.
6. Human success output MUST be one deterministic stdout line containing the
   package name/version, entry module, module count, and package count. It MUST
   contain no absolute path, temporary directory, host separator, lock bytes,
   allocation identity, or map-order artifact. Diagnostics and usage errors
   remain on stderr under the existing CLI channel policy.
7. JSON success output MUST be one UTF-8 object with these exact required
   fields and values:
   ```json
   {
     "protocol": "ling.project.check/0.1",
     "status": "ok",
     "package": {"name": "...", "version": "..."},
     "entry": "...",
     "modules": 0,
     "packages": 0,
     "graph": "..."
   }
   ```
   `graph` is the existing path-free RFC-0002 package-graph identity. No
   absolute manifest path or source bytes may be emitted.
8. A project validation failure MUST exit with the existing compile/validation
   failure class `1` and, in JSON mode, emit one object with `protocol`,
   `status: "error"`, and a deterministic `diagnostics` array containing the
   existing Diagnostic JSON values. No new `L-<DOMAIN>-<NUMBER>` code is
   allocated by this RFC. Internal invariant/I/O failures use the existing
   internal-failure class `5`.
9. The report marker is `ling.project.check/0.1`. It is Experimental and
   current-writer-only. Readers MUST NOT infer support for project `run`,
   `test`, `build`, publication, or Stable 1.0 behavior from this marker.

## Conformance plan

- Add parser tests for the exact subcommand, required/repeated manifest and
  locked options, format placement, unknown options, stale `zero` spellings,
  and invalid path forms.
- Run valid single-package, multi-module, dependency, and Unicode-name
  projects from distinct temporary roots and compare human/JSON output bytes.
- Reject missing, malformed, non-canonical, and mismatched locks without
  changing `ling.lock` or any source file; retain the existing bilingual
  project diagnostics and spans.
- Prove that the command performs no parent search, network/registry access,
  semantic evaluation, test discovery, or build-artifact publication.
- Verify path-free JSON, package-graph identity stability, deterministic field
  order, exit codes, stderr/stdout separation, and current-writer-only report
  compatibility.

## Compatibility impact

- Language and source: no syntax, type/effect, source-span, Semantic ID, or
  Unicode 17.0.0 behavior changes.
- CLI: adds only the Experimental nested `ling project check` command; all
  existing commands and their accepted options remain unchanged.
- Diagnostics: reuses existing project/manifest/lock diagnostics; no code,
  severity, template, or registry allocation changes.
- Protocol: registers `ling.project.check/0.1` without a schema file or Stable
  promise. Incompatible report changes require a new version and migration
  evidence.
- Filesystem and data: reads only the explicit project root and lock; no lock,
  source, cache, build, or network artifact is written.

## Unresolved alternatives

- An update-mode command that creates or rewrites `ling.lock` is deferred to a
  separate decision because check commands should be side-effect free.
- Semantic compilation of all project modules, project `run`/`test`, and build
  artifact semantics remain separate PRJ-1107/CLI tasks.
- Parent search and workspace-root discovery remain deferred until an accepted
  workspace-selection policy exists.
