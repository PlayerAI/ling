# RFC-0019: Seed Interpreter–VM Differential Contract / Seed Interpreter–VM Differential 契约

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-21
> 目标版本：v0.0.1 Seed
> 作者/Owner role：vm-design
> 相关缺口：GAP-BYTECODE-SEMANTICS-001
> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC defines the executable comparison contract for VM-1209. It makes the
checked Seed interpreter the semantic oracle for the supported bytecode slices,
without making Rust representation, allocation, or instruction scheduling part
of Ling behavior.

本 RFC 规定 VM-1209 的可执行比较契约。它把经过检查的 Seed interpreter 作为
受支持字节码切片的语义基准，同时不把 Rust 表示、分配方式或指令调度纳入
Ling 行为。

## Summary

For each executable conformance source, the harness builds one checked
`ProgramSnapshot`, runs the reference interpreter and a verifier-created VM
program, and compares a bounded logical outcome. Success compares logical host
events and the Unit entry result. Failure compares the stable Fault category,
operation, source name, original UTF-8 byte span, and committed-effect state.
The harness also freezes the checked snapshot identity and verifies that
lowering/round-trip does not change it. It never compares addresses, heap
layout, frame layout, Rust debug output, physical paths, or instruction counts.

对于每个可执行 conformance 源文件，harness 构建一个 checked `ProgramSnapshot`，
分别运行 reference interpreter 和由 verifier 创建的 VM 程序，并比较有界的逻辑
结果。成功时比较宿主逻辑事件和 Unit entry 返回结果；失败时比较稳定 Fault
类别、操作、源名称、原始 UTF-8 字节区间和已提交效果状态。harness 同时固定
checked snapshot identity，验证 lowering/round-trip 不改变该 identity。它绝不
比较地址、heap/frame 布局、Rust debug 输出、物理路径或 instruction count。

## Status and scope

- Current lifecycle state: `Accepted`
- Stable implementation basis: `yes` for the Experimental v1.0/v1.1/v1.2 VM slices
- In scope:
  - executable `tests/bytecode/v1/programs` sources with a checked `Main.main`;
  - source-level closure/recursion, aggregate/match, and mutable-place fixtures
    that already have Accepted lowering authorities;
  - logical `Console.write` event comparison;
  - Unit entry success and structured Runtime Fault comparison;
  - original source name/span, category/operation, and committed-state comparison;
  - deterministic checked snapshot identity and bytecode round-trip evidence.
- Out of scope:
  - comparing allocation addresses, Rust layouts, frame addresses, debug text,
    physical paths, or instruction counts;
  - treating verifier/internal errors as user Runtime Faults;
  - a general cross-version compatibility claim beyond explicitly supported 1.x
    readers;
  - decoder/verifier fuzzing, cancellation, and additional resource models
    owned by VM-1210;
  - Native/FFI or concurrent execution engines not present in this release.
- Normative documents or clauses affected:
  - `RFC-0014` §6 and conformance plan (observable Runtime Fault and differential
    fields);
  - `RFC-0015`, `RFC-0016`, `RFC-0017`, and `RFC-0018` for the covered VM slices;
  - `DEC-0012` for Semantic/Program identity.

## Normative changes

1. The harness MUST consume the same checked `ProgramSnapshot` for the
   interpreter and bytecode lowerer. It MUST NOT parse, resolve, infer types,
   or reconstruct semantics separately for the VM side.
2. A successful `Main.main : Unit -> Unit` run MUST compare the ordered logical
   host-event sequence and the Unit result. For Seed v0.0.1, `Console.write`
   is the only event source; each event is the exact UTF-8 text payload without
   a platform-specific rendering layer.
3. A Runtime Fault comparison MUST use only the stable projection:
   `(category, operation, source_name, start_byte, end_byte, committed)`. The
   category and operation use the existing registered names; the source span is
   the original half-open UTF-8 byte span; `committed` is true exactly when a
   prior host effect or a host failure marked the operation observable.
4. A VM `ExecutionError::Internal` or bytecode verification failure MUST fail
   the harness as an implementation/infrastructure defect. It MUST NOT be
   coerced into a user Fault or ignored as an allowed differential.
5. Every fixture MUST assert that independently rebuilt checked snapshots have
   equal `ProgramId` values. Bytecode encode/decode/verify round trips MUST
   preserve the logical outcome, while byte identity may differ only where an
   explicitly documented writer profile permits it.
6. The harness MUST bound source names, event text, Fault rendering, and fixture
   counts. It MUST compare logical events rather than process stdout/stderr
   bytes, and MUST keep stderr/diagnostic channels separate from Console events.
7. A differential failure MUST report the fixture logical name and the first
   mismatching projection field. Test output MUST NOT include physical paths,
   addresses, allocator details, or unbounded source text.

## Conformance plan

- Run the v1.0 hello, direct-call, and format-fault bytecode corpus through both
  engines and compare events, Unit result, Fault projection, source spans, and
  snapshot IDs.
- Add v1.1 closure/recursion and v1.2 aggregate/match/mutable-place source
  fixtures to the same table-driven harness.
- Include success, skipped-effect, deterministic Runtime Fault, and state
  mutation-through-observation cases; keep host capability failure and VM
  resource ceilings in their owning VM-1208/VM-1210 tests.
- Verify deterministic output across repeated snapshot construction and
  encode/decode/verify execution without comparing implementation internals.
- Keep malformed bytecode, fuzzing, cancellation, and resource stress evidence
  in VM-1210 rather than silently expanding this oracle.

## Compatibility impact

- Source semantics: none; the harness observes already accepted Seed behavior.
- Bytecode: no opcode, record, field, or format revision. `PROTO-BYTECODE`
  gains differential evidence while remaining Experimental.
- Diagnostics: no new diagnostic code or schema. Differential mismatches are
  test failures, not public Ling diagnostics.
- Semantic identity: compares existing `ProgramId` values but does not make
  bytecode bytes a Semantic ID or canonical semantic encoding.
- CLI, ABI/FFI, host paths, allocation layout, and Unicode 17.0.0: unchanged.

## Unresolved alternatives

- Comparing raw stdout/stderr, VM instruction counts, or heap addresses remains
  rejected because those values are host/implementation details.
- A three-way Interpreter–VM–Native oracle remains future work until an accepted
  Native execution contract exists.
- A tolerant Fault comparison that ignores source spans or committed effects is
  rejected because it would hide observable semantic regressions.
