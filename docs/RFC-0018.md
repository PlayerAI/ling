# RFC-0018: Seed VM Effect, Capability, and Fault Boundary / Seed VM Effect、Capability 与 Fault 边界

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-21
> 目标版本：v0.0.1 Seed
> 作者/Owner role：vm-design
> 相关缺口：GAP-BYTECODE-SEMANTICS-001
> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC is the accepted implementation authority for the VM-1208
Effect/Capability/Fault integration slice. It refines the existing
`RFC-0014`, `DEC-0010`, `RFC-0016`, and `RFC-0017` contracts without adding
source syntax, a new Effect, a new Capability, or a bytecode revision.

本 RFC 是 VM-1208 Effect/Capability/Fault 集成切片的已接受实现依据。它细化
现有 `RFC-0014`、`DEC-0010`、`RFC-0016` 和 `RFC-0017` 的契约，不增加源语法、
新的 Effect、新的 Capability 或新的字节码版本。

## Summary

The checked Effect row, bytecode metadata, injected host table, verifier, and
runtime Fault must form one deterministic boundary. A VM run receives only a
verified program, explicit limits, and explicit host capabilities. Reachable
`Console.Write` requirements are validated before the first user instruction;
host failures retain a stable category, operation, committed state, and
original UTF-8 source provenance. A panic raised by an injected host adapter is
contained at that boundary and becomes the existing `other` host category
instead of escaping as a Rust panic or a new user-facing diagnostic.

Checked Effect 行、字节码元数据、注入的宿主表、验证器和运行时 Fault 必须组成
一个确定性的边界。VM 运行只接收已验证程序、显式限制和显式宿主能力。可达的
`Console.Write` 要求必须在第一条用户指令前校验；宿主失败保留稳定类别、操作、
提交状态和原始 UTF-8 源位置。注入的宿主适配器产生的 panic 在边界处被封装，
转为既有 `other` 宿主类别，不得作为 Rust panic 或新的用户诊断泄漏。

## Status and scope

- Current lifecycle state: `Accepted`
- Stable implementation basis: `yes` for the Experimental v1.0/v1.1/v1.2 VM slices
- In scope:
  - Effect closure for direct instructions, direct calls, and complete closure calls;
  - module Capability metadata and explicit host-capability preflight;
  - source-mapped Runtime Faults for capability and host failures;
  - stable host failure categories and committed-effect tracking;
  - containment of unwinding panics from injected host adapters;
  - aggregate and mutable-place v1.2 paths using the same boundary.
- Out of scope:
  - new source-level Effects or Capabilities;
  - dynamic capability discovery, ambient authority, or host-path identity;
  - new bytecode opcodes, records, wire tags, or format revisions;
  - interpreter/VM corpus expansion owned by VM-1209;
  - decoder/verifier fuzzing, cancellation, or resource-model expansion owned by VM-1210;
  - native ABI, FFI unwind guarantees, or aborting-process recovery.
- Normative documents or clauses affected:
  - `DEC-0010` (State and Capability model);
  - `RFC-0014` §§5–6 and §8 (Effect/Capability/Fault and source provenance);
  - `RFC-0016` and `RFC-0017` (v1.2 aggregate and mutable-place lowering).

## Normative changes

1. The lowerer MUST consume checked Typed Core. It MUST preserve the checked
   `Console.Write` Effect and module requirement, and MUST NOT synthesize an
   undeclared Capability. Local `State<T>` remains a checked semantic Effect;
   under `RFC-0017` it is represented by SSA updates and is not encoded as a
   host Capability or bytecode Effect tag.
2. For every function, the encoded Effect list MUST be sorted, duplicate-free,
   and equal to the transitive closure of reachable direct `ConsoleWrite`
   instructions, direct calls, and complete closure calls. A latent function
   type with `Console.Write` contributes the Effect only when a complete call is
   reachable. No host operation may be hidden by reordering or omission.
3. A module that contains a function in that closure MUST declare the matching
   `Console.Write` Capability. The module Capability list MUST be canonical and
   deterministic. The verifier MUST recompute the closure and reject metadata
   disagreement before constructing executable state.
4. The runtime host table MUST resolve `Console.write` only through the
   explicit injected `ConsoleCapability` handle. The VM MUST perform this
   resolution during entry preflight, before charging a step, frame, or heap
   limit and before any user Effect. Missing capability is a structured
   `capability_unavailable` Runtime Fault.
5. A host operation failure MUST become `RuntimeFaultKind::HostCapability` with
   operation `Console.write`, one of the stable categories
   `broken_pipe`, `permission_denied`, `interrupted`, or `other`, and the
   adapter-provided committed flag. Effects committed before a later Fault
   remain observable; no instruction after the Fault executes.
6. An unwinding panic raised while invoking an injected host adapter MUST NOT
   cross the VM API boundary. The VM MUST convert it to category `other` with
   committed state set to `true`, because the adapter gives no reliable proof
   that an externally observable write did not occur. The VM MUST NOT expose the
   panic payload, Rust type name, backtrace, OS text, or host path as Ling
   semantics. This requirement does not promise recovery from `panic=abort` or
   an FFI boundary that terminates the process.
7. Every capability or host Runtime Fault MUST retain the verified original
   source-map name and half-open UTF-8 byte span, the stable diagnostic code
   `L-RUNTIME-0001`, the operation/category facts, and the committed flag.
   Runtime Fault rendering remains bilingual and deterministic; no new
   diagnostic allocation is introduced by this RFC.
8. Bytecode bytes, metadata ordering, preflight order, Fault facts, and source
   spans MUST remain independent of process hash seeds, filesystem paths,
   allocation addresses, Rust layout, and host error text. Existing 1.0 and
   1.1 artifacts retain their behavior; v1.2 aggregate and mutable-place
   artifacts use the same rules.

## Conformance plan

- Verify positive direct-call, closure-call, aggregate, and mutable-place
  programs with exact Effect and module Capability metadata.
- Reject missing/extra/unsorted Effect and Capability metadata before execution
  and before any configured resource limit is charged.
- Assert that local `State<T>` is visible in checked effect evidence while no
  host Capability is required for the SSA-only v1.2 lowering.
- Exercise all four host error categories, both committed states, source-map
  spans, bilingual JSON diagnostics, and the no-output-before-preflight rule.
- Invoke a panicking Console adapter and assert a stable `other` Runtime Fault,
  committed state, original span, and no panic escapes the `execute_v1` API.
- Re-run encode/decode/verify/execute round trips and deterministic-byte checks
  across the supported 1.x revisions without comparing addresses or instruction
  counts.

## Compatibility impact

- Source semantics: none; the RFC implements only Effects and Capabilities
  already authorized by `DEC-0010` and the Seed checked pipeline.
- Bytecode: no opcode, record, field, tag, or version change. `PROTO-BYTECODE`
  gains explicit VM-1208 coverage while remaining Experimental.
- Runtime and diagnostics: host panics normalize to the existing
  `L-RUNTIME-0001`/`other` category; no new code, JSON schema, or exit contract
  is introduced.
- CLI, Semantic IDs, canonical semantic bytes, ABI/FFI, and Unicode 17.0.0:
  none changed.
- Security and determinism: explicit capability injection and preflight remain
  mandatory; host implementation details are not observable Ling data.

## Unresolved alternatives

- Dynamic host capability discovery remains rejected because it would make
  execution depend on ambient authority and would bypass checked requirements.
- Treating an adapter panic as a distinct public Fault category remains
  rejected; `other` is the already accepted stable category and preserves the
  diagnostic registry.
- Recovering from `panic=abort` or a terminating FFI host is outside a Rust VM
  boundary and remains future host-process supervision work.
