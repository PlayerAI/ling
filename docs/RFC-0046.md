## Summary

This RFC defines the Seed semantic-token taxonomy, modifier meanings, evidence
precedence, conservative recovery, client-supported legend projection, and
source-span/privacy rules required by LSP-2401. It authorizes taxonomy revision
`ling.semantic-token-taxonomy/0.1` as the basis for later typed generation and
transport work; it does not advertise a semantic-token provider or implement a
wire request.

本 RFC 定义 LSP-2401 所需的 Seed semantic-token 分类、modifier 含义、证据优先级、保守
恢复、客户端支持的 legend 投影以及源码跨度/隐私规则。它授权分类版本
`ling.semantic-token-taxonomy/0.1` 作为后续类型化生成与传输工作的基础，但不公布
semantic-token provider，也不实现 wire request。

## Normative changes

### 1. Taxonomy identity and canonical legend

The taxonomy identity is `ling.semantic-token-taxonomy/0.1`. The canonical
token-type order is:

```text
namespace type enum interface struct typeParameter parameter variable
property enumMember function method keyword comment string number operator
```

Every name above is an LSP 3.17 standard token type. Version 0.1 defines no
custom token type. Canonical modifier order is:

```text
declaration definition readonly modification documentation defaultLibrary mutable
```

The first six names are standard LSP modifiers. `mutable` is the only custom
modifier. Legend indices are presentation values, not Ling semantics; a writer
MUST construct them only through §5 and MUST NOT persist or expose the indices
as Semantic IDs.

### 2. Source-role mapping

After applying §4 precedence, one source token maps as follows:

| Proven source role | Canonical token type |
| --- | --- |
| module declaration, imported module name, import alias | `namespace` |
| type alias, primitive or other named type reference | `type` |
| variant type declaration | `enum` |
| Trait declaration or reference | `interface` |
| record type declaration | `struct` |
| type parameter or type variable | `typeParameter` |
| function, Trait, or implementation parameter | `parameter` |
| remaining value or local binding/reference | `variable` |
| record field declaration, field label, or checked projection | `property` |
| variant constructor declaration/reference/pattern | `enumMember` |
| callable value declaration/reference/call | `function` |
| Trait or implementation member declaration/reference/call | `method` |
| Seed keyword and `true`/`false` | `keyword` |
| line, block, or documentation comment | `comment` |
| text literal | `string` |
| integer or float literal | `number` |
| comparison, assignment, arithmetic, boolean, pipe, or arrow operator | `operator` |

Punctuation, delimiters, apostrophes used only as syntax, whitespace, newline,
layout, lexer error, and EOF tokens emit no semantic token. A name's spelling,
capitalization, Unicode script, or normalization form MUST NOT select its role.

### 3. Modifier semantics

- `declaration` marks a source declaration without an executable body: import
  aliases and Trait member signatures.
- `definition` marks module, type, constructor, field, value/function,
  parameter, Trait, implementation, and implementation-member definitions.
  One token MUST NOT carry both `declaration` and `definition`.
- `readonly` marks an exact immutable value, binding, parameter, or field
  declaration/reference. It MUST NOT be inferred merely because no write was
  observed in the current snapshot.
- `mutable` marks an exact mutable value, binding, or field declaration and its
  resolved references. It is mutually exclusive with `readonly`.
- `modification` additionally marks a checked assignment target. It does not
  imply that other references are mutable unless compiler identity proves it.
- `documentation` marks only a lexer-owned documentation comment.
- `defaultLibrary` marks an exact builtin or Prelude reference. It MUST NOT be
  applied by spelling or to user shadowing definitions.

No other modifier is defined. Absence of a client-supported modifier changes
only presentation and MUST NOT change token type, span, order, or compiler
analysis.

### 4. Evidence precedence and recovery

For every nonempty original source span, a generator MUST choose at most one
token type using this strict precedence:

1. exact checked definition or resolved-reference identity and role;
2. compiler-owned structural source role where identity is unnecessary, such
   as keywords, declaration syntax, parameters, fields, comments, and literals;
3. lexer-owned classification only for keywords, booleans, comments, text,
   numbers, and operators.

Lower evidence MUST NOT override higher evidence. An unresolved identifier,
lexer error, recovery placeholder, missing token, or synthetic zero-width token
emits nothing. Recovery MUST NOT classify a name from capitalization, nearby
diagnostics, Tree-sitter captures, message text, or a previous snapshot.

If checked analysis fails, the generator MAY emit only the six lexer-proven
families in precedence item 3. This is the complete 0.1 fallback; it does not
pretend resolution or type checking succeeded and carries no fabricated
declaration, definition, mutability, or library modifier.

### 5. Client-supported projection

A later provider MUST read the client's standard semantic-token capability.
Malformed known capability members are invalid initialization parameters;
ordinary unknown members are ignored. The selected legend is deterministic for
one client capability:

1. Walk the canonical type order and retain each client-supported type.
2. For an unsupported semantic category, use the first supported fallback in
   this table; if none is supported, omit that category's tokens:

| Category | Ordered fallback |
| --- | --- |
| `namespace` | `variable` |
| `enum`, `interface`, `struct`, `typeParameter` | `type`, `variable` |
| `parameter`, `property`, `enumMember` | `variable` |
| `method` | `function`, `variable` |
| `function` | `variable` |
| `type` | `variable` |
| `keyword`, `comment`, `string`, `number`, `operator`, `variable` | none |

3. Deduplicate projected types without changing first-occurrence order.
4. Retain canonical standard modifiers only when advertised by the client.
   Retain custom `mutable` only when the client advertises the exact string.
5. Deduplicate modifiers without changing canonical order.

A server MUST NOT advertise a semantic-token provider if the selected type
legend is empty. The eventual provider's Experimental discovery MUST carry the
exact taxonomy identity. Provider shape, requests, full/delta support, and
result identity remain LSP-2403 authority and are not claimed here.

### 6. Span, position, ordering, and snapshot truth

Compiler-owned original UTF-8 spans are authoritative. A token MUST have a
nonempty span inside one exact captured source. A multiline comment or text
token MUST be split at original line boundaries into nonempty line-local
segments; newline bytes and a CR in CRLF are never part of a segment. Every
segment retains the same type and modifiers.

A later LSP writer MUST project segment start and length through the encoding
negotiated by RFC-0004/DEC-0029. It MUST order segments by start position and
MUST reject overlap, invalid projection, a changed complete snapshot, or a
changed open-document version rather than clamp, reorder ambiguously, or emit a
partial success. BOM and CRLF remain governed by the source map.

### 7. Privacy, identity, and future concepts

Definition IDs and Semantic IDs MAY select the exact checked role internally
but MUST NOT be serialized, hashed into a result visible to clients, or exposed
as token types/modifiers. Canonical type text, Effect rows, Capability sets,
Trait witnesses, identifier security facts, host paths, allocation details,
and compiler debug text MUST NOT enter semantic-token data.

Effect and Capability are inferred checked facts in the current language, not
explicit source token roles. Version 0.1 therefore defines no `effect` or
`capability` type. `resource`, `actor`, `node`, `kernel`, `semanticId`,
`borrowed`, `unsafeBoundary`, and `generated` from the lower-authority plan are
also absent. Adding any such category requires Accepted source-span, privacy,
fallback, negotiation, and migration authority plus a new taxonomy marker.

## Conformance plan

- Freeze the exact canonical type/modifier order, standard/custom status,
  mapping table, exclusivity rules, and client projection/fallback algorithm.
- Cover modules/imports, aliases/records/variants/cases, Traits/implementations,
  type parameters, parameters, immutable/mutable values, fields, calls,
  assignments, builtins/Prelude shadowing, keywords, booleans, comments,
  literals, and operators.
- Verify checked identity beats structural and lexical evidence; invalid and
  unresolved identifiers are omitted while conservative lexical fallback never
  fabricates checked roles or modifiers.
- Cover Chinese and decomposed identifiers, emoji prefixes, BOM, CRLF,
  multiline comments/text, UTF-8/16/32 projection, nonempty line splitting,
  non-overlap, deterministic ordering, repeated snapshots, edits, stale
  versions, and dependency/read-only documents once transport exists.
- Cover clients supporting all, some, custom `mutable`, standard-only, and no
  token types/modifiers; unknown capability fields and malformed known fields.
- Prove no Semantic ID, DefinitionId, type/effect/capability fact, host path, or
  future language category enters the wire result.

## Compatibility impact

- **Taxonomy:** adds Accepted `ling.semantic-token-taxonomy/0.1` with no
  predecessor; it does not yet create an implemented public protocol.
- **Protocol inventory:** registers a Planned public semantic-token surface as
  Future. LSP-2402/LSP-2403 must supply generation and transport authority,
  executable fixtures, and a current protocol marker before implementation.
- **Diagnostics/schema/identity:** no `L-*` allocation, JSON schema, Semantic
  ID, DefinitionId, or canonical-byte change.
- **Language/runtime/data:** no syntax or semantics, Typed Core evaluation,
  interpreter, runtime, bytecode, VM, ABI, package, filesystem/network, or
  Unicode 17.0.0 table change.
- **Migration:** incompatible taxonomy order, mapping, fallback, modifier,
  negotiation, span, privacy, or exclusion changes require a new taxonomy
  marker and migration evidence.

## Unresolved alternatives

Typed reference/source-role generation, provider capability shape, full/delta,
result IDs, request parameters, document selection, temporary/dependency
policy, response limits, cancellation, caching, stale error codes, fixture
schema, Zed presentation, Stable lifecycle, and general Semantic Transactions
remain LSP-2402 through LSP-2404 and LSP-2501/LSP-2502 work.

Custom Effect/Capability and future resource/actor/node/kernel/ownership/borrow/
generated categories are rejected for 0.1 because the current checked facts do
not authorize an exact public source role and several concepts are not in the
implemented language subset.
