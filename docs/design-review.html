零语言（Ling）设计评审

评审对象：LANGUAGE.md · SEMANTICS.md · RFC-0001.md（v0.0.1 Seed 草案）

一、总体判断

这是一套少见的“知道自己要什么”的语言设计：v0.0.1 的范围切割、显式非目标、“为完成 v0.0.1 而伪造能力视为失败”这条线，体现了真正的工程纪律。

但它的风险不在执行，而在于同时押注了四五个各自都未被验证过的设计赌注——跨 Profile 统一语义、Effect/Capability/Ownership 全推导、Semantic Graph 双视图一致、AI 语义事务——这些赌注之间还会互相放大难度。文档的成熟度分布并不均匀：工程治理部分（RFC 流程、验收标准、测试策略）是资深水准；语言核心语义里有几笔（自动 Borrow、跨 Profile 语义）还停在愿望层面。两者之间的差距，就是接下来真正的工作量所在。

二、设计上正确的决策

  • “可以省略，不可隐瞒”（§2.2）是整套设计的定海神针。推导型语言最大的敌人是隐藏行为，这条原则配合 Audit Source 的强制展开，方向正确。
  • Effect 与 Capability 分开（§8）：行为事实和授权事实本来就是两件事，Pony 和 Koka 各做了一半，这里合起来想清楚了。时间、随机、网络不再是环境函数而是显式 Effect，对测试和回放的价值是实打实的。
  • 合同证据阶梯（§9）：Proved / RuntimeChecked / Tested / Assumed / Unverified 五档，且“不得把测试通过显示成已证明”——大多数形式化工具都没有这种诚实。
  • Unicode 安全不是装饰品（§5）：UAX #31 + UTS #39/#55 + NFC + 作用域内 confusable 检测，比几乎所有“支持 Unicode 标识符”的语言（包括 Rust）都认真。说明中文标识符是当真的一等公民，不是噱头。
  • ASCII 关键字 + 中文标识符的分工务实。翻译关键字历来制造方言分裂，这个坑躲开了。
  • REPL 必须复用同一套 Parser/Checker/Interpreter（RFC §11.3）、规范优先级高于实现、错误码稳定且不来自自然语言——这些是老手才会写进 RFC 的条款。

三、质疑与风险

1. “一门语言，三种严格程度”是最大的未验证假设 待验证

§2.4 说不是“Debug 时 GC 语言、Release 变 Rust”，但恰恰需要证明的就是这一点。Ownership 是会传染的：按 GC 假设写的代码（自由别名、闭包抓引用）在 Resource 纪律下根本编不过。如果 Explore 代码通常无法不重写就进 Critical，承诺就塌缩成“一套语法、三门语言”——正是文档宣称要避免的东西。同类尝试（Swift 的 noncopyable、Austral）都是单模型收尾。

建议这个机制最早写 RFC：拿出同一个非平凡函数在三个 Profile 下编译通过的具体样例，证明可移植性存在，否则趁早修改承诺。连带问题：Int 是任意精度（§6.2），那 Critical Profile 里 Int 是什么？跨 Profile 数值语义现在是有缝的。

2. = 身兼绑定和赋值 已采纳，改为 <-

原设计中 = 在三个上下文里意思不同（绑定 / 字段初始化 / 可变赋值），需要 EqualsExpression 延后消歧，并让“创建不可变绑定”和“修改已有 Place”这两个语义相反的操作共用同一个符号——优化的是新手前 10 分钟的熟悉感，付出的是永久的解析复杂度和教学困惑。

处理结果：赋值已改为 F# 风格的 <-，= 只承担绑定与初始化，词法层面无歧义。已同步修订 LANGUAGE.md §4.2、SEMANTICS.md §9.4、RFC-0001.md §6.4 / §8 EBNF / §8.1 / §20.4 / §21.5 及全部示例。

3. 自动 Borrow 推导是把 Rust 最难的东西做成了隐式 待验证

§4.4 / §9.3 从函数体推导参数是不是 &mut，意味着函数的类型取决于它的实现——改一行实现（加一处写），远处的调用方就变了。HM 类型推导是成熟的，可变义务推导不是。Rust 当年刻意让签名显式、把推导留在函数体内，换来的就是可预期的错误信息和分离编译。

好在 v0.0.1 的受限版本（只允许局部可变 binding、不许逃逸）是正确的试探姿势。建议长期保持“签名显式、调用点隐式 reborrow”，别把体→签名的泄漏固化进语言。

4. 中文标识符的难点不在词法，在生态 待办

文档把编译器内的部分解决得很好，但真实成本在外面：IME 与中英文标点切换的输入摩擦、CI 日志和终端字体、grep、代码评审工具。设计其实已经握有正确答案——Semantic ID 与显示名解耦 + 多语言别名（§5.8），能让同一项目在中文团队和英文团队各有视图。

但别名被推迟到 v0.0.1 之后，这意味着第一批代码（含标准库命名）会在别名系统存在之前定型，顺序上有风险。如果中文标识符是旗舰特性，别名 RFC 应该提前，而不是推后。

5. Semantic Graph 的 round-trip 会悄悄吃掉预算 待观察

“语义身份优先”的终局要同时维护 Author Source 和 Audit Source 两个可编辑视图且机械一致（§14.3）。Unison 走了很多年证明这条路能走通但极其昂贵——而人类依然活在 git diff 和 GitHub review 的文本世界里。parse_audit(render_audit(g)) = g 这个要求写进文档是对的，但请预期它会消耗比 Parser 本身更多的人力。

6. AI 治理有投机性基础设施的味道；推导域叠加会放大报错难度 待观察

“AI 不属于 TCB”（§2.3）的立场完全赞同，但在还没有真实用户时就设计 Semantic Transaction 的前置条件、保留约束、provenance 全套机制，是在为不存在的流量建收费站。v0.0.1 只做查询图输出、事务后置——这个裁剪是对的，保持住。

另外，Effect Row + Ownership + Region + Placement + Contract 全都进函数类型且全靠推导。推导失败时，用户面对的是五个约束域同时报错的场面，那会让 Rust 的 borrow 错误显得亲切。ling explain 应该是 v0.0.1 的一等公民，不是附属命令。

四、命名核查：ling

拼音“零”→ ling，转换本身很优雅，中文含义保住了。但 ling 也不是净土，只是冲突远比 Vercel 的 Zerolang 小：

  • np/ling：学术实验语言（LINear LaNGuage，线性类型 + 进程演算），自带 ling CLI。冷门且多年不活跃，但它确实是一门叫 ling 的语言。
  • LING（Erlang-on-Xen unikernel VM）：不是语言，是 BEAM 的独立运行时，同样冷门。

结论：这两个都够 obscure，不构成 Zerolang 那种“同赛道 + 同理念 + 同名”的致命冲突，ling 可以用。但 RFC-0002 冻结前应补一次正式检索：crates.io / npm 的 ling 占用、.ling 扩展名冲突、商标库，并在文档里留下检索记录。

五、优先行动建议

  1. 先证“跨 Profile 可移植”：同一个带可变状态的函数，Explore 和 Critical 各编一遍，把过程和限制写成 RFC。这是整个设计的承重墙。
  2. 在语法冻结前重新表决 = 赋值。已完成 已采纳 <- 方案，三份文档已同步修改。
  3. 把多语言别名提前到标准库命名定型之前，否则第一批代码会把命名惯例锁死在单一语言上。
