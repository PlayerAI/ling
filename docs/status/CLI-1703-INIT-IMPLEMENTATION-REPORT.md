# CLI-1703-INIT implementation report

## Scope

This report covers the bounded child authorized by Accepted DEC-0038. It does
not claim `test`, `build`, workspace discovery, editor integration, or any
other future project command.

## Implemented behavior

- `ling init [--format human|json] [--name package] [--display-name text] <directory>`
  is parsed by the existing hand-written CLI catalog.
- The destination must be missing and its parent must already be a directory;
  no parent search, overwrite, network, shell, or environment lookup occurs.
- The scaffold is staged in a private sibling directory and committed with one
  directory rename after manifest parsing, module discovery, and lock update
  succeed.
- Generated bytes are fixed UTF-8/LF content for `ling.toml`, `src/Main.ling`,
  `.gitignore`, and canonical `ling.lock/1`.
- Success JSON is `ling.init/0.1`; host filesystem failures use `L-IO-0003`.

## Evidence

- Implementation: `crates/ling-cli/src/init.rs` and `crates/ling-cli/src/main.rs`.
- Process tests: `crates/ling-cli/tests/init.rs`.
- Protocol/schema fixtures: `tests/protocols/init/`, `schemas/init/0.1/`.
- Authority: `docs/decisions/0038-cli-init-command.md`.

## Compatibility and determinism

RFC-0002 manifest and lock semantics are reused without new fields. Physical
paths appear only as the requested report operand and are excluded from package
or lock identities. Repeated invocations with identical operands produce the
same generated bytes; failed attempts remove only private staging state.

## Deferred

Overwrite/force, current-directory defaults, template selection, `.zed` files,
workspace manifests, registry dependencies, and project test/build behavior
remain deferred under the parent CLI/project gaps.
