# RFC-0020: Seed VM Robustness, Cancellation, and Resource Evidence / Seed VM 健壮性、取消与资源证据

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-21
> 目标版本：v0.0.1 Seed
> Owner role：vm-design
> 相关缺口：GAP-BYTECODE-SEMANTICS-001
> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC closes the VM-1210 robustness boundary without changing Ling source
semantics or the `ling.bytecode/1.x` wire formats. It defines an explicit,
cooperative host cancellation token, preserves the existing Runtime Fault
diagnostic identity, and fixes the evidence obligations for fuzzing and
resource-limit stress.

本 RFC 在不改变 Ling 源码语义或 `ling.bytecode/1.x` wire format 的前提下，
收口 VM-1210 健壮性边界。它定义显式的协作式宿主取消 token，保留现有
Runtime Fault 诊断身份，并固定 fuzz 与资源限制压力测试的证据义务。

## Summary

RFC-0020 authorizes only the Experimental VM host-control and robustness
evidence needed by VM-1210. It does not add a Ling source feature, bytecode
field, CLI command, or Stable protocol.

本 RFC 仅授权 VM-1210 所需的实验性 VM 宿主控制接口与健壮性证据，不增加
Ling 源码功能、字节码字段、CLI 命令或 Stable 协议。

## Status and scope

- Current lifecycle state: `Accepted`
- Stable implementation basis: `no`; the control API remains Experimental.
- In scope:
  - `ling.vm.control/0.1` `CancellationToken` and the explicit
    `execute_v1_with_cancellation` entry point;
  - cancellation checks before the initial capability preflight and before
    every instruction or terminator;
  - deterministic `cancelled` Runtime Fault projection with the existing
    `L-RUNTIME-0001` diagnostic code and original source span;
  - deterministic mutation of a valid bytecode seed in the existing fuzz
    target, repeated decode/verify, bounded diagnostics, and no-panic behavior;
  - table-driven step, frame, heap, oversized-table, and malformed-UTF-8
    resource evidence.
- Out of scope:
  - preemptive thread interruption, signal handling, process termination, or
    rollback of effects already committed;
  - Ling `Task`, `Scope`, `Cancel`, async, Actor, LSP request cancellation, or
    cancellation propagation semantics;
  - a common logical heap model, wall-clock deadline, scheduler, or replay
    protocol;
  - any opcode, bytecode field, format revision, CLI command, ABI/FFI rule, or
    Native/Concurrent execution engine.
- Normative documents or clauses affected:
  - `RFC-0014` §6–§8 for Runtime Faults, explicit limits, source maps, and
    deterministic execution;
  - `RFC-0018` for the host Capability/Fault boundary;
  - `RFC-0019` for the differential harness boundary;
  - `DEC-0013` for entry/runtime failure behavior.

## Normative changes

1. `CancellationToken` MUST be an explicit host-owned, monotonic request
   signal. Calling `cancel` more than once is idempotent. The token MUST NOT
   be inferred from a source Effect, Capability, wall clock, or thread state.
2. `execute_v1` MUST retain its existing non-cancellable behavior. The
   explicit `execute_v1_with_cancellation` entry point MUST accept a verified
   program, explicit `ExecutionLimits`, injected host Capabilities, and one
   token. It MUST NOT add an ambient cancellation source.
3. The cancellable entry point MUST check the token before Capability preflight
   and before every instruction or terminator. If cancellation is observed, it
   MUST stop before executing that operation and return a `cancelled` Runtime
   Fault mapped to the current verified source span. A preflight cancellation
   wins over missing Capability and configured resource limits.
4. Cancellation MUST preserve the existing committed-effect rule: effects
   completed before observation remain visible and set `committed`; no effect
   after the cancellation boundary may execute. Cancellation MUST NOT roll back
   host output or mutate a Ling `Result` value.
5. The `cancelled` Runtime Fault MUST use category `cancelled`, operation
   `execution.cancelled`, the original source name and half-open UTF-8 byte
   span, and the existing `L-RUNTIME-0001` diagnostic schema and code. No new
   diagnostic allocation is authorized by this RFC.
6. The bytecode fuzz target MUST run arbitrary input and bounded mutations of
   the checked valid Hello seed through decode/verify twice, require identical
   outcomes, and bound any rendered diagnostic. A panic, nondeterministic
   result, partial executable publication, or unbounded diagnostic is a fuzz
   failure. Fuzzing MUST not claim semantic validity for mutated artifacts.
7. Resource evidence MUST cover step and frame exhaustion before the charged
   operation, heap failure without partial allocation, verifier oversized-table
   rejection, malformed UTF-8 metadata rejection, and cancellation before and
   after a committed host effect. It MUST compare only stable Fault facts and
   logical host output, not allocator layout or addresses.

## Conformance plan

- Cancel before entry with missing Capability and zero limits; require a
  source-mapped uncommitted `cancelled` Fault.
- Have a host adapter cancel after one successful `Console.write`; require the
  first event, committed state, and no later event.
- Run the existing step/frame/heap and malformed decoder corpora together with
  deterministic valid-seed mutations and bounded diagnostic rendering.
- Build the excluded fuzz workspace with the locked offline dependency set;
  execute sanitizer corpus smoke only on the pinned CI host when the local
  Windows ASan runtime is unavailable.

## Compatibility impact

- Source semantics, Checked Core, Effect rows, Capability closure, and
  `ling.bytecode/1.0`, `1.1`, and `1.2` bytes are unchanged.
- `ling.vm.control/0.1` is a new Experimental host-control API and is not a
  bytecode or CLI compatibility promise.
- Runtime Faults reuse `L-RUNTIME-0001`; JSON fields and Semantic IDs are
  unchanged. The new stable operation/category are confined to this accepted
  Experimental VM control boundary.
- Unicode remains 17.0.0; original UTF-8 source spans and deterministic logical
  names remain authoritative.

## Unresolved alternatives

- Preemptive cancellation is rejected because it cannot guarantee source-order
  effect boundaries or safe host unwinding in this Seed VM.
- Treating cancellation as a step-limit exhaustion is rejected because the
  host request and deterministic resource budget have different causes.
- Structured Task/LSP cancellation remains governed by their own future RFCs.
