## Summary

This RFC defines the bounded Preview cancellation contract required by
LSP-2502. The stdio transport associates standard `$/cancelRequest`
notifications with live JSON-RPC request IDs, propagates the existing
cooperative token through cancellable analysis, and publishes either one
complete response or no partial artifact. Its public marker is
`ling.lsp.request-cancellation/0.1`.

本 RFC 定义 LSP-2502 所需的有界 Preview 取消契约。stdio 传输将标准
`$/cancelRequest` 通知与存活的 JSON-RPC 请求 ID 关联，把现有协作取消 token
传入可取消分析，并且只发布一个完整响应，绝不发布部分产物。公开版本标记为
`ling.lsp.request-cancellation/0.1`。

## Normative changes

### 1. Protocol identity and discovery

The protocol marker is `ling.lsp.request-cancellation/0.1`. Every successful
initialize response MUST advertise this fixed discovery object at
`capabilities.experimental.lingRequestCancellation`:

```json
{
  "method": "$/cancelRequest",
  "requestCancelledCode": -32800,
  "requestIds": ["number", "string"],
  "version": "ling.lsp.request-cancellation/0.1"
}
```

No client capability or dynamic registration is required. Changing the
method, ID domain, precedence, error code, or discovery fields incompatibly
requires a new protocol marker and migration evidence.

### 2. Request identity and lifetime

After the stdio reader accepts a syntactically valid JSON-RPC request frame
whose `id` is a string or number, it MUST create one fresh DEC-0031 token and
associate it with the exact JSON value before making the request executable.
String comparison is scalar-value exact; number comparison uses the exact
accepted JSON number representation. A null ID remains accepted by RFC-0004
but is not cancellable.

The association remains live until the single request response has been
selected, an exit outcome has been selected, or transport processing aborts.
Cleanup MUST remove only that request's token. A second request using an
already-live exact ID MUST return Invalid Request `-32600` and MUST NOT execute
or replace the first association. Reuse after cleanup creates an independent
token.

### 3. Cancellation notification

The accepted wire form is a JSON-RPC notification with method
`$/cancelRequest` and an object parameter containing exactly one required
known member `id`; ordinary unknown members are ignored. `id` MUST be a string
or number under §2. A valid notification atomically cancels the currently live
matching token before its own ordered dispatch. Unknown, duplicate, or late
cancellation is an idempotent no-op. It never cancels a future reuse of the
same ID.

Notifications never receive a response, including malformed cancellation
notifications. A request-form `$/cancelRequest` is invalid and returns
Invalid Request `-32600`; it has no cancellation effect. Invalid JSON-RPC
version, method shape, parameter shape, null ID, boolean, array, or object ID
has no cancellation effect. The ordinary RFC-0004 parser still owns any
response required for a malformed request envelope.

### 4. Transport and execution order

The stdio reader MAY run independently from the single request executor so it
can observe cancellation while analysis is running. Frames and resulting
responses remain in accepted input order; `ling-lsp` MUST NOT execute two
mutable server requests concurrently. The reader MUST perform only bounded
envelope inspection and token signalling; all lifecycle, parameters, state,
and method behavior remains owned by `LspServer`.

Cancellation observation is cooperative, not a timing guarantee. If a token
is observed before the final publication checkpoint, cancellation wins. Once
the complete response has been selected for framed output and the association
is cleaned up, a later notification is a no-op. Scheduling, wall-clock delay,
thread identity, and host allocation MUST NOT enter a response.

### 5. Propagation and compiler queries

The transport-owned token MUST be supplied to every cancellable analysis
handler. At minimum, workspace-symbol index construction and selection,
rename planning, completion candidate validation and resolve, and semantic
token generation/delta construction MUST check before compiler work, at
bounded loops or stage boundaries, and immediately before publication.

Compiler-backed cancellable entry points MUST return typed
`QueryError::Cancelled` when a checkpoint observes cancellation. Query stages
MUST check before expensive work, between bounded module/solver/index stages,
and before inserting a newly computed cache entry. A cancelled or failed
stage MUST NOT insert a partial value. A complete immutable dependency result
published before a later cancellation observation MAY remain cached; this is
not partial request publication and must remain behaviorally invisible.

The compiler cancellation probe is an in-process observation only. It carries
no request ID, deadline, document version, path, diagnostic, VM fault, or
serialized cache identity.

### 6. Atomic publication and response precedence

A cancellable request MUST build response data and any cache/history/update
batch privately. Immediately before mutating session state or returning
success it MUST, in order, check cancellation and revalidate its RFC-0030
snapshot. Cancellation has precedence over freshness, success, limitation,
and publication when already observed at that checkpoint; an earlier
parameter, lifecycle, or compiler failure retains its existing error.

Observed cancellation returns standard RequestCancelled `-32800` with a
bilingual fixed message appropriate to the method. It publishes no partial
Workspace Edit, completion-resolve handle batch, workspace index, semantic
token result/history entry, diagnostics, source mutation, or Ling diagnostic.
The JSON-RPC error is a transport result and does not allocate an
`L-<DOMAIN>-<NUMBER>` code.

### 7. Bounds, privacy, and failure cleanup

At most one live association exists per accepted non-null request frame and
all associations are session-local. EOF, framing failure, output failure, or
executor termination MUST drop the registry without persistence. Cancellation
state, request IDs, source text, paths, compiler keys, Semantic IDs,
Definition IDs, Rust/debug values, timing, and addresses MUST NOT enter cached
compiler values or public responses except for the ordinary echoed JSON-RPC
response ID.

## Conformance plan

- Cover string and number IDs, independent IDs, reuse after completion,
  duplicate-live rejection, and exact string/number separation.
- Cover valid, unknown, duplicate, late, malformed, null-ID, and request-form
  cancellation while preserving notification response-freedom.
- Exercise cancellation before work, during bounded compiler/index loops, and
  at the final publication boundary for workspace symbols, rename, completion,
  completion resolve, and semantic tokens.
- Prove a cancelled request returns `-32800` and cannot mutate Workspace Edit,
  completion-resolve, workspace-index, semantic-token-history, diagnostic, or
  compiler partial-cache state.
- Repeat framed transcripts and cancellation storms without depending on
  timing; cover EOF, exit, malformed frames, and writer failures without leaked
  associations or non-protocol stdout.
- Run exact protocol fixtures plus locked offline workspace tests, strict
  Clippy, CI, governance, LSP, support, status, RC0, traceability, formatting,
  diff, and execution-plan checksum gates.

## Compatibility impact

- **LSP/protocol:** adds standard `$/cancelRequest`, RequestCancelled `-32800`,
  duplicate-live-ID rejection, and Preview discovery marker
  `ling.lsp.request-cancellation/0.1`. There is no predecessor.
- **Compiler/query:** adds typed cooperative cancellation to selected
  compiler-backed queries without changing successful query identities,
  checked facts, source spans, or deterministic cache values.
- **Diagnostics/schema/identity:** adds no Ling diagnostic, standalone JSON
  schema, Semantic ID, Definition ID, or canonical compiler byte change.
- **Language/runtime/data:** no Ling syntax or semantics, Typed Core
  evaluation, interpreter, runtime, bytecode, VM, ABI, package, filesystem,
  network, or Unicode 17.0.0 table change.
- **Migration:** clients that do not send cancellation are unchanged;
  incompatible cancellation behavior requires a new marker and migration
  evidence.

## Unresolved alternatives

Parallel request execution, general scheduler fairness and priorities,
deadlines, quotas, progress, server-initiated cancellation, async non-stdio
transports, Stable editor compatibility, and general Semantic Transaction
publication remain deferred to LSP-2503/LSP-2504 or later authority.
