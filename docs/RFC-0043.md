# RFC-0043: Snapshot-Bound LSP Completion Resolve Preview / 快照绑定的 LSP 补全解析 Preview

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-23
> 目标版本：v0.1 Preview
> 作者/Owner role：ide-protocol-design
> 相关缺口：GAP-LSP-TRANSACTION-PROTOCOL-001，GAP-SEMANTIC-PROTOCOL-LIFECYCLE-001，GAP-FORMATTER-AUTHOR-SOURCE-001，GAP-UNICODE-ALIAS-SYNTAX-001，GAP-AUTHOR-SOURCE-LOCALIZATION-001
> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC defines a capability-negotiated `completionItem/resolve` extension to
RFC-0042. It lazily presents checked signatures, Effect Rows, and module
Capabilities through opaque snapshot-bound handles while preserving the exact
Unicode insertion edit produced by completion. It does not invent Author Source
documentation, expose compiler identities, or authorize formatter rewrites.

本 RFC 为 RFC-0042 定义经能力协商的 `completionItem/resolve` 扩展。它通过绑定
快照的不透明句柄，延迟展示已检查签名、Effect Row 与模块 Capability，同时保持
completion 产生的 Unicode 插入编辑完全不变；它不虚构 Author Source 文档、不暴露
编译器 identity，也不授权 formatter 重写。

## Summary

`ling.lsp.completion/0.2` is an opt-in extension of
`ling.lsp.completion/0.1`. A capable client receives standard Completion Items
with opaque `data` and may send the exact item to `completionItem/resolve`.
Resolution succeeds only while the complete immutable request snapshot is
unchanged. The result preserves every insertion-critical field and may add
bounded deterministic `detail` and `documentation` derived solely from the
checked metadata authorized by DEC-0080.

## Status and scope

- Current lifecycle state: `Accepted`.
- Stable implementation basis: `yes` for this Preview protocol.
- In scope:
  - capability-negotiated standard `completionItem/resolve`;
  - exact RFC-0042 Completion Items augmented with opaque versioned `data`;
  - one complete immutable workspace or isolated-temporary snapshot;
  - checked user definitions and local/parameter bindings represented by
    DEC-0080 metadata, plus directly attached `///` Author Source documentation;
  - deterministic display-only signatures, Effect Rows, Capabilities,
    bilingual factual documentation, bounds, expiry, and stale rejection;
  - plaintext and safe Markdown `MarkupContent` selected from client
    capabilities; and
  - migration from the exact non-resolving RFC-0042 behavior.
- Out of scope:
  - constructing or serializing `DocumentationId`, localized documentation or
    source text, ordinary `//`/`/* */` comments, or detached `///` comments;
  - resolving modules, import aliases, fields, keywords, source-less builtins,
    Prelude entries, generated sources, or dependencies to fabricated facts;
  - changing `label`, `kind`, ranking, filtering, insertion text, replacement
    range, `textEdit`, or adding snippets/additional edits/commands;
  - formatter execution, source mutation, semantic transactions, persistent
    handles, cross-session caches, progress, asynchronous cancellation,
    redacted privileged capabilities, AI/remote content, or Stable lifecycle.
- Normative dependencies: RFC-0004, RFC-0005, RFC-0023, RFC-0029, RFC-0030,
  RFC-0037, RFC-0038, RFC-0039, RFC-0042, DEC-0002, DEC-0010, DEC-0012,
  DEC-0019, DEC-0023, DEC-0029, DEC-0071, DEC-0075, DEC-0079, and DEC-0080.

## Normative changes

### 1. Capability negotiation and discovery

The server enables resolve only when
`capabilities.textDocument.completion.completionItem.resolveSupport.properties`
is an array of strings containing both `detail` and `documentation`. Missing
completion, completion-item, or resolve-support objects select the exact
RFC-0042 fallback. A present malformed known object, non-string property, or
empty properties array makes `initialize` invalid under RFC-0004. Unknown
ordinary capability fields are ignored.

`completionItem.documentationFormat`, when present, MUST be a non-empty array
of strings. The server selects the first supported value, `plaintext` or
`markdown`; no supported value makes `initialize` invalid. When absent,
`plaintext` is selected.

Without negotiated resolve, initialize and completion remain byte-for-field
compatible with RFC-0042: `resolveProvider` is `false`, the exact
`ling.lsp.completion/0.1` discovery object is returned, Completion Items contain
no `data`, and resolve requests fail as unavailable.

With negotiated resolve, `completionProvider.resolveProvider` is `true` and
the Experimental discovery object is:

```json
"lingCompletion": {
  "contexts": ["expression", "member", "type", "pattern", "module", "keyword"],
  "maxItems": 256,
  "resolve": {
    "documentationFormat": "plaintext",
    "maxHandles": 1024,
    "properties": ["detail", "documentation"],
    "version": "ling.lsp.completion-resolve/0.1"
  },
  "source": "checked",
  "version": "ling.lsp.completion/0.2"
}
```

`documentationFormat` contains the negotiated value. No custom request or
dynamic registration is introduced.

### 2. Completion 0.2 items and opaque handles

RFC-0042 candidate derivation, validation, ranking, limits, freshness, and all
insertion-critical fields remain unchanged. Every emitted 0.2 item adds exactly
one `data` object:

```json
"data": {
  "handle": "ling.lsp.completion-resolve/0.1:blake3:<64 lowercase hex digits>",
  "version": "ling.lsp.completion-resolve/0.1"
}
```

The handle is a session-local opaque correlation value. First, the server makes
a domain-separated, length-delimited BLAKE3 digest of the complete Request
Snapshot: lifecycle, negotiated position encoding, workspace revision, every
URI-ordered document's URI/logical name/revision/origin/open/writable/temporary/
client-version/bytes, and every canonical project input's kind/revision/bytes.
The handle digest covers the protocol marker, that snapshot digest, request URI,
replacement byte span, exact request byte offset, final item ordinal, stable
candidate kind, and existing internal candidate identity. Only the final digest
is serialized. The server retains the
originating immutable Request Snapshot, exact emitted item, optional DEC-0080
identity, and negotiated documentation format. It MUST NOT serialize a URI,
path, source or module ID, resolver/Semantic identity, revision, type key, span,
Effect key, or Capability key in `data`.

Equal completion requests in one unchanged session produce equal handles and
responses. Handles have no meaning across sessions and are not cache keys,
Semantic IDs, security credentials, or compatibility identities. A digest
collision between unequal retained records fails the completion atomically.

At most 1,024 handles are retained. If one successful completion batch would
exceed the remaining capacity, all older batches expire before the new batch is
published. A batch itself is already bounded to 256 by RFC-0042. Failed or stale
completion requests publish no handles.

### 3. Resolve request validation and freshness

`completionItem/resolve` is request-only and is available only in Ready state
after successful resolve negotiation. Notifications perform no work. Params
MUST be one object containing the exact emitted `label`, `kind`, `sortText`,
`filterText`, `insertTextFormat`, `textEdit`, and `data`. Known lazy fields
`detail` and `documentation` MUST be absent. The `data` object MUST contain only
the exact version and a syntactically valid handle. Unknown ordinary top-level
fields are ignored and are not reflected.

The server looks up the handle and compares every required field with the
retained original before doing compiler work. A malformed item, malformed data,
unknown data field, invalid handle spelling, version mismatch, modified
insertion-critical field, or client-supplied lazy field is InvalidParams.
A well-formed but missing or expired handle is RequestFailed.

Resolution recaptures the complete request snapshot and requires exact equality
with the retained snapshot before and after rebuilding the checked workspace.
Any document, version, URI mapping, VFS revision, visible bytes, position
encoding, project input, lifecycle, or temporary-isolation difference makes the
handle stale and returns RequestFailed. Positions are not reprojected or
clamped. Processing is synchronous and bounded; this version makes no
asynchronous cancellation promise.

### 4. Checked metadata selection

The retained optional identity may select exactly one entry from
`ResolvedCompletionMetadataIndex` built from the same completely checked
snapshot. The selected entry MUST have the retained normalized name and existing
resolver identity. Missing, duplicate, mismatched, invalid-source, or unchecked
metadata fails atomically.

Only DEC-0080 user-definition and binding entries are presentable. After exact
identity selection, the server MAY read the same retained source snapshot's
compiler CST/Format IR solely to select attached `///` text under §6. A valid
item without such an identity—module, alias, field, keyword, source-less
builtin, Prelude, generated, or dependency-only candidate—resolves successfully
to the exact original item with no lazy fields. Absence is never filled with a
guessed signature, placeholder documentation, Semantic Graph inference,
unrelated source excerpt, filesystem lookup, remote request, or AI output.

### 5. Deterministic signature presentation

When checked `type_display` exists, `detail` uses this display-only grammar:

```text
<normalized-name>: <checked-type> [! {<Effect>, ...}] [requires {<Capability>, ...}]
```

Square brackets above denote optional presentation components and are not
emitted. Effect and Capability names are their existing canonical names in
canonical order. Empty rows/sets are omitted. A missing checked type omits all
lazy fields; it is not rendered as unknown. The presentation is not Ling source,
does not enter parsing, formatting, identity, or evaluation, and MUST NOT be
copied into `textEdit`.

`detail` is bounded to 4,096 UTF-8 bytes. It contains no path, URI, position,
revision, package source, internal ID, stability claim, or debug formatting.

### 6. Bilingual factual and Author Source documentation

For an entry with a checked type, `documentation` contains the full detail,
optional attached Author Source documentation, and these applicable checked
facts in this fixed order:

1. `种类 / kind`: `definition` or `binding`;
2. `效果 / effects`: canonical comma-separated non-empty Effect names; and
3. `能力 / capabilities`: canonical comma-separated non-empty Capability names.

The optional Author Source section is selected only after complete checking.
Using the compiler CST projected through the preservation-oriented Format IR,
the server finds the smallest enclosing Let, Type, Trait, Trait member,
Implementation, implementation member, field, or variant declaration that
contains the metadata span. It walks backward over whitespace and layout and
accepts only the contiguous `///` lines separated from each other and the
declaration by exactly one physical newline. A blank line, ordinary/block
comment, code token, or file boundary terminates the block. Each line removes
exactly `///` and at most one following ASCII space; remaining Unicode text and
line order are preserved and joined with LF. The server creates no
`DocumentationId` and does not associate comments with an unchecked identity.

Plaintext begins with `已检查的 Ling 符号 / checked Ling symbol`, followed by
detail, optional `文档 / documentation:` and normalized Author Source lines,
then fact lines. Markdown begins with one `ling` fenced block containing detail;
optional Author Source lines are emitted as blockquotes after escaping every
ASCII Markdown punctuation character; fact bullets use inline-code values.
Signature/fact Markdown fails safely if a rendered compiler value contains a
backtick. Raw HTML is never emitted. Documentation is bounded to 16,384 UTF-8
bytes.

The protocol does not infer prose, translate documentation or names, claim
localization equivalence, read detached comments, construct a persistent
documentation identity, or present dependency/generated/builtin documentation.
Changing attachment, normalization, provenance, locale, or `DocumentationId`
behavior requires a new protocol version.

### 7. Insertion, Unicode, and formatter preservation

Resolve MUST return the exact retained RFC-0042 `label`, `filterText`, `kind`,
`sortText`, `insertTextFormat`, and `textEdit`. It MUST NOT return `insertText`,
`insertTextMode`, `additionalTextEdits`, `commitCharacters`, `command`, or a
different range/newText. Therefore RFC-0042's checked Unicode 17.0.0 spelling,
original UTF-8 span, negotiated position projection, and replacement simulation
remain the sole insertion authority.

No formatter is run and no source/comment bytes are rewritten during resolve.
Formatter preservation is satisfied by leaving the already validated exact
edit unchanged. Alias syntax, localized keywords, confusable rewriting, NFC
migration, snippets, import edits, and broader Author Source formatting remain
outside this version.

### 8. Result, failures, and compatibility

Success returns one standard Completion Item. It contains the exact stored 0.2
item and, when checked metadata exists, exactly `detail` and `documentation`.
`documentation` is a standard MarkupContent object with exact negotiated `kind`
and rendered `value`. Resolution does not return null.

Malformed or modified params use InvalidParams `-32602` with
`补全项解析参数无效 / invalid completion-item resolve parameters`. Unnegotiated,
missing, expired, stale, compiler, metadata, collision, bound, unsafe-rendering,
or response-size failures use RequestFailed `-32803` with
`补全项解析不可用 / completion-item resolve unavailable`. No compiler diagnostic
is allocated and no partial metadata is returned.

Any incompatible negotiation, item/data, handle, expiry, snapshot, metadata,
signature, documentation, insertion-preservation, failure, bound, or result
change requires a new marker and migration evidence.

## Compatibility impact

- **Protocol:** adds negotiated Preview `ling.lsp.completion/0.2` and
  `ling.lsp.completion-resolve/0.1`; exact RFC-0042 0.1 remains the fallback.
- **Compiler query:** consumes DEC-0080 checked metadata without changing its
  identity or checked facts; adds only bounded in-memory LSP handle state.
- **Identity/schema:** handles are opaque session correlation values, not
  Semantic/resolver IDs or public schemas; no Semantic ID change.
- **Diagnostics/language/runtime:** no diagnostic allocation, Ling syntax or
  semantics, Typed Core evaluation, interpreter, runtime, bytecode, VM, ABI,
  package, filesystem/network, or Unicode 17.0.0 table change.

## Unresolved alternatives

Documentation identities, localization, detached/source excerpts, generated and
dependency provenance, builtin documentation, field signatures, snippets,
additional edits, auto-imports, formatter integration, persistent/cross-session
handles, asynchronous cancellation, dynamic registration, AI assistance, and
Stable lifecycle remain future work requiring separate Accepted authority.
