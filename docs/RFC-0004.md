# RFC-0004: LSP lifecycle and transport / LSP 生命周期与传输

> 状态：Accepted
> 类型：Standards Track<br>
> 创建日期：2026-08-22<br>
> 目标版本：v0.1 Preview<br>
> 作者/Owner role：ide-protocol-design<br>
> 相关缺口：GAP-SEMANTIC-PROTOCOL-LIFECYCLE-001 | GAP-LSP-TRANSACTION-PROTOCOL-001<br>
> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC is an Accepted, bounded Preview authority for the Ling language-server
process lifecycle. It does not turn the broader Semantic Graph, Workspace Edit,
or Semantic Transaction proposals into accepted protocols.

## Summary

This RFC defines the first executable LSP boundary for Ling: `ling lsp --stdio`
speaks a single-request JSON-RPC 2.0 stream using `Content-Length` framing. The
server has an explicit lifecycle (`Uninitialized`, `AwaitingInitialized`,
`Ready`, `ShutdownRequested`, and `Exited`), negotiates the position encoding
already authorized by DEC-0029, validates bounded workspace-folder metadata,
and provides deterministic initialization and shutdown behavior.

The protocol is intentionally Preview and current-writer-only. It provides no
document synchronization, diagnostics, semantic tokens, Workspace Edits,
Semantic Transactions, cancellation, compiler snapshots, or filesystem
workspace resolver. Those surfaces remain governed by their own gaps and later
accepted specifications.

## Normative changes

### 1. Command and channels

The Preview server is launched only as:

```text
ling lsp --stdio
```

The command accepts no source path, `--format` option, or other option. It does
not search for a project and does not read or write files. Standard input and
standard output carry protocol bytes only. Human diagnostics, transport
failures, and implementation logs MUST use standard error; a server MUST NOT
write an unframed byte to standard output.

The protocol marker is the ASCII string `ling.lsp.lifecycle/0.1`. It identifies
the lifecycle contract, not a claim that the full Language Server Protocol is
implemented or Stable.

### 2. Transport framing

Each message is one UTF-8 JSON-RPC 2.0 object preceded by an ASCII header block:

```text
Content-Length: <decimal byte length>\r\n
\r\n
<exactly that many UTF-8 bytes>
```

Header names are ASCII case-insensitive. `Content-Length` MUST occur exactly
once, contain one or more decimal digits with no sign or surrounding non-ASCII
bytes, and be no larger than 1,048,576 bytes. Unknown ASCII headers MAY be
ignored. Header lines and the complete header block MUST use CRLF; a bare LF,
duplicate `Content-Length`, missing `Content-Length`, invalid ASCII, or a body
shorter than the declared length is a transport error. The header block is
limited to 8,192 bytes. A transport error emits no guessed response and ends
the server stream.

The server accepts one JSON-RPC object at a time. JSON arrays/batches are an
invalid request. A body that is not valid UTF-8 JSON produces a JSON-RPC parse
error with `id: null`, after which the server MAY continue reading the next
frame. A response uses the same framing and is flushed before the next input is
read.

Request IDs are JSON strings, numbers, or null and are echoed without changing
their value. An absent `id` denotes a notification and MUST NOT receive a
response. Boolean, array, or object IDs are invalid requests. The server does
not expose JSON-RPC batch or cancellation behavior.

### 3. Lifecycle state machine

The initial state is `Uninitialized`. The only request permitted in that state
is `initialize`. A successful `initialize` request enters
`AwaitingInitialized`; the response MUST be sent before the client may send
`initialized`. The `initialized` notification enters `Ready`.

Only a `Ready` server accepts `shutdown`. A successful `shutdown` request
returns JSON `null` and enters `ShutdownRequested`. The `exit` notification
then enters `Exited` and terminates with process status 0. An `exit`
notification received before `shutdown` still enters `Exited` but terminates
with process status 1. The server treats end-of-input without an `exit`
notification as a clean transport end for the library API; the CLI returns 0
after flushing already-written responses.

Requests made before `initialize` receive error `-32002` (server not
initialized). Requests made after `shutdown` receive error `-32003` (server is
shutting down), except that `exit` is a notification-only operation. Duplicate
or state-incompatible lifecycle requests receive `-32600` (invalid request).
Unknown methods in `Ready` receive `-32601` (method not found). Notifications
never receive an error response.

The following methods are the complete v0.1 method set:

| Method | Kind | Allowed state | Result/effect |
| --- | --- | --- | --- |
| `initialize` | request | `Uninitialized` | returns server capabilities; enters `AwaitingInitialized` |
| `initialized` | notification | `AwaitingInitialized` | enters `Ready` |
| `shutdown` | request | `Ready` | returns `null`; enters `ShutdownRequested` |
| `exit` | notification | any non-`Exited` state | enters `Exited`; status 0 only after shutdown |

`initialized` and `exit` with an ID are invalid requests and do not change
state. A notification with an unknown method is ignored. A request with an
unknown method follows the error rules above.

### 4. Initialization parameters and result

`initialize.params` MUST be an object. The optional
`capabilities.general.positionEncodings` field, when present, MUST be an array
of strings. The server selects the first supported label in client order from
`utf-8`, `utf-16`, and `utf-32`; unknown labels are ignored. An absent or
unsupported-only list selects `utf-16`, exactly as DEC-0029 requires.

The optional `workspaceFolders` field is either null or an array of at most 32
objects. Each object MUST contain a nonempty `uri` string of at most 4,096
UTF-8 bytes and a nonempty `name` string of at most 256 UTF-8 bytes. Neither
string may contain NUL or a Unicode control character. URI strings are retained
as opaque protocol values, compared byte-for-byte, and MUST be unique within
the request. The server does not convert them to host paths or touch the
filesystem.

On success the result contains exactly the implemented capability projection:

```json
{
  "capabilities": {
    "positionEncoding": "utf-16",
    "workspace": {
      "workspaceFolders": {
        "changeNotifications": false,
        "supported": true
      }
    }
  },
  "serverInfo": {
    "name": "ling",
    "version": "0.0.1-dev"
  }
}
```

The selected encoding replaces the example value. The server version is the
workspace package version. No unimplemented capability is advertised. Invalid
parameter types, limits, duplicate URIs, or invalid strings return `-32602`
without changing state.

### 5. Errors and deterministic output

The server uses the JSON-RPC codes `-32700`, `-32600`, `-32601`, and `-32602`
plus the Ling Preview lifecycle codes `-32002` and `-32003`. Error messages are
stable bilingual strings; implementation-specific paths, Rust types, pointer
values, allocation order, and debug output MUST NOT appear in responses.

Responses are serialized as compact UTF-8 JSON with deterministic object-key
ordering. The server retains no client-controlled data beyond the validated
position encoding and workspace-folder values in the current process. It does
not publish diagnostics or Semantic IDs.

### 6. Explicit non-claims

This RFC does not accept or implement the Semantic Graph/Transaction lifecycle
gap, the LSP position/version/edit transaction gap, or any document-analysis
feature. DEC-0029 remains the sole authority for source byte/position
projection. A later RFC MUST define snapshot identity, document versions,
stale-result and failure responses, field stability, migration, cancellation,
and Workspace Edit/Semantic Transaction behavior before those features are
implemented or advertised.

## Conformance plan

- Add executable lifecycle transcripts for UTF-8, UTF-16 fallback, UTF-32,
  Unicode workspace names, duplicate/oversized/invalid workspace folders,
  pre-initialize requests, duplicate initialization, shutdown ordering, and
  early exit.
- Assert exact JSON-RPC framing, response IDs, deterministic bytes, bilingual
  error messages, CRLF-only headers, 1 MiB body rejection, malformed JSON
  recovery, and no stdout contamination.
- Add negative transport fixtures for missing/duplicate/invalid
  `Content-Length`, bare-LF headers, truncated bodies, invalid UTF-8, batches,
  invalid IDs, and post-shutdown requests.
- Run the CLI subprocess fixture with `ling lsp --stdio` and verify that all
  protocol output is framed stdout and all human text is stderr.
- Keep transaction, document-sync, diagnostics, cancellation, and Semantic
  Graph migration fixtures deferred until their governing authority is
  accepted.

## Compatibility impact

- **Source and language:** no `.ling` syntax, type, effect, runtime, Unicode,
  or source-span behavior changes. The exact `ling` executable and `.ling`
  extension remain unchanged.
- **CLI:** adds the Preview `ling lsp --stdio` command. Existing commands,
  options, and exit meanings are unchanged. The command is not a 1.0 Stable
  editor-support promise.
- **Protocol:** adds the current-writer-only `PROTO-LSP-LIFECYCLE` record with
  version `ling.lsp.lifecycle/0.1`; incompatible lifecycle or transport changes
  require a new version and migration evidence.
- **Diagnostics:** no `L-*` diagnostic allocation is added. JSON-RPC errors are
  transport-level protocol errors, not Ling compiler diagnostics.
- **Semantic IDs, schemas, bytecode, ABI, and package identity:** none.
- **Determinism and Unicode:** frame limits, state transitions, response fields,
  workspace ordering, and position negotiation are deterministic. Unicode
  behavior remains pinned to Unicode 17.0.0; source bytes remain authoritative.

## Unresolved alternatives

- Workspace URI-to-path resolution, root URI precedence, multi-root change
  notifications, document synchronization, snapshots, cancellation, and
  request quotas remain unresolved and are intentionally deferred.
- A future protocol may define Workspace Edits or Semantic Transactions, but it
  MUST NOT silently reuse `ling.lsp.lifecycle/0.1` for incompatible fields.
- A separate stable LSP/editor RFC may replace the Preview capability surface;
  this RFC does not claim N-1 reader compatibility.
