# RFC-0033: LSP pull diagnostics Preview / LSP 拉取诊断 Preview

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-23
> 目标版本：v0.1 Preview
> 作者/Owner role：ide-protocol-design
> 相关缺口：GAP-LSP-TRANSACTION-PROTOCOL-001; GAP-SEMANTIC-PROTOCOL-LIFECYCLE-001
> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC defines the bounded LSP 3.17 document and workspace diagnostic pull
surface for Ling. It reuses RFC-0032's immutable compiler analysis and exact
diagnostic values so push and pull cannot create different current diagnostic
sets.

## Summary

`ling.lsp.pull-diagnostics/0.1` is advertised only when the initializing client
declares `textDocument.diagnostic`. It implements `textDocument/diagnostic` and
`workspace/diagnostic` with deterministic stateless result IDs, full and
unchanged reports, exact current document versions, removed-URI clearance, and
bounded failure-atomic responses. RFC-0032 push diagnostics remain enabled and
neither channel changes compiler diagnostic meaning.

## Status and scope

- Current lifecycle state: `Accepted`
- Stable implementation basis: `yes` for this Preview protocol
- In scope:
  - conditional static provider capability and exact protocol identifier;
  - current tracked-document and complete workspace diagnostic requests;
  - deterministic full/unchanged result identity;
  - workspace open/closed/removed URI version and clearance behavior;
  - push/pull diagnostic-value parity and bounded final responses.
- Out of scope:
  - dynamic registration, work-done progress, partial-result streaming,
    server-observable request cancellation, `workspace/diagnostic/refresh`,
    related-document report maps, notebook documents, configuration, result-ID
    persistence, background workers, root-cause grouping, deduplication, caps,
    suppression, fixes, Workspace Edits, Semantic Transactions, and Stable

- Normative dependencies:
  - the LSP 3.17 pull-diagnostics request/report structures;
  - RFC-0004 lifecycle/transport and RFC-0023/RFC-0029 overlays;
  - RFC-0030 workspace snapshots and RFC-0031/RFC-0032 diagnostic analysis;
  - DEC-0019/DEC-0071 immutable observation and DEC-0034/DEC-0072 ordering and

## Normative changes

### 1. Negotiation and method availability

Initialize MUST treat `capabilities.textDocument.diagnostic` as pull support
only when it is a JSON object. An absent member means unsupported; a present
non-object member makes initialize params invalid. Support is immutable for the
session.

For a supporting client, initialize MUST advertise exactly:

```json
"diagnosticProvider": {
  "identifier": "ling.lsp.pull-diagnostics/0.1",
  "interFileDependencies": true,
  "workDoneProgress": false,
  "workspaceDiagnostics": true
}
```

For a non-supporting client the member MUST be absent and both pull method
requests MUST return JSON-RPC MethodNotFound. Notifications using either method
MUST create no work and no response. Push diagnostics remain independently
advertised and active for every client.

### 2. Request subset and validation

`textDocument/diagnostic` accepts an object with required
`textDocument.uri`, optional `identifier`, optional `previousResultId`, and
ordinary forward-compatible fields. The URI MUST be an exact currently tracked
Ling document identity. `identifier`, when present, MUST equal
`ling.lsp.pull-diagnostics/0.1`. `previousResultId` MUST be a string.

`workspace/diagnostic` accepts an object with required `previousResultIds`
array, optional `identifier`, and ordinary forward-compatible fields. Each
entry MUST have exact string `uri` and `value` members; URIs MUST be valid Ling
document identities and unique. At most 1024 entries are accepted. The same
identifier rule applies.

Known members with wrong types, invalid or duplicate identities, an unknown
current document request, over-limit arrays, or an unsupported identifier MUST
return InvalidParams without analysis or state mutation. Optional work-done and
partial-result tokens and unknown ordinary fields are accepted but ignored;
this provider advertises no progress and emits no `$/progress` notification.

### 3. Current analysis and parity

Each accepted request MUST capture and compile one owned RFC-0032 diagnostic
ticket using only locked-offline in-process compiler libraries. Completion MUST
compare the complete ticket identity with current state before constructing a
response. A stale or internally failed result MUST NOT change pending push work,
the push ledger, document state, or any result cache.

Pull diagnostic arrays MUST be byte-for-byte the same RFC-0032 adapter values,
in the same order, that a current push analysis groups for that URI. Pull does
not consume, clear, or populate the push ledger. Temporary documents remain
syntax-only. No filesystem, environment, cache-root, registry, network, shell,
clock, or host-path input is permitted.

### 4. Stateless result IDs

Every URI report has this exact result-ID format:

```text
ling.lsp.pull-result/0.1:blake3:<64 lowercase hexadecimal digits>
```

The BLAKE3 input is a domain-separated length-prefixed byte sequence containing
`ling.lsp.pull-result-id/0.1`, `ling.lsp.diagnostic/0.2`, the exact URI UTF-8
bytes, and the compact JSON bytes of that URI's ordered diagnostic array. Each
length is an unsigned 64-bit big-endian integer. No document version, session
revision, path, timestamp, process identity, or map iteration enters the ID.

The algorithm is stateless: the server stores no client result-ID cache. Equal
current diagnostic arrays for the same URI produce the same ID across document
versions and repeated processes; another URI or diagnostic byte sequence
produces an independently derived ID. Result IDs are Preview protocol values,
not Semantic IDs and not a Stable collision-resistance promise.

### 5. Document report

The server computes the current result ID and diagnostics for the requested
URI. If `previousResultId` exactly equals the current ID, the result MUST be:

```json
{"kind":"unchanged","resultId":"..."}
```

Otherwise it MUST be:

```json
{"items":[],"kind":"full","resultId":"..."}
```

`relatedDocuments` MUST be omitted. An empty diagnostic array is a successful
full result, not `null` and not absence.

### 6. Workspace report and removal clearance

The workspace candidate URI set is the union of every current ticket document
and every valid URI in `previousResultIds`. It is emitted once in Unicode
scalar-value URI order. Current URIs use their exact grouped diagnostic array;
a previous-only removed URI uses an empty array.

Each item contains `uri`, current `version` for an open document or `null` for
a closed/disk/removed document, `kind`, and `resultId`. A matching prior ID
produces an unchanged item without `items`; otherwise a full item includes the
complete `items` array. Thus removed sources deterministically publish one full
empty replacement when their earlier non-empty ID is supplied. Repeated empty
IDs may be unchanged. The final response is exactly `{"items":[...]}`.

### 7. Bounds and failures

All JSON responses MUST be fully encoded before return. A success body larger
than the RFC-0004 transport maximum MUST instead return LSP RequestFailed
`-32803` with a fixed bilingual message. Invalid params use `-32602`, an
unnegotiated method uses `-32601`, and an internal analysis/encoding invariant
uses `-32603`. Errors contain no host path or debug rendering and change no
server state.

The current server processes one complete message at a time. It therefore
cannot observe a later `$/cancelRequest` until the synchronous pull has already
responded. Cancellation, progress, and partial results are not advertised and
no cancellation error or retry field is emitted in 0.1.

## Conformance plan

- Verify capability presence/absence and exact fields, negotiated method
  availability, request/notification distinction, identifiers, known-field
  types, unknown-field tolerance, duplicate/invalid URI rejection, and bounds.
- Cover document full/empty/unchanged results, version-only and diagnostic
  changes, UTF-8/16/32 adapter values, temporary syntax isolation, and exact
  push/pull array parity.
- Cover URI-sorted workspace full/unchanged mixtures, open integer versions,
  closed `null` versions, previous-only removed clearance, empty workspaces,
  reordered previous IDs, and repeated-process result-ID identity.
- Verify result-ID domain bytes and format, cross-URI separation, no server
  cache, no ledger/pending mutation, stale/internal/oversized failure atomicity,
  and response-before-any-pending-push notification framing.
- Run locked offline workspace tests, strict Clippy, CI, governance, LSP,
  support, status, RC0, traceability, formatting, and deterministic-diff gates.

## Compatibility impact

- **Protocol:** adds capability-gated Preview
  `ling.lsp.pull-diagnostics/0.1`; push and adapter versions are unchanged.
- **Migration:** no predecessor exists. Incompatible request, report, result-ID,
  provider, bound, or error behavior requires a new marker and migration
  evidence. Clients without pull support observe no new provider or method.
- **Diagnostics:** no code, severity, message, Facts, repair, Semantic ID, or
  `ling.diagnostic/0.1`/adapter value change.
- **Language/runtime/data:** no Ling syntax, semantics, Typed Core,
  interpreter, runtime, bytecode, VM, ABI, filesystem, cache, or Unicode
  17.0.0 change.

## Unresolved alternatives

Result-ID persistence was rejected because deterministic IDs need no mutable
cache. Related-document maps and partial streaming were rejected for 0.1
because workspace reports already expose the complete bounded URI set and the
sequential transport cannot interleave progress safely.

Dynamic registration, server-observable cancellation, progress, partial
results, refresh requests, notebook diagnostics, root-cause grouping,
deduplication, caps, suppression, repair application, Workspace Edits, Semantic
Transactions, general scheduling/fairness, and Stable lifecycle remain future
work.
