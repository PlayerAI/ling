> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC defines Ling's bounded `textDocument/rename` behavior. It closes
IDE-2306 with checked identity-based edits over the current immutable source
snapshot. It does not define a general Semantic Transaction, localized Author
Source equivalence, generated-source mutation, or Stable edit protocol.

本 RFC 定义 Ling 有界的 `textDocument/rename` 行为。它通过当前不可变源码快照上的
已检查、基于身份的编辑关闭 IDE-2306；它不定义通用 Semantic Transaction、
本地化 Author Source 等价、生成源码修改或 Stable 编辑协议。

## Summary

`ling.lsp.rename/0.1` selects one checked definition, binding, or resolved
import alias, validates one exact NFC Unicode 17.0.0 new name, derives every
owned declaration/reference occurrence, simulates all replacements in a fresh
compiler, and returns a deterministic versioned `documentChanges` Workspace
Edit only when the client promises transactional failure handling.

## Normative changes

### 1. Capability validation and discovery

Initialize recognizes optional `capabilities.workspace.workspaceEdit`. When
present it MUST be an object. Optional `documentChanges` MUST be a boolean and
optional `failureHandling` MUST be one of `abort`, `transactional`,
`textOnlyTransactional`, or `undo`. Unknown ordinary members are ignored;
malformed known members reject initialize without state mutation.

Rename is transaction-capable only when `documentChanges` is `true` and
`failureHandling` is exactly `transactional`. The negotiation result is fixed
for the session. RFC-0040 prepare-rename remains available independently.

Every successful initialize continues to advertise the RFC-0040 standard
`renameProvider` and additionally advertises:

```json
"lingRename": {
  "newName": "unicode17-xid-nfc-allowed-non-suspicious",
  "result": "versionedDocumentChanges",
  "transactional": true,
  "version": "ling.lsp.rename/0.1"
}
```

The object adds no custom request. A client that did not negotiate the exact
transaction capability receives RequestFailed for `textDocument/rename`; the
server never falls back to an unversioned `changes` map.

### 2. Request and immutable snapshot

`textDocument/rename` accepts an object with required string
`textDocument.uri`, required unsigned-u32 `position.line` and `character`, and
required string `newName`. Unknown ordinary fields are ignored. Malformed
known fields, unknown documents, or positions that cannot map exactly through
the negotiated encoding return InvalidParams `-32602`; positions are never
clamped. Notifications perform no work.

The server MUST be Ready and capture one complete immutable path-free snapshot.
A non-temporary request checks all non-temporary visible sources. A temporary
request checks only the exact temporary source plus project inputs. No server
document, VFS revision, disk state, or client buffer is mutated. Before every
successful response, including `null`, the complete snapshot MUST be
recaptured and compared; a difference fails atomically.

### 3. Checked target and complete occurrences

Selection uses RFC-0040's exact original-byte selector and canonical
smallest-containing-span rule. A definition or binding target owns its one
source-backed declaration plus every resolver expression reference in the
checked RFC-0039 grouping. A resolved import-alias target owns exactly its
declaration and every checked qualified-use root for that same importer module
and resolved target module. Alias collection is structural HIR/resolver work;
spelling search is forbidden.

Every owned occurrence MUST have a valid non-empty original UTF-8 identifier
span, normalize to the selected target's existing NFC name, be non-overlapping,
and reside in a uniquely mapped writable document. Source-less, builtin,
Prelude, dependency/read-only, unresolved, generated/virtual, incomplete, or
oversized targets return `null`. A target is never inferred from spelling,
types, coherence candidates, Semantic Graph data, host paths, or debug output.

### 4. New-name policy

`newName` MUST:

1. pass the authoritative Unicode 17.0.0 XID and forbidden-code-point rules;
2. already equal its NFC normalized form;
3. have Identifier_Status `Allowed`; and
4. not have the existing suspicious mixed-script observation.

The edited snapshot MUST also pass ordinary lexical keyword handling and the
resolver's normalized-name and confusable-skeleton collision checks. Therefore
keywords, Restricted identifiers, decomposed spellings, suspicious mixed
scripts, duplicate names, confusable collisions, shadowing changes,
ambiguities, visibility failures, and Trait/coherence failures are rejected
without output. The protocol exposes no Unicode security facts.

An exact byte-for-byte no-op new name returns `null`. An NFC new name may
replace older NFC-equivalent non-canonical source spellings.

### 5. Simulation, identity, and behavior condition

The server applies all candidate replacements only to owned copies of the
captured bytes, in descending original-byte order per document. It then builds
a fresh compiler with the same project inputs and edited visible sources and
MUST complete resolution, type checking, and Effect checking.

The simulated checked target selected at every translated occurrence MUST have
exactly the predicted source/span/relation set and target kind. Bindings MUST
retain the same `(ModuleId, BindingId)`; import aliases MUST retain the same
resolved target module. A definition rename to a different NFC name MUST
produce a different DefinitionId as required by DEC-0012, while all edited
occurrences resolve to that one new DefinitionId. Any missing, additional,
retargeted, overlapping, or multiply selected occurrence fails atomically.

This is the version 0.1 identity/behavior-preservation condition: the complete
edited workspace remains checked, the selected binding/import identity is
preserved where applicable, definition migration is explicit, and the exact
reference relation topology is unchanged. It is not a claim of general
program equivalence or stable Semantic ID migration.

### 6. Deterministic versioned Workspace Edit

Success returns exactly a standard Workspace Edit with `documentChanges`.
Documents are ordered by canonical URI. Each document contains one
`TextDocumentEdit`; open documents carry their captured integer client
version, and closed documents carry `null`. Edits are ordered by ascending
original range, never overlap, and contain only `range` plus exact `newText`.
No `changes`, resource operation, annotation, resolver/Semantic identity,
revision, logical path, package, provenance, or custom field is emitted.

The existing 16,384 target-location bound and RFC-0004 1 MiB response bound
apply before publication. Standard Workspace Edit describes proposed client
work; transactional application and rollback are the negotiated client's
responsibility. Ling guarantees atomic analysis and all-or-nothing response
construction, not mutation outside the server process.

### 7. Failures and compatibility

Invalid request shape uses `重命名参数无效 / invalid rename parameters` with
InvalidParams `-32602`. Missing transactional capability, invalid new name,
checked-analysis failure, collision/coherence failure, invalid occurrence or
projection, simulation mismatch, stale completion, bound failure, or oversized
response uses `重命名不可用 / rename unavailable` with RequestFailed `-32803`.
Ordinary ineligible selections and exact no-ops return `null`. No compiler
diagnostic is allocated.

Any incompatible capability, target, occurrence, name, simulation, identity,
ordering, version, result, null, bound, snapshot, or failure change requires a
new protocol marker and migration evidence.

## Compatibility impact

- **Protocol:** adds Preview `ling.lsp.rename/0.1`; no predecessor.
- **Compiler query:** adds a bounded immutable checked import-alias occurrence
  index and exposes a borrowed checked target group for simulation; neither is
  persistent or a public language feature.
- **Identity:** definition renames explicitly change DefinitionId; no Semantic
  ID schema or serialized identity migration is introduced.
- **Diagnostics/language/runtime:** no diagnostic allocation, Ling
  syntax/semantics, Typed Core evaluation, interpreter, runtime, bytecode, VM,
  ABI, package, filesystem/network, or Unicode 17.0.0 table change.

## Unresolved alternatives

Unversioned `changes` fallback was rejected because it cannot satisfy the
stale-open-document requirement. `textOnlyTransactional` was rejected because
version 0.1 requires one unambiguous whole-edit failure mode. Server-side edit
application was rejected because standard rename returns proposed edits. A
general Semantic Transaction, localized source equivalence, generated files,
module/file renames, type-only identities, cancellation, change annotations,
and Stable lifecycle remain later work.
