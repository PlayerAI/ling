# RFC-0025: Locked project command and artifact protocol / 锁定工程命令与产物协议

> 状态：Accepted
> 类型：Standards Track<br>

> 目标版本：v0.1 Preview<br>
> 作者/Owner role：package-design<br>

> 生命周期记录：`docs/governance/lifecycle.toml`

## Summary

This RFC completes the PRJ-1107 project CLI contract without changing the
existing file-oriented commands or RFC-0024 graph-only command. Supplying an
explicit `--manifest-path ling.toml` selects one RFC-0002 project for semantic
`check`, `run`, `test`, or `build`. Every project operation is locked and
offline, consumes the package-aware checked snapshot, and exposes one shared
Experimental result protocol.

本 RFC 完成 PRJ-1107 的工程 CLI 合约，同时保持现有单文件命令和 RFC-0024
图检查命令不变。显式提供 `--manifest-path ling.toml` 后，`check`、`run`、
`test`、`build` 将选择一个 RFC-0002 工程。所有工程操作均为锁定、离线操作，
只消费包感知的 checked snapshot，并使用统一的 Experimental 结果协议。

Because v0.1 has no accepted test-declaration syntax, project `test` is
deliberately a single isolated entry smoke test. Project `build` emits a
canonical checked semantic artifact for the fixed `explore` profile and
`semantic` target; it does not claim native executable or VM bytecode output.

## Normative changes

### 1. Command forms and mode selection

The complete project command forms are:

```text
ling check --manifest-path PATH --locked --offline [--format human|json]
ling run   --manifest-path PATH --locked --offline [--format human|json]
ling test  --manifest-path PATH --locked --offline [--format human|json]
ling build --manifest-path PATH --locked --offline
           --profile explore --target semantic --output PATH
           [--format human|json]
```

For `check`, `run`, and `test`, a positional file or directory operand selects
the previously accepted file mode. `--manifest-path` selects project mode and
MUST be mutually exclusive with positional input. `build` is project-only and
MUST reject a positional input.

Each listed project option MUST appear exactly once. `--profile`, `--target`,
and `--output` are valid only for `build`. Unknown commands, options, values,
duplicate options, missing values, or mixed file/project selection MUST fail
as invalid usage with exit code `2`. The stale executable name `zero` and the
stale extension `.zero` have no meaning.

RFC-0024 `ling project check --manifest-path PATH --locked` remains a distinct
graph-only command and retains `ling.project.check/0.1`; it MUST NOT silently
switch to semantic project mode.

### 2. Workspace selection and project loading

`PATH` MUST name a readable file whose final component is exactly `ling.toml`.
Its containing directory is the sole selected project root. No command may
search a parent, child, current directory, environment variable, user setting,
cache, registry, network location, or another manifest.

Manifest version 1 selects exactly one root package and its recursively
vendored local dependencies. The root package is the only runnable, testable,
or build-selected package. Dependencies participate in checking and linking
but are not independently selectable workspace members. `--package`,
`--workspace`, and equivalent member selectors are unsupported and MUST be
rejected. This is the complete v0.1 workspace-selection rule; multi-member
workspaces require a later manifest version and Accepted RFC.

Every project command MUST use the existing RFC-0002 manifest reader,
`load_locked_project`, and package graph. It MUST NOT duplicate dependency or
module resolution. `--locked` requires the existing canonical `ling.lock/1`
to match the entire graph and MUST NOT rewrite it. `--offline` is an explicit
forward-compatibility promise: no registry, Git, URL, DNS, network, shell, or
environment lookup is permitted. Neither option creates a second mode.

### 3. Checked project boundary

After graph validation, every project operation MUST obtain the package-aware
checked snapshot through `CompilerDb::project_semantic_snapshot`. Evaluation
and artifact production MUST consume this checked Typed Core snapshot and
MUST NOT parse, resolve, type-check, infer Effects, or interpret unchecked AST
through an alternate pipeline.

The semantic pipeline covers every package and discovered module in the locked
graph. Public source diagnostics retain the existing bilingual registered
codes and original UTF-8 byte spans with path-free logical source names of the
form `package:<package>/<logical-path>`. Independent diagnostics are emitted in
deterministic checked-pipeline order. Warnings do not change success status.

### 4. Project check

Project-mode `ling check` MUST complete graph validation and the full parse,
resolution, type, Effect, and package-aware Semantic Graph pipeline. It MUST
not locate or execute `main` and MUST write no source, lock, cache, or artifact.
Success establishes that the complete locked project has a checked
`ling.semantic/0.2` snapshot.

### 5. Project run

Project-mode `ling run` MUST first complete project checking, then locate the
entry module declared by the root manifest and validate `main` using the
existing Accepted entry contract. It executes exactly that checked definition
with the existing deterministic interpreter and `Console.Write` host
capability. It MUST NOT execute a dependency entry or unchecked source.

Human mode writes the program's captured console bytes to stdout exactly.
JSON mode captures those bytes and places them in the success or failure
report; it MUST NOT interleave program text with the JSON document. A runtime
Fault retains exit code `4`; invalid entry shape is a compile/check failure
with exit code `1`.

### 6. Project test

Until Ling has Accepted source-level test declarations, project-mode
`ling test` is one deterministic entry smoke test named
`<root-package>::<entry-module>`. It performs a fresh checked project load,
validates `main`, executes it once with an isolated in-memory console, and
records the captured bytes. It MUST NOT enumerate arbitrary `.ling` files as
standalone programs, discover hidden test conventions, run dependencies, or
claim per-definition unit-test coverage.

Successful entry execution produces totals `total=1`, `passed=1`, `failed=0`.
A compile/entry failure produces exit `1`; a runtime Fault produces exit `4`.
The standalone file/directory `ling test PATH` contract and `ling.test/0.1`
remain unchanged.

### 7. Project build and canonical artifact

The only accepted v0.1 build inputs are profile `explore` and target
`semantic`; all other values MUST be rejected as invalid usage. `--output`
names one regular output file. Its parent directory MUST already exist. The
command MUST refuse to follow or replace an existing file, directory, or
symlink and MUST publish no partial artifact on failure.

After successful project checking, `build` emits canonical UTF-8 JSON with one
trailing LF and this exact top-level key order:

```json
{"graph":"sha256:...","profile":"explore","program":"experimental:blake3:...","protocol":"ling.project.artifact/0.1","semantic":{},"target":"semantic"}
```

`semantic` is the exact decoded `ling.semantic/0.2` object for the checked
project, not an escaped JSON string. No host path, timestamp, filesystem
metadata, environment value, allocation identity, unordered map iteration, or
debug output may enter the bytes. `graph` is the RFC-0002 package graph ID and
`program` is the package-aware ProgramId.

The artifact identity is `sha256:` plus lowercase hexadecimal SHA-256 of the
complete canonical artifact bytes. Because those bytes include `profile` and
`target`, the identity satisfies RFC-0002 §5. The artifact is checked semantic
input for tooling; it is not executable bytecode, a native binary, a cache
key authorizing dependency substitution, or a Stable publication format.

### 8. Shared result protocol

JSON command results use `ling.project.command/0.1`. Each success report is
one UTF-8 JSON object plus LF on stdout with required fields:

```json
{"protocol":"ling.project.command/0.1","operation":"check|run|test|build","status":"ok","package":{"name":"...","version":"..."},"entry":"...","graph":"...","program":"..."}
```

Operation-specific fields are:

- `run`: `stdout` as a JSON string;
- `test`: `tests` containing exactly one `{name,status,stdout}` object and
  `counts` containing integer `total`, `passed`, and `failed`;
- `build`: `artifact` containing `protocol`, `identity`, `bytes`, `profile`,
  and `target` but no physical output path;
- `check`: no additional required field.

Warnings and failures are emitted on stderr. A JSON failure is one object with
`protocol`, `operation`, `status: "error"`, and a deterministic `diagnostics`
array; `run` and `test` runtime failures additionally include captured
`stdout`. Human success output is bilingual and deterministic. Check, test,
and build human summaries contain no host path; run success is only captured
program output.

The protocol is Experimental and current-writer-only. Unknown fields have no
reader commitment. Incompatible fields or meanings require a new version and
migration evidence.

### 9. Exit classes and failure atomicity

The existing exit classes apply uniformly: `0` success, `1` source/project/
entry validation failure, `2` invalid usage, `4` runtime or host I/O failure,
`5` internal invariant failure, and `6` semantic snapshot mismatch. Exit `3`
remains reserved.

Manifest, lock, graph, source, entry, and runtime failures reuse existing
registered diagnostics. Artifact publication failures use a dedicated
registered bilingual `L-IO-*` code with stable `operation` and `io_kind`
Facts. A failed command MUST NOT modify sources or `ling.lock`; a failed build
MUST leave the requested output absent.

## Conformance plan

- Add parser tests for every command form, mixed file/project modes, duplicate
  and missing flags, unsupported profile/target/member options, stale names,
  and exact exit `2` behavior.
- Check valid single-package, multi-module, dependency, and Unicode projects;
  reject syntax, resolution, type, Effect, entry, lock, and artifact failures
  with bilingual diagnostics and original byte spans.
- Execute a dependency-using root entry in human and JSON modes and compare
  exact captured output, path-free identity fields, runtime Fault mapping, and
  repeatability across distinct physical roots.
- Run the isolated project smoke test and prove that standalone test discovery
  remains unchanged and no hidden files or dependency entries execute.
- Build the same project in distinct empty destinations and compare exact
  artifact bytes and SHA-256 identity; vary checked source, graph, profile, or
  target inputs and require an identity change or explicit unsupported-value
  rejection.
- Reject existing output files/directories/symlinks, unwritable/missing parent
  directories, malformed locks, and semantic failures without publishing a
  partial artifact or mutating project inputs.
- Freeze human/JSON stdout/stderr separation and every exit class. Prove no
  parent search, network, shell, environment, cache, lock update, dependency
  execution, or host-path leakage occurs.

## Compatibility impact

- **Source and language semantics:** no syntax, type, Effect, entry, or runtime
  rule changes. Commands consume existing checked project semantics.
- **CLI:** adds manifest-selected modes to `check`, `run`, and `test`, plus
  project-only `build`. Existing positional file modes and RFC-0024 graph
  check remain unchanged.
- **Diagnostics:** adds one artifact-I/O code; existing diagnostic schema and
  codes are unchanged.
- **Protocols:** adds Experimental `ling.project.command/0.1` and canonical
  `ling.project.artifact/0.1`. Existing `ling.project.check/0.1`,
  `ling.test/0.1`, and `ling.semantic/0.2` remain distinct.
- **Semantic IDs:** package-aware DefinitionId, BodyId, and ProgramId bytes are
  unchanged and embedded only by value. Artifact identity is a separate
  SHA-256 domain.
- **Data and migration:** build never overwrites an existing output. The new
  artifact has no predecessor and no Stable compatibility promise.
- **Binary/ABI:** none. The semantic artifact is not executable and exposes no
  Rust layout or ABI.
- **Determinism:** selection, graph, checked snapshot, reports, artifact bytes,
  and identity exclude ambient and unordered inputs.
- **Unicode:** remains 17.0.0; original source bytes and spans are preserved.

## Unresolved alternatives

- A directory-searching Cargo-style default was rejected because RFC-0002
  requires explicit selection absent a later Accepted discovery policy.
- Treating vendored dependencies as selectable workspace members was rejected;
  manifest version 1 has one root and no workspace schema.
- Reinterpreting RFC-0024 graph check as semantic checking was rejected because
  its exact Experimental observable behavior remains useful and compatible.
- Inventing test attributes or scanning arbitrary project files as standalone
  tests was rejected. Rich unit/integration tests require source syntax and
  isolation semantics in a later Accepted RFC.
- Calling current standalone bytecode a project artifact was rejected because
  its package table/lowering contract does not yet encode the complete
  RFC-0002 graph. The checked semantic artifact is honest about current scope.
- Output replacement, default build directories, Native/Critical profiles,
  bytecode/native/Wasm targets, caches, publication, signatures, and
  multi-member workspaces remain future work.
