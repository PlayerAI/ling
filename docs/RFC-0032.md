# RFC-0032: LSP push diagnostics v0 / LSP 推送诊断 v0

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-23
> 目标版本：v0.1 Experimental
> 作者/Owner role：ide-protocol-design
> 相关缺口：GAP-LSP-TRANSACTION-PROTOCOL-001
> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC defines deterministic `textDocument/publishDiagnostics` production
for the current Ling LSP server. It closes LSP-2202 without defining pull
diagnostics, diagnostic suppression/caps, or a general asynchronous scheduler.

## Summary

`ling.lsp.publish-diagnostics/0.1` captures an immutable analysis ticket after
successful source state changes, computes compiler diagnostics from those
exact bytes, and atomically publishes only a still-current result. Publications
replace prior URI results, carry open-document versions, clear removed or
diagnostic-free documents, and reuse RFC-0031 field mapping.

The adapter marker advances compatibly to `ling.lsp.diagnostic/0.2` solely to
admit validated `untitled://ling/...` sources. Every valid 0.1 non-temporary
adapter input retains identical output.

## Normative changes

### 1. Trigger and logical debounce

A successful state-changing `didOpen`, `didChange`, `didClose`, host disk
snapshot publication, or `ling/workspace/reload` MUST mark workspace diagnostic
analysis pending. Rejected operations and byte/state-identical no-ops MUST NOT
create work. A complete ordered RFC-0029 change array is one mutation.

The server exposes an explicit flush boundary. Multiple successful mutations
before one flush MUST coalesce to the newest complete state. The stdio host
MUST flush once after handling and writing any response for each input frame;
therefore compiler work never occurs inside overlay parsing/mutation and a
request response precedes notifications caused by that request. This logical
debounce observes no wall clock and makes no latency guarantee.

### 2. Immutable analysis ticket and freshness

Beginning pending analysis captures one owned ticket containing lifecycle
state, negotiated position encoding, session revision, every tracked URI,
logical name, exact visible UTF-8 bytes, open/closed state, optional current
client version, origin, and present project-input bytes/revisions. Ticket data
is path-free and later server mutation cannot change it.

Completion MUST compare the complete captured identity with current server
state. Any difference in lifecycle, encoding, revision, document identity,
bytes, origin, open state, client version, or project input makes the result
stale. A stale or failed completion MUST emit nothing, MUST NOT mutate the
published-result ledger, and MUST leave newer pending work intact. Only a
successful current completion clears pending state.

### 3. Compiler diagnostic set

Analysis MUST use only ticket bytes and locked offline compiler libraries. It
MUST perform no filesystem, environment, package-registry, network, shell,
cache-root, or host-path access.

For each captured source, the compiler first performs source, lexical, and
parse analysis. A source contributes its lexical errors when any exist;
otherwise it contributes its parse errors. If any source has syntax
diagnostics, the complete syntax set is published and semantic analysis is not
run. This is the bounded fast-failure path and prevents cascaded diagnostics
from unchecked syntax.

When all non-temporary sources are syntactically valid, they are lowered and
checked together through module resolution, type checking, and Effect checking.
Registered user-facing HIR, resolution, type, and Effect failures are converted
through their existing `to_diagnostic` rules. A successful checked workspace
contributes no diagnostics. Temporary sources participate in source/lex/parse
analysis only; they have no declared project membership and MUST NOT change
non-temporary workspace resolution or type/effect results.

An internal source/AST/query invariant failure is not a Ling user diagnostic.
It leaves the prior publication ledger unchanged and keeps analysis pending;
it MUST NOT be converted to an invented code, empty clearance, debug string,
or partial compiler result.

### 4. Adapter 0.2 extension

`ling.lsp.diagnostic/0.2` accepts the complete 0.1 source set plus validated
temporary `untitled://ling/<logical>.ling` identities. Temporary URI identity
MUST exactly match `untitled/<logical>.ling` in its `SourceFile`. Temporary
output otherwise uses the exact RFC-0031 field mapping, position projection,
ordering, and failure atomicity. No 0.1 output byte changes for an unchanged
non-temporary input.

### 5. Publication set and wire shape

A current result is grouped by primary URI. The candidate ledger contains one
entry for every URI in the ticket, including URIs with zero diagnostics. Each
entry is this exact JSON-RPC notification:

```json
{
  "jsonrpc": "2.0",
  "method": "textDocument/publishDiagnostics",
  "params": {
    "diagnostics": [],
    "uri": "ling://workspace/src/Main.ling",
    "version": 7
  }
}
```

`params.version` MUST be present with the exact non-negative client version for
an open document and MUST be omitted for a closed/disk-only or dependency
document. Diagnostics use RFC-0031/RFC-0032 adapter values and retain canonical
order within the URI.

URIs are compared in Unicode scalar-value order. The server emits a
notification only when an entry's exact `params` differs from the committed
ledger. It then emits empty clearance for every previously committed URI absent
from the candidate, using that ledger entry's last optional version, in the
same URI order. All notification values are constructed before ledger mutation;
any failure rejects the complete publication. After success the candidate
replaces the ledger atomically.

Consequently a newer open version replaces an older result even when the
diagnostic array is unchanged; the first successful analysis establishes an
explicit empty result; closing a temporary document clears it; closing a
workspace document republishes the visible disk result without `version`; and
removing a tracked source clears its previous URI.

### 6. Capability and compatibility marker

Initialize MUST advertise this exact Experimental member:

```json
"lingPublishDiagnostics": {
  "adapterVersion": "ling.lsp.diagnostic/0.2",
  "debounce": "message-boundary",
  "version": "ling.lsp.publish-diagnostics/0.1"
}
```

The marker describes current writer behavior; it adds no client request. An
incompatible trigger, ticket, diagnostic-set, notification, version, ledger,
or clearance change requires a new marker and migration evidence.

## Compatibility impact

- **Protocol:** adds Experimental `ling.lsp.publish-diagnostics/0.1` and
  advances `ling.lsp.diagnostic/0.1` to the backward-compatible 0.2 source-set
  extension. Neither protocol is Stable.
- **Diagnostic compatibility:** no code, severity, message, Facts, repair,
  Semantic ID, or `ling.diagnostic/0.1` schema change.
- **Source/language/runtime compatibility:** no Ling syntax, semantics, Typed
  Core, interpreter, runtime, bytecode, VM, ABI, or Unicode 17.0.0 change.
- **Host behavior:** adds deterministic stdio notifications and in-process
  compiler work but no filesystem/network access or latency guarantee.

## Unresolved alternatives

A wall-clock debounce timer and background worker pool were rejected for v0.1
because they would make tests and output timing host-dependent without an
accepted scheduler/fairness policy. The explicit flush/ticket boundary permits
a future host scheduler without changing freshness or publication semantics.

Pull diagnostics, push/pull parity, client refresh, cancellation requests,
partial results, result IDs, progress, root-cause grouping, deduplication,
caps, suppression, tags, code-description URLs, repair application, Workspace
Edits, Semantic Transactions, and Stable lifecycle remain future work.
