# RFC-0014: Portable verified bytecode and VM contract / 可移植已验证字节码与 VM 契约

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-21
> 目标版本：v0.1 Living
> 作者/Owner role：vm-design
> 相关缺口：GAP-BYTECODE-SEMANTICS-001
> 生命周期记录：`docs/governance/lifecycle.toml`

## Summary

This RFC defines Ling's first portable bytecode boundary, `ling.bytecode/1.0`, and the rules that separate untrusted bytes from executable VM state. The format is an explicitly encoded, little-endian, length-delimited register machine. It contains package, module, type, constant, source, function, entry-point, and source-map records; it never serializes a Rust enum or in-memory layout.

Version 1.0 deliberately covers the first VM vertical slice: `Unit`, `Bool`, `Int`, `Text`, direct function calls, immutable local values, integer operations, conditionals, the accepted scalar built-ins, `Console.write`, and return. It derives only from checked Typed Core. A decoder produces an untrusted model; an independent verifier is the only constructor of executable `VerifiedProgram` state; the VM accepts only that state.

The verifier proves structural, index, control-flow, register-type, signature, Effect, Capability, entry-point, source-map, and resource invariants before execution. Execution remains strict call-by-value and observably left-to-right. Program Faults preserve the interpreter's structured `L-RUNTIME-0001` behavior and original UTF-8 byte spans. Malformed bytecode is a bytecode diagnostic, never a Ling Runtime Fault or host panic.

## Normative changes

### 1. Trust boundary and abstract artifact

Bytecode compilation MUST consume a completed `ProgramSnapshot` or an equivalent checked Typed Core snapshot. It MUST NOT consume unresolved AST nodes, rerun name lookup in the backend, infer missing types, synthesize undeclared capabilities, or reinterpret host paths as language identity.

The pipeline has three distinct states:

```text
CheckedProgramSnapshot
    -> BytecodeModelV1
    -> encoded bytes
    -> DecodedProgramV1       (untrusted)
    -> VerifiedProgramV1      (executable)
```

The encoder and decoder MAY share scalar helpers, but verification MUST be a separate operation over the decoded model. The public constructor of `VerifiedProgramV1` is the verifier; neither decoded fields nor an unsafe escape hatch may manufacture it. The VM MUST accept only a `VerifiedProgramV1` plus explicit host capabilities and execution limits.

The abstract version-1.0 artifact is:

```text
BytecodeV1_0 {
    strings:     StringTable,
    packages:    PackageTable,
    modules:     ModuleTable,
    types:       TypeTable,
    constants:   ConstantTable,
    sources:     SourceTable,
    functions:   FunctionTable,
    entry:       FunctionIndex,
    source_map:  SourceMapTable,
}
```

Table indexes are artifact-local typed identifiers. A string index, function index, type index, package identity, source identity, and DEC-0012 Semantic ID are different domains and MUST NOT be interchangeable Rust aliases or untyped strings.

### 2. Envelope and scalar encoding

The exact 40-byte header is:

| Offset | Width | Field | Required value |
| ---: | ---: | --- | --- |
| 0 | 8 | magic | bytes `4c 49 4e 47 42 43 00 00` (`LINGBC\0\0`) |
| 8 | 4 | header length | little-endian `u32` value `40` |
| 12 | 2 | format major | little-endian `u16` value `1` |
| 14 | 2 | format minor | little-endian `u16` value `0` |
| 16 | 2 | language major | little-endian `u16` value `0` |
| 18 | 2 | language minor | little-endian `u16` value `1` |
| 20 | 2 | Unicode major | little-endian `u16` value `17` |
| 22 | 2 | Unicode minor | little-endian `u16` value `0` |
| 24 | 2 | Unicode patch | little-endian `u16` value `0` |
| 26 | 2 | reserved | zero |
| 28 | 4 | flags | zero |
| 32 | 8 | total byte length | exact little-endian artifact length |

The byte sequence after the header contains, in order, the string, package, module, type, constant, source, and function tables, then one `u32` entry function index, then the source-map table. No alignment padding or trailing bytes are permitted.

Unless a field below says otherwise:

- `u16`, `u32`, and `u64` are unsigned little-endian fixed-width integers;
- an index is a `u32`; `NO_INDEX` is `0xffff_ffff` and is legal only where explicitly stated;
- a table is `u32 entry_count` followed by that many records;
- a record is `u32 payload_byte_length` followed by exactly that many payload bytes;
- a variable vector is `u32 element_count` followed by its elements;
- `CapabilityTag` and `EffectTag` are one-byte `u8` values; vectors of fixed-width scalar values do not add per-element record framing;
- a Boolean byte is exactly `0` or `1`;
- reserved bytes and flags MUST be zero;
- checked arithmetic MUST be used before slicing, seeking, multiplying counts, or allocating.

Unknown tags, opcodes, nonzero reserved bits, length mismatches, truncation, and trailing bytes are errors. A decoder MUST NOT guess a version or recover by skipping unknown executable content.

### 3. Deterministic tables

The string table record payload is the raw UTF-8 string bytes. Strings are unique and sorted by raw UTF-8 bytes. A string value may contain NUL and is not normalized merely because it is stored in this table. Fields used as identifiers or logical paths are validated separately under their accepted Unicode/path rules.

A package record is exactly:

```text
name: PackageName string index
version: PackageVersion string index
content_sha256: 32 raw bytes
```

Packages use RFC-0002 syntax and are unique and sorted by `(name bytes, numeric version tuple, content bytes)`. The digest is the binary value of an RFC-0002 `sha256:` `PackageSourceId`, not text and not a Semantic ID.

A module record is:

```text
package: PackageIndex | NO_INDEX
name: qualified module-name string index
capabilities: sorted unique vector<CapabilityTag>
```

`NO_INDEX` denotes the file-oriented Seed compilation boundary. Project bytecode MUST use a package index. Modules are unique and sorted by `(package presence, package key, normalized module-name bytes)`. Version 1.0 defines one capability tag: `1 = Console.Write`. A module that can reach a `Console.Write` instruction through its functions MUST declare that capability, as required by DEC-0010.

The version-1.0 type table contains exactly these four entries in this order:

| Index | Tag | Ling type |
| ---: | ---: | --- |
| 0 | `0x00` | `Unit` |
| 1 | `0x01` | `Bool` |
| 2 | `0x02` | arbitrary-precision `Int` |
| 3 | `0x03` | `Text` |

Each type record payload is its one-byte tag. No duplicate, alias, variable, error, or open type is encodable. Function signatures refer to these type indexes directly; function values are not a version-1.0 value type.

A constant record starts with one tag byte, three zero reserved bytes, and its declared type index. Its remaining payload is:

| Tag | Type | Payload |
| ---: | --- | --- |
| `0x00` | `Unit` | empty |
| `0x01` | `Bool` | one Boolean byte |
| `0x02` | `Int` | sign byte, three zero bytes, `u32` magnitude length, minimal unsigned big-endian magnitude |
| `0x03` | `Text` | one string index |

An `Int` sign is `0` for zero, `1` for positive, or `2` for negative. Zero has an empty magnitude and sign `0`; a nonzero magnitude starts with a nonzero byte and has sign `1` or `2`. Constants are unique and sorted by `(type index, tag, payload bytes)`.

A source record is:

```text
module: ModuleIndex
logical_name: string index
original_byte_length: u64
content_sha256: 32 raw bytes
```

The logical name is package-root-relative for a project or module-root-relative for a file-oriented compilation, uses `/`, and contains no physical absolute path, current directory, username, URI, or environment expansion. Source records are unique and sorted by `(module key, logical-name bytes)`. The length and digest describe the exact original source bytes, including BOM or CRLF; source text itself is not embedded.

### 4. Function and register model

Version 1.0 is a block-based register machine in static single-assignment form. It has no operand stack. A function record is:

```text
module: ModuleIndex
name: identifier string index
parameter_types: vector<TypeIndex>
result_type: TypeIndex
effects: sorted unique vector<EffectTag>
register_count: u32
blocks: vector<Block>
```

Functions are unique and sorted by `(module key, normalized function-name bytes)`. Version 1.0 has one Effect tag: `1 = Console.Write`. The declared Effect set MUST equal the transitive Effect closure of the function's reachable instructions and direct calls; it is not a producer hint.

Blocks are stored in ascending block index, beginning at block `0`. A block payload is:

```text
parameters: vector<(RegisterIndex, TypeIndex)>
instructions: vector<InstructionRecord>
terminator: TerminatorRecord
```

Each element of the function's `blocks` vector is encoded as `u32 payload_byte_length` followed by exactly the block payload above. Block-parameter pairs are the two consecutive `u32` indexes shown above. Every instruction and the terminator retains its own record framing from §5; no additional alignment or implicit padding is present.

The entry block's parameters correspond one-for-one to the function parameters, in order. A branch supplies one value for every target-block parameter. Function arguments and branch arguments are values, not writable aliases.

Every register index is less than `register_count`. Each register is defined exactly once by an entry/block parameter or instruction destination. A use is legal only when its definition dominates that use on every incoming control-flow path. An instruction cannot read its own destination. The verifier assigns one exact type to every register and rejects conflicting joins. Local immutable bindings normally become register aliases in lowering and require no bytecode instruction.

### 5. Instruction encoding

Every instruction and terminator uses the record framing from §2. Its payload begins with a one-byte opcode and three zero reserved bytes. The remaining operands are exact; an operand list uses a `u32` count followed by register indexes.

Version-1.0 instructions are:

| Opcode | Name | Operands after prefix | Static result and behavior |
| ---: | --- | --- | --- |
| `0x01` | `Const` | `dest, constant` | `dest` has the constant's type |
| `0x02` | `IntUnary` | `dest, operator:u8, reserved[3], operand` | operator `0=positive`, `1=negative`; `Int -> Int` |
| `0x03` | `IntBinary` | `dest, operator:u8, reserved[3], left, right` | operator `0=add`, `1=subtract`, `2=multiply`, `3=divide`, `4=remainder`; `Int * Int -> Int` |
| `0x04` | `Compare` | `dest, operator:u8, reserved[3], left, right` | result is `Bool`; table below defines operand types |
| `0x10` | `Call` | `dest, function, argument_count, arguments...` | exact direct signature call |
| `0x11` | `Intrinsic` | `dest, intrinsic:u8, reserved[3], argument_count, arguments...` | exact accepted scalar built-in call |
| `0x20` | `ConsoleWrite` | `dest, text` | requires `Text`; produces `Unit` and `Console.Write` |

`Compare` operator tags are:

| Tag | Operation | Operand type |
| ---: | --- | --- |
| `0x00` | equal | `Bool` |
| `0x01` | not equal | `Bool` |
| `0x02` | equal | `Int` |
| `0x03` | not equal | `Int` |
| `0x04` | less | `Int` |
| `0x05` | less or equal | `Int` |
| `0x06` | greater | `Int` |
| `0x07` | greater or equal | `Int` |
| `0x08` | equal | `Text` |
| `0x09` | not equal | `Text` |

`Intrinsic` tags and exact signatures are:

| Tag | Built-in | Signature |
| ---: | --- | --- |
| `0x00` | `Text.format` | `(Text, Int) -> Text` |
| `0x01` | `max` | `(Int, Int) -> Int` |
| `0x02` | `min` | `(Int, Int) -> Int` |

`Text.format`, `max`, and `min` have the exact DEC-0011 behavior. `ConsoleWrite` performs one logical call through the injected `Console.Write` capability, and that operation writes the Text followed by exactly one UTF-8 LF; the VM/adapter split is not observable. `map` and `sum` are not assigned version-1.0 tags because their `List` boundary is not in this slice.

Version-1.0 terminators are:

| Opcode | Name | Operands after prefix | Behavior |
| ---: | --- | --- | --- |
| `0x80` | `Jump` | `target_block, argument_count, arguments...` | transfer to one block |
| `0x81` | `Branch` | `condition, true_block, true_count, true_arguments..., false_block, false_count, false_arguments...` | require `Bool`; select exactly one successor |
| `0x82` | `Return` | `value` | return a value matching the function result |

There is no implicit fallthrough. Every block has exactly one terminator. `&&` and `||` lower to blocks and `Branch` so DEC-0017 short-circuit behavior is explicit. Reordering, constant folding, or branch simplification is allowed only when result, Fault, Effect, and strict floating-point behavior remain observationally equal under `SEMANTICS.md` §8; version 1.0 itself has no floating-point operation.

### 6. Evaluation, Capability, Fault, and source maps

Within a block, the VM executes instructions in stored order, then its terminator. `Call` operands are already-evaluated registers listed in source evaluation order. Lowering MUST emit all potentially observable operand work in strict left-to-right order and MUST NOT hoist work from a skipped branch. A VM MUST NOT reorder instructions across an Effect or possible Fault unless the equivalence required by `SEMANTICS.md` §8.2 is proved.

Before executing any entry instruction, the VM computes the reachable direct-call graph and its required capabilities. Missing injected capabilities fail preflight before any program Effect. `ConsoleWrite` is valid only when its function Effect closure and owning module capability metadata include `Console.Write`. The injected handle is not serialized and cannot be forged by an instruction.

The following are Ling Runtime Faults and use the existing bilingual `L-RUNTIME-0001` contract:

- division or remainder by zero (`division_by_zero`);
- a `Text.format` placeholder count other than one (`invalid_format`);
- host Console failure (`broken_pipe`, `permission_denied`, `interrupted`, or `other`);
- unavailable required host capability detected by execution preflight (`capability_unavailable`);
- deterministic step/frame limit exhaustion (`resource_limit`);
- host allocation failure or implementation memory ceiling (`out_of_memory`).

Effects completed before a Runtime Fault remain observable; no instruction after the fault executes. A step is charged before each instruction and terminator, so exhaustion occurs before that operation and cannot partially perform it. `Call` itself is one step; callee operations are charged separately. Runtime limits do not convert a Fault into a Ling `Result` value.

Malformed bytes, invalid indexes, invalid control flow, type disagreement, missing bytecode metadata, or a verifier resource limit are `L-BYTECODE-*` load/compile diagnostics, not Runtime Faults. If the current Ling compiler emits bytecode that its own verifier rejects, that is `L-INTERNAL-0001`; blaming user source would hide a compiler invariant failure. An impossible invariant after construction of `VerifiedProgramV1` is likewise an internal error, never `InvalidCheckedCore` exposed as a user Fault.

Each instruction and terminator has exactly one source-map record:

```text
function: FunctionIndex
block: BlockIndex
ordinal: u32              # instruction index; terminator == instruction_count
source: SourceIndex
start_byte: u64
end_byte: u64
origin: u8                # 0 = direct, 1 = lowering-derived
reserved: seven zero bytes
```

Source-map records are sorted by `(function, block, ordinal)`, contain no duplicate or missing executable location, and use zero-based half-open original UTF-8 byte spans. `start_byte <= end_byte <= original_byte_length` is required. The source must belong to the function's module. A lowering-derived instruction uses the smallest enclosing checked source expression that justifies it; it MUST NOT fabricate a physical path or round an invalid UTF-8 boundary. A host may render line/column only after matching the source digest and applying DEC-0002 mapping rules.

### 7. Verification and resource limits

Verification is failure-atomic: it returns either one complete immutable `VerifiedProgramV1` or no executable state. It performs these phases in order:

1. envelope, exact version, total length, reserved fields, and record boundaries;
2. UTF-8, package/module/source names, table uniqueness/order, constant canonicality, and all index bounds;
3. function/block/instruction decoding, opcode operand lengths, signature references, and entry-block shape;
4. control-flow target/argument checks, reachability, dominance, single assignment, exact register types, call signatures, and return types;
5. transitive Effect calculation, module Capability authorization, and entry-point checks;
6. complete source-map coverage, source ownership, byte ranges, and deterministic ordering.

The entry MUST identify `Main.main`, with exact signature `(Unit) -> Unit`, one entry-block Unit parameter, and a module authorized for its reachable external Effects. Project bytecode may have a package identity; file-oriented bytecode uses `NO_INDEX`. No other function is implicitly executed during loading or verification.

The decoder/verifier enforces these version-1.0 hard maxima before allocation:

| Resource | Maximum |
| --- | ---: |
| artifact bytes | 67,108,864 |
| string entries | 262,144 |
| bytes in one string or integer magnitude | 16,777,216 |
| packages | 65,536 |
| modules | 65,536 |
| types | exactly 4 |
| constants | 1,048,576 |
| source files | 65,536 |
| functions | 262,144 |
| registers in one function | 65,536 |
| blocks in one function | 65,536 |
| call/branch arguments in one operation | 65,536 |
| instructions plus terminators in the artifact | 4,194,304 |
| source-map records | exactly the executable-location count, at most 4,194,304 |

Counts must also fit the remaining artifact bytes; reaching a numeric maximum does not authorize an impossible allocation. Implementations MAY apply a smaller caller-supplied limit, but must report the requested/configured maximum and actual value with a structured bytecode resource diagnostic. Normal locked/offline builds MUST require no network access after dependencies are available.

Execution takes explicit limits. Version 1.0 requires at least `step_limit`, `frame_limit`, and `heap_byte_limit` hooks. Their CLI defaults are not set by this RFC. Step and frame accounting are logical and deterministic. Heap enforcement is a host-safety boundary and MUST NOT expose allocation addresses, Rust layout, allocator text, or platform error strings; backend differential tests run without intentionally hitting implementation memory ceilings unless a later profile specification fixes a common logical heap model.

When reporting more than one independent verifier error, ordering is `(artifact byte offset, diagnostic code, stable reason tag, referenced index tuple)`. An implementation MAY stop after the first error; the selected first error MUST follow the same order. Error rendering is bounded independently from input size.

### 8. Compatibility, diagnostics, and determinism

`ling.bytecode/1.0` readers accept exactly format `(1, 0)`. They reject every other version before decoding version-specific tables. A later `1.N` is backward-compatible only if a reader supporting `1.N` also accepts every valid earlier `1.M` artifact and preserves the meaning of all earlier bytes. Adding an opcode, type, flag, Effect, Capability, record field, or table requires at least a minor-version increment and explicit reader support. Reinterpreting or removing an existing value, weakening a verifier invariant, changing evaluation/Fault behavior, or changing scalar framing requires a new major version and migration evidence.

There is no previous Ling bytecode format and no N-1 claim. Rust enum discriminants, `serde`/`bincode` output, current evaluator values, and pre-RFC prototypes are not recognized as legacy bytecode. A reader never sniffs or upgrades them. A migration tool must decode under the old verifier and encode through the new writer; byte copying or unchecked transmutation is forbidden.

The `BYTECODE` diagnostic domain is authorized for failures whose earliest root cause is bytecode lowering, decoding, resource validation, or verification. Exact `L-BYTECODE-*` codes and typed Facts MUST be registered before their emitters are merged. Public messages are Simplified Chinese and English. Bytecode-offset diagnostics use spans in the artifact bytes; Runtime Fault diagnostics use the verified original source-map span. Existing code meanings and `ling.diagnostic/0.1` framing do not change.

For one toolchain version, target bytecode version, checked snapshot, and explicit lowering options, the writer MUST produce byte-identical output across process hash seeds, host paths, directory enumeration, and supported operating systems. It sorts every set/map by the keys above, emits zero reserved fields, and never writes timestamps, addresses, filesystem metadata, Rust type names, debug text, host endianness, or capability handles.

Bytecode bytes are not DEC-0012 canonical semantic bytes. Equivalent programs or optimization levels may have different instruction graphs, and a bytecode digest is not a `BodyId` or `ProgramId`. Any future artifact/cache identity must include toolchain, format, language, Unicode, profile, target, lowering options, and verified input identity under a separate Accepted protocol.

## Conformance plan

- Freeze an independently constructed minimal `ling.bytecode/1.0` golden artifact and exact disassembly for `Main.main () = Console.write "你好，零"`; require encode-decode-encode byte equality and the exact UTF-8 output `你好，零\n`.
- Add positive fixtures for all four types, arbitrary integers beyond 128 bits, scalar built-ins, direct and recursive call graphs, branch/block parameters, short-circuit skipped Fault/Effect, package and standalone module keys, and Unit entry/return.
- Add malformed fixtures for every header field, count/length boundary, UTF-8 failure, unsorted/duplicate table, noncanonical integer, invalid/reserved tag, wrong operand length, invalid index, duplicate register definition, use-before-definition, dominance failure, bad block argument, invalid jump, wrong call/return type, Effect mismatch, Capability mismatch, invalid entry, incomplete source map, cross-module source map, and span overflow.
- Assert registered bilingual `L-BYTECODE-*` diagnostics, exact artifact offsets or verified original UTF-8 source spans, stable reason tags, bounded rendering, and no panic for arbitrary bytes.
- Differentially compare interpreter and verified VM result, logical Console events, Runtime Fault category/operation/commit state, and original byte span. Do not compare allocation address, frame layout, physical path, or internal instruction count.
- Run decoder/verifier fuzzing from valid and corrupt seeds, plus a valid-model mutator that preserves framing while violating one verifier invariant. Enforce termination, memory, diagnostic-count, and output-size bounds.
- Vary source physical root, line ending, process hash seed, file enumeration, and supported host while requiring byte-identical output for identical checked input. Change one constant, control-flow edge, Effect, Capability, span, or language/Unicode version and require an appropriate byte change or rejection.
- Record first-version migration evidence: random legacy bytes and Rust serialization are rejected, future major/minor versions are rejected by a 1.0 reader, and verification never publishes partial executable state.

## Compatibility impact

- **Source:** none. This RFC adds no Author Source syntax or type/evaluation rule. Unsupported version-1.0 backend features are rejected during lowering while the interpreter remains the execution path; they are not silently miscompiled.
- **Binary protocol:** `ling.bytecode/1.0` becomes an Accepted planned-public design. It remains `Future` and unimplemented in the support/protocol inventory until VM-1201 through VM-1204 provide the model, encoder, decoder, verifier, VM, fixtures, and evidence. Incompatible wire changes require a version transition.
- **CLI:** none in this RFC. It neither changes the default `run` backend nor introduces a bytecode input/output command. Any command, extension, exit behavior, or default limit needs its owning accepted CLI change.
- **Diagnostics:** the `BYTECODE` root-cause domain is authorized, but this RFC-only milestone allocates no code and changes no existing diagnostic Facts. VM implementation must register exact bilingual codes before use. Runtime program failures continue to use `L-RUNTIME-0001`; compiler-produced invalid bytecode uses `L-INTERNAL-0001`.
- **Semantic identity:** none. Definition, Body, and Program IDs and their canonical bytes are unchanged. Bytecode-local indexes and package identities remain distinct typed domains.
- **ABI/FFI:** none. The artifact is an interpreter/VM data protocol, not a native calling convention, memory layout, or foreign ABI.
- **Determinism:** byte order, table order, register validation, source-map order, error selection, and step accounting are specified without ambient or unordered inputs. Heap exhaustion remains a documented host limit, not a cross-backend semantic identity.
- **Unicode and positions:** Unicode remains 17.0.0. Identifiers retain their accepted NFC/XID/security rules; Text bytes are not normalized; source spans remain original UTF-8 byte ranges.

## Unresolved alternatives

- A stack machine was rejected for version 1.0 because block-entry stack joins obscure value identity and make typed verifier diagnostics less direct. Single-assignment registers expose dataflow without prescribing a Rust value layout.
- Serializing Rust enums, `serde` objects, or evaluator `Value` state was rejected because compiler refactors, discriminants, allocation choices, and host layout are not a portable protocol.
- WebAssembly was rejected as the primary v0.1 VM format because Ling still needs a verifier for Checked Core Effects, Capabilities, source Fault provenance, and language-specific types. A future Wasm backend may consume verified Ling IR.
- Serializing Checked Typed Core directly was rejected because source-oriented compiler structures are not an execution format and would expand the trusted execution surface.
- Ignoring unknown opcodes/flags was rejected: executable semantics cannot be safely skipped. Explicit minor-version support is the extension boundary.
- Embedding source text was rejected for 1.0 to avoid duplicating source artifacts and leaking paths/content. Logical names, exact byte length, digest, and byte spans provide the required provenance boundary.
- Full Seed aggregates, closures, mutation, and collection built-ins remain future accepted minor revisions owned by VM-1205 through VM-1208. Version 1.0 has no placeholder opcode for them and must reject lowering those constructs explicitly.
- Compression, signatures, artifact/cache IDs, dynamic linking, JIT metadata, debugger records, and a common logical heap-accounting model remain separate future proposals. No unresolved alternative prevents implementation of the version-1.0 slice.
