# RFC-0021: Static Trait Dictionary Call Boundary / 静态 Trait 字典调用边界

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-22
> 目标版本：v0.1 Living
> 作者/Owner role：type-system-design
> 相关缺口：GAP-TRAIT-COHERENCE-001
> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC completes the missing runtime-facing boundary left open by
`RFC-0005` and `DEC-0027`. It defines how a checked, statically selected Trait
member reaches the interpreter and the existing verified bytecode direct-call
path. It does not add dynamic dispatch, trait objects, or a new bytecode wire
revision.

本 RFC 收口 `RFC-0005` 与 `DEC-0027` 留下的运行时边界，规定经过检查并静态选定的
Trait 成员如何进入 interpreter 以及现有已验证字节码的 direct-call 路径。本 RFC
不增加动态分派、trait object 或新的字节码 wire revision。

## Summary

The compiler produces an immutable dictionary witness for each solved concrete
obligation. A Trait member reference is resolved to a member slot in that
witness and to the concrete implementation `DefinitionId`. The interpreter
and bytecode lowerer consume that checked mapping; neither backend performs
candidate search or infers an implementation from a runtime value.

编译器为每个已求解的具体 obligation 生成不可变 dictionary witness。Trait 成员引用
解析为 witness 中的成员 slot 以及具体实现的 `DefinitionId`。interpreter 与
bytecode lowerer 只消费该 checked mapping；后端不得重新搜索候选实现，也不得根据
运行时值猜测实现。

## Status and scope

- Current lifecycle state: `Accepted`
- Stable implementation basis: `yes` for the experimental v0.1 static Trait slice
- In scope:
  - qualified static member references written as `Trait.member`;
  - concrete nominal receivers selected by the existing RFC-0005 solver;
  - immutable witness attachment to `TypedProgram` and `CheckedProgram`;
  - deterministic member-slot and implementation-definition identity;
  - interpreter invocation and partial application through a witness-bound value;
  - lowering to the existing verified bytecode direct-call representation;
  - interpreter/VM differential evidence for successful and rejected calls;
- Out of scope:
  - implicit receiver syntax, dynamic dispatch, existential values, and trait objects;
  - generic receiver substitution or blanket/generic implementations;
  - associated types, default methods, supertraits, specialization, and negative impls;
  - a serialized dictionary table or a new `ling.bytecode` revision;
  - v0.0.1 Seed support, CLI claims, or a Stable 1.0 Trait promise;
- Normative documents or clauses affected:
  - `RFC-0005` §1.5, §2, and §4;
  - `DEC-0026` and `DEC-0027`;
  - `RFC-0014` §5–§8 for the existing direct-call verifier and source maps;
  - `docs/SEMANTICS.md` §6.8 and `docs/LANGUAGE.md` §6.4.

## Normative changes

1. A qualified expression `Trait.member` MUST resolve to the declared member
   of exactly one Trait visible from the current module. It is a static member
   reference, not a runtime namespace lookup. The first explicit argument is
   the receiver; subsequent arguments follow the declared member signature.
   No implicit receiver or dynamic fallback is permitted.
2. The first implementation slice MUST accept only a concrete nominal receiver
   for which the existing coherence index and solver produce exactly one
   candidate. A receiver type variable, a generic implementation, an
   unresolved obligation, or an ambiguous candidate MUST be rejected before a
   `TypedProgram` is published.
3. Each implementation member MUST have a deterministic definition identity
   derived from the owning Trait identity, implementation identity, and member
   ordinal. The identity MUST remain independent of physical paths, allocation
   addresses, Rust layout, and hash-map order. The member's original UTF-8 span
   remains diagnostic provenance only.
4. The checked representation MUST contain, for every resolved member call, an
   immutable record containing `(witness identity, member ordinal, member
   DefinitionId, receiver type)`. The witness MUST contain the selected
   `(TraitId, ImplId, receiver type, ordered member slots)` and MUST be attached
   to the checked program before either backend is called. Backends MUST NOT
   re-run coherence or solver selection.
5. A witness-bound member value MAY be partially applied. Applying it MUST
   consume arguments in source order, bind the selected witness before user
   arguments, and invoke only the member `DefinitionId` recorded in the
   checked mapping. A call with too many or incompatible arguments MUST fail at
   checking time; an absent or inconsistent mapping at runtime is an internal
   Checked Core fault, not a user-level dynamic dispatch result.
6. The interpreter MUST execute the implementation member body with the
   explicit receiver as its first parameter and the same environment and
   source-span rules as an ordinary checked definition. It MUST preserve
   existing effect ordering and host-fault projection.
7. The bytecode lowerer MUST translate a witness-resolved member call to the
   existing direct-call instruction and implementation-definition table. The
   verifier MUST apply the existing call-target, arity, type, Effect,
   Capability, and source-map checks. No dictionary identity may be inferred
   from a VM value, and no new wire tag or revision is introduced by this RFC.
8. The canonical checked witness bytes and Semantic/Program identity MUST
   include selected implementation and ordered member identity, while omitting
   source paths, spans, allocation details, and host formatting. Repeated
   lowering, module presentation order, and hash seeds MUST produce equal
   logical mappings and canonical bytes.
9. Rejected Trait programs remain outside the v0.0.1 support matrix. Until the
   implementation evidence in this RFC is complete, public CLI/LSP/package
   surfaces MUST continue to report the existing unsupported boundary rather
   than claim partial Trait execution.

## Conformance plan

- Accept a positive same-module program with one concrete nominal receiver,
  one Trait member, a multi-argument member call, and a partial-application
  case; compare checked interpreter and verified VM results.
- Reject an unknown member, a non-Trait qualified name, a generic receiver, an
  unresolved obligation, an ambiguous implementation, a missing implementation
  member, and an over-applied member with stable bilingual diagnostics and
  original UTF-8 byte spans.
- Verify deterministic member `DefinitionId` and witness bytes across repeated
  processes, CRLF/BOM/Unicode source, module input order, and hash seeds.
- Mutate or remove witness/member mappings and require failure-atomic checked
  construction or a bounded `InvalidCheckedCore` fault; no backend may silently
  fall back to candidate search.
- Lower the same checked snapshot to the existing bytecode revision, decode and
  verify it, then compare logical events, Unit/results, Runtime Fault facts,
  source spans, and checked snapshot identity with the interpreter.
- Keep generic/blanket implementations, trait objects, serialized dictionary
  formats, and future bytecode revisions in separately accepted RFCs.

## Compatibility impact

- Source: adds only the v0.1 static `Trait.member` call boundary authorized by
  `RFC-0005`; v0.0.1 source behavior is unchanged.
- Bytecode: no opcode, record, tag, field, or version change. Existing direct
  calls carry the selected implementation target.
- Runtime: adds no host capability or Runtime Fault category. Missing checked
  mappings use the existing internal Checked Core fault boundary.
- Diagnostics: no new code is allocated by this RFC; future public Trait
  diagnostics must use registered bilingual codes and preserve source spans.
- Semantic IDs and schemas: the existing checked identity must incorporate the
  witness/member selection; no new public JSON schema version is claimed.
- CLI, LSP, package protocols, ABI/FFI, and Unicode 17.0.0: unchanged.

## Unresolved alternatives

- Serializing dictionary tables in bytecode is deferred because the first slice
  can preserve the selected identity through a verified direct-call target.
  A serialized witness is a new compatibility surface and requires a new RFC.
- Generic dictionary threading is deferred until type-variable substitution
  and generic implementation coherence have independent accepted evidence.
- Implicit receiver syntax and dynamic dispatch are rejected for this slice;
  they would require a distinct existential/object model and runtime contract.
