# RFC-0036: LSP Document Symbols Preview / LSP 文档符号 Preview

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-23
> 目标版本：v0.1 Preview
> 作者/Owner role：ide-protocol-design
> 相关缺口：GAP-LSP-TRANSACTION-PROTOCOL-001; GAP-SEMANTIC-PROTOCOL-LIFECYCLE-001
> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC defines Ling's bounded LSP `textDocument/documentSymbol` surface. It
closes IDE-2301 by composing the Accepted lifecycle, overlay, position, and
resolved-definition boundaries into deterministic hierarchical or flat source
outlines without exposing Semantic IDs as presentation identity.

本 RFC 定义 Ling 有界的 LSP `textDocument/documentSymbol` 接口。它组合已接受的
生命周期、overlay、位置与 resolved-definition 边界，生成确定性的层级或扁平源码
outline，同时不把 Semantic ID 暴露为展示身份，从而关闭 IDE-2301。

## Summary

`ling.lsp.document-symbol/0.1` captures one complete current request snapshot,
resolves the visible workspace from exact bytes, builds one compiler-owned
module outline with original UTF-8 byte spans, and projects it through the
initialize-negotiated position encoding. Clients declaring hierarchical
support receive one module-rooted `DocumentSymbol` tree; other clients receive
a pre-order `SymbolInformation` list.

## Normative changes

### 1. Negotiation and discovery

Initialize recognizes optional
`capabilities.textDocument.documentSymbol.hierarchicalDocumentSymbolSupport`.
If `documentSymbol` is present it MUST be an object; if the known hierarchical
member is present it MUST be a boolean. Malformed known shapes reject
initialize as InvalidParams without lifecycle mutation. Absence means flat
fallback. The selected mode is immutable for the session.

Every successful initialize MUST advertise `documentSymbolProvider: true` and
this exact Experimental member:

```json
"lingDocumentSymbols": {
  "maxSymbols": 4096,
  "mode": "hierarchical",
  "version": "ling.lsp.document-symbol/0.1"
}
```

`mode` is `hierarchical` only when the client explicitly declares `true`; it
is otherwise `flat`. The capability adds no custom request.

### 2. Request and snapshot

`textDocument/documentSymbol` accepts a request object with required string
`textDocument.uri` and ignores ordinary unknown fields. The URI MUST be an
exact currently tracked Ling document identity. Wrong known shapes or unknown
documents return InvalidParams `-32602`. A notification with this method does
nothing and receives no response.

The server MUST be Ready, capture one immutable path-free request snapshot,
and use exact visible bytes, project inputs, URI/logical-name identities,
position encoding, document versions, origins, and revision. Non-temporary
requests resolve the complete non-temporary snapshot. A temporary request
resolves only that exact temporary source plus project inputs, so scratch files
cannot alter workspace symbol resolution.

The complete snapshot MUST be recaptured before success. Any difference makes
the result stale and returns RequestFailed without partial output or mutation.
The synchronous host cannot observe a later cancellation while handling the
request; 0.1 advertises no work-done or partial-result channel.

### 3. Compiler structural outline

The compiler query produces exactly one module root. Its full span is the
complete HIR program span and its selection span is the declared module-name
span. It merges the resolver-validated HIR collections into original-byte
source order and creates these children:

| Ling structure | Compiler outline | LSP `SymbolKind` |
| --- | --- | ---: |
| module | Module | Module `2` |
| record type | Record | Struct `23` |
| variant type | Variant | Enum `10` |
| alias type | Alias | Class `5` |
| record field | Field | Field `8` |
| variant case | VariantCase | EnumMember `22` |
| parameterized top-level `let` | Function | Function `12` |
| immutable zero-parameter `let` | Constant | Constant `14` |
| Trait declaration | Trait | Interface `11` |
| Trait member | TraitMember | Method `6` |
| implementation | Implementation | Object `19` |
| implementation member | ImplementationMember | Method `6` |

Type fields/cases, Trait members, and implementation members are children of
their declarations. Other top-level nodes are children of the module.
Implementation display names are exactly `impl <normalized-trait> <receiver>`,
where receiver text is sliced from its validated original UTF-8 span and
trimmed only at its edges. Its selection span is the Trait-name span.

Names otherwise retain original source spelling. Local pattern bindings are
not module-outline definitions in 0.1. Seed rejects mutable top-level
definitions; they MUST NOT be represented as a reachable Variable kind.
Builtins and Prelude values remain excluded. Semantic Graph and resolver IDs
remain internal identity and MUST NOT be copied into `name`, `detail`, or an
invented `data` field.

Every selection span MUST be within its full span, every child full span within
its parent, and every span MUST name the exact source and fit its original
bytes. Violation rejects the complete query. At most 4096 nodes including the
module root are allowed; overflow returns no truncated result.

### 4. Ordering

Sibling nodes sort by `(original start byte, original end byte, compiler
outline kind, display name)`. The currently generated HIR has unique
structural source spans; the final name tie-breaker makes equal span/kind
observations deterministic. Hierarchical children use this order.
Flat fallback performs a stable pre-order traversal of the same tree.

No URI map order, filesystem path, hash-map iteration, allocation, thread,
clock, process, environment, cache, or debug rendering enters the result.

### 5. Hierarchical response

An explicitly hierarchical client receives an array containing exactly the
module root. Every node has exactly:

```json
{
  "children": [],
  "kind": 12,
  "name": "计算",
  "range": {"end":{"character":20,"line":3},"start":{"character":0,"line":3}},
  "selectionRange": {"end":{"character":6,"line":3},"start":{"character":4,"line":3}}
}
```

`range` and `selectionRange` project original bytes through the negotiated
UTF-8, UTF-16, or UTF-32 source map. `children` is always present, including
an empty array. `detail`, `tags`, and `deprecated` are omitted.

### 6. Flat response

A flat client receives one `SymbolInformation` per tree node in pre-order.
Each item has exact `name`, mapped `kind`, and `location` containing the request
URI and projected full `range`. Non-root items have `containerName` equal to
their immediate parent's display name; the root omits it. No hierarchy,
selection range, package path, version, Semantic ID, tags, or deprecated field
is emitted.

### 7. Failures and compatibility

Syntax/HIR/resolution failure, invalid compiler outline, projection failure,
stale completion, node overflow, or an encoded success body above RFC-0004's
1 MiB maximum returns LSP RequestFailed `-32803` with fixed bilingual message
`文档符号不可用 / document symbols unavailable`. No compiler diagnostic is
allocated, no partial result is emitted, and diagnostics/push state/documents
remain unchanged.

An incompatible mapping, hierarchy, field, ordering, bound, request, or error
change requires a new marker and migration evidence. Additive compiler
language constructs require an Accepted mapping before appearing in this
response.

## Compatibility impact

- **Protocol:** adds Preview `ling.lsp.document-symbol/0.1`; no predecessor.
- **Compiler query:** adds an immutable bounded resolved structural outline;
  existing DEC-0073 flat definition-index behavior is unchanged.
- **Diagnostics/identity:** no code allocation or Semantic ID/schema change.
- **Language/runtime/data:** no Ling syntax/semantics, Typed Core, interpreter,
  runtime, bytecode, VM, ABI, filesystem/network/cache, or Unicode 17.0.0
  behavior changes.

## Unresolved alternatives

Using Semantic IDs as display identifiers was rejected because LSP symbol
presentation and compiler identity have different lifecycles. Returning a
hierarchical tree to a client that did not declare support was rejected in
favor of the standard flat fallback. Truncation was rejected because omission
would be silent; the bounded request fails atomically instead.

Local bindings, inferred detail text, documentation, deprecation tags, dynamic
registration, progress, partial results, asynchronous cancellation, caching
promises, Workspace Edits, Semantic Transactions, and Stable lifecycle remain
future work.
