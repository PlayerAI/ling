## Summary

This RFC extends Accepted RFC-0014 with the backward-compatible `ling.bytecode/1.1` minor revision owned by VM-1205. Revision 1.1 adds structural function value types with latent Effect rows, explicit closure construction, typed indirect application, partial application, immutable lexical capture, and local self-recursion. It also authorizes checked-source lowering for top-level recursion and this first-class function slice.

The extension does not expose a Rust closure layout or host stack. Captures are ordered artifact values, recursive closure initialization is one verifier-proved self slot, and every function invocation uses the VM's existing iterative frame stack. Frame exhaustion and allocation failure retain RFC-0014's structured Runtime Fault behavior.

## Normative changes

### 1. Version boundary and shared 1.x rules

The protocol identifier for this revision is `ling.bytecode/1.1`, encoded as format tuple `(1, 1)` in the unchanged RFC-0014 40-byte header. Language and Unicode version fields remain `(0, 1)` and `(17, 0, 0)` respectively. All RFC-0014 rules remain normative unless this RFC explicitly replaces a version-specific rule.

A 1.1 reader MUST accept and verify every valid 1.0 artifact under its original 1.0 rules. It MUST dispatch on the exact version before reading version-specific type, function, or instruction records. A 1.0 artifact is not rewritten, reinterpreted as containing closures, or accepted with 1.1-only bytes. A 1.0 reader continues to reject 1.1 before table decoding.

The 1.1 writer emits only `(1, 1)`. Migrating a 1.0 artifact to 1.1 means decode and verify as 1.0, then encode the equivalent unified verified model under the 1.1 writer; byte-header patching is forbidden. Both revisions remain Experimental and bytecode bytes remain distinct from DEC-0012 canonical semantic bytes.

### 2. Version-1.1 value types and latent Effects

The first four type records remain byte-identical scalar records in the RFC-0014 order. Version 1.1 permits additional structural function type records after them:

```text
FunctionType {
    tag:             u8 = 0x10
    reserved:        [u8; 3] = zero
    parameter_types: vector<TypeIndex>
    result_type:     TypeIndex
    effects:         sorted unique vector<EffectTag>
}
```

The record framing remains `u32 payload_byte_length` followed by the payload. A function type has at least one parameter. Its parameter and result indexes MUST refer only to an earlier type-table entry. This strict topological order forbids recursive wire types and permits bounded single-pass validation. Function types are unique and sorted structurally by `(tag, parameter type-index vector, result type index, Effect-tag vector)` after the fixed scalar prefix.

The Effect vector is the latent Effect of completely applying the function value. Creating, capturing, passing, returning, or partially applying that value performs no latent Effect. A complete `CallClosure` contributes the callee type's latent Effect row at that instruction. The row contains only Effect tags implemented by the selected bytecode revision; version 1.1 still defines only `1 = Console.Write`.

Function values have no equality or ordering operation. No instruction may inspect their capture count, target function, bound arguments, allocation identity, or implementation representation.

### 3. Version-1.1 function records

The version-1.1 function record replaces the version-1.0 payload with:

```text
kind:               u8                  # 0 = named, 1 = closure body
reserved:           [u8; 3] = zero
module:             ModuleIndex
name:               string index
capture_count:      u32
parameter_types:    vector<TypeIndex>   # captures first, callable parameters second
result_type:        TypeIndex
effects:            sorted unique vector<EffectTag>
register_count:     u32
blocks:             vector<Block>
```

A named function has `kind = 0` and `capture_count = 0`; its name obeys the RFC-0014 identifier rule. A closure body has `kind = 1`; its name is non-semantic bytecode metadata generated deterministically as `closure_<source-start>_<source-end>_<lexical-ordinal>`, using unsigned decimal integers without leading zeroes. Closure-body uniqueness is `(module key, name bytes)`. Named-function and closure-body namespaces are disjoint.

For a closure body, `capture_count <= parameter_types.len()`. The first `capture_count` entry parameters receive captures; the remaining entry parameters are the callable parameters visible in its function value. A closure body MUST have at least one callable parameter. The complete callable function type—remaining parameters, result, and function-record Effect row—MUST exist in the type table.

Functions are stored in ascending `(module key, kind, name bytes)` order. Direct `Call` may target only a named function and retains the exact version-1.0 signature behavior. The entry point is a named function. Closure bodies are reached only through a verified closure value.

### 4. Lexical capture and recursive initialization

Checked-source lowering computes the free local bindings of each local parameterized binding. A reference is free when it resolves to a parameter or local binding outside that local function and is not a module definition or built-in. Captures are the minimal such set; unused surrounding bindings MUST NOT be captured.

Capture order is canonical lexical declaration order: containing function parameters in parameter-pattern preorder, followed by local bindings in source/preorder, recursively applying the same rule to enclosing local functions. The lowering implementation MUST use this order directly and MUST NOT derive capture order from hash iteration, allocation addresses, debug text, or physical paths.

Version 1.1 captures only immutable values, by value, at the `MakeClosure` instruction. Subsequent rebinding or REPL generations do not alter an existing closure. Capturing a mutable binding, Place, Cell, or value whose bytecode type is unavailable is an explicit lowering rejection owned by a later task; it is not silently copied or boxed.

A local `let rec` binding may refer to itself. Exactly one capture operand for that closure may be the `Self` source described below. Its corresponding capture parameter type MUST equal the complete callable function type of the closure. `Self` denotes the closure value being constructed, not a Unit placeholder and not a partially initialized observable cell. No other cyclic capture graph or mutually recursive local group is encodable in 1.1.

Top-level recursion uses ordinary direct `Call` and requires no closure allocation when the function is only called directly. Referencing the recursive top-level function as a value uses `MakeClosure` with zero captures; recursive calls inside its named body remain direct.

### 5. New instructions

Version 1.1 adds two instructions. They retain RFC-0014 record framing and the one-byte opcode plus three zero reserved bytes prefix.

`MakeClosure` has opcode `0x12` and payload:

```text
destination:  RegisterIndex
function:     FunctionIndex
capture_count: u32
captures:     capture_count * CaptureOperand

CaptureOperand {
    kind:     u8              # 0 = register, 1 = self
    reserved: [u8; 3] = zero
    value:    u32             # RegisterIndex for register; NO_INDEX for self
}
```

The function target may be named only when `capture_count = 0`; otherwise it MUST be a closure body. The operand count MUST equal the target function's `capture_count`. Register captures are read in encoded order and their exact types MUST match the corresponding leading function parameters. At most one operand is `Self`; `Self` is permitted only for a closure body, uses `NO_INDEX`, and its expected type MUST equal the resulting complete callable function type. A register operand MUST NOT use `NO_INDEX`.

The destination type is the unique structural function type formed from the target's non-capture parameters, result, and Effect row. Construction is Pure. The VM allocates the complete closure atomically; allocation failure is `L-RUNTIME-0001` category `out_of_memory` at the `MakeClosure` source span and publishes no destination value.

`CallClosure` has opcode `0x13` and payload:

```text
destination:    RegisterIndex
callee:         RegisterIndex
argument_count: u32
arguments:      vector<RegisterIndex>
```

The callee MUST have a structural function type. `1 <= argument_count <= remaining parameter count`, and each argument type MUST match in order. The callee register is evaluated before argument expressions; lowering emits argument work strictly left-to-right as required by RFC-0014 and `SEMANTICS.md` §8.

If fewer than all remaining parameters are supplied, `CallClosure` returns a function value whose type contains the unapplied suffix, the same result, and the same latent Effect row. No function body is entered and no latent Effect occurs. If all remaining parameters are supplied, the VM pushes one explicit frame containing captures, previously bound partial arguments, and current arguments in that order. The destination then has the target result type. Supplying zero or too many arguments is invalid bytecode.

### 6. Verification, call graph, and Capability preflight

The version-1.1 verifier extends RFC-0014's ordered phases without weakening any 1.0 invariant. It validates function-type topological order and uniqueness; function kind/name/capture shape; capture operand kind, sentinel, count, and exact type; `Self` uniqueness and type; indirect-call callable/argument/result typing; and complete source-map coverage for the new instructions.

Effect validation uses both direct and indirect edges:

- a direct `Call` contributes its target function's transitive row;
- a complete `CallClosure` contributes the callee function type's latent row;
- `MakeClosure` and partial `CallClosure` contribute no immediate Effect;
- every closure target's function-record row MUST equal the row in its complete callable type;
- every function-record row MUST equal the union of its reachable direct calls, complete indirect-call latent rows, and direct Effect instructions.

Capability preflight begins from the entry function's verified Effect closure. It therefore rejects a missing `Console.Write` handle before execution even when the required Effect is reachable only through a higher-order argument or captured closure. Preflight MUST NOT execute closure construction, inspect runtime branch choices, or depend on a physical allocation layout.

Malformed closure metadata is `L-BYTECODE-*`, never a Runtime Fault. Compiler-produced invalid closure bytecode is `L-INTERNAL-0001`. An impossible target, capture, or callable invariant after construction of verified state is an internal VM error.

### 7. Runtime frames, limits, Faults, and determinism

Named calls, complete closure calls, and recursive calls all use the same iterative VM frame stack. Implementations MUST NOT implement language recursion through Rust or host-language recursion. A frame is charged before allocating or entering it; if `frame_limit` is exhausted, execution produces RFC-0014 `L-RUNTIME-0001` category `resource_limit` at the call instruction and enters no new frame.

Closure storage and growth of a partial application are charged against `heap_byte_limit`. Because RFC-0014 does not define a common cross-backend heap formula, differential tests that intentionally exhaust heap compare only the documented host-safety category and source provenance, not an exact shared threshold. Allocation failure remains `out_of_memory`, exposes no allocator text/address, and cannot partially perform a program Effect.

One logical step is charged for `MakeClosure` or `CallClosure` before its operation, exactly like every other instruction. Callee instructions are charged separately. Values captured or bound earlier are not reevaluated. Effects completed before a recursive limit Fault remain committed.

The writer's function-type order, function order, capture order, instruction order, source-map order, and generated closure labels MUST be byte-identical for the same checked snapshot and lowering options across host paths, hash seeds, and supported operating systems. Closure allocation identity, pointer topology, reference counts, host stack details, and Rust `Debug` output are never observable Ling or protocol behavior.

## Conformance plan

- Freeze independent 1.1 bytes/disassembly containing a function type, captureless function reference, captured closure, partial application, `Self` capture, and complete indirect call; require decode-verify-encode byte equality.
- Lower and execute checked source for captureless first-class top-level functions, immutable lexical capture, closure return, partial application, exact application, top-level recursion, and local self-recursion.
- Differentially compare interpreter and VM result, Console logical events, Runtime Fault category/operation/commit state, and original UTF-8 byte span for terminating and frame-limited cases.
- Add malformed vectors for type forward/cyclic references, duplicate/unsorted function types, invalid function kind/name/capture count, invalid capture kind/sentinel/index/type, duplicate or wrong-typed `Self`, direct call to a closure body, non-function indirect call, zero/too-many/mistyped arguments, missing partial-result type, Effect disagreement, and missing source-map entries.
- Verify missing higher-order Console capability fails preflight before step/frame/heap limits and before all Effects.
- Verify mutable capture, polymorphic function values, unsupported aggregate captures, and mutually recursive local groups fail lowering explicitly without publishing bytecode.
- Run arbitrary-byte and valid-model mutation tests with bounded allocation, deterministic first-error selection, and no panic.

## Compatibility impact

- **Source:** no new syntax. Existing checked monomorphic first-class functions, closures, partial applications, and recursion gain an additional Experimental backend representation; interpreter behavior remains authoritative for differential evidence.
- **Binary protocol:** introduces backward-compatible `ling.bytecode/1.1`. A 1.1 reader accepts 1.0 and 1.1; a 1.0 reader rejects 1.1. No Stable or N-1 release promise is created.
- **CLI:** none. No bytecode command, default backend, or runtime-limit default is added.
- **Diagnostics:** no new Runtime Fault meaning. Exact new bytecode rejection reasons use already registered bilingual `L-BYTECODE-*` codes unless a genuinely new root-cause code is registered before implementation.
- **Schema and Semantic ID:** no JSON schema, Definition/Body/Program ID, or canonical semantic-byte change. Closure labels and capture slots are bytecode-local.
- **ABI/FFI:** none. The abstract closure value and frame rules do not define Rust, native, C, or device layout.
- **Determinism:** canonical type/function/capture order and explicit self capture remove host enumeration and allocation identity from the artifact and execution result.
- **Unicode and positions:** Unicode remains 17.0.0. Closure labels are ASCII bytecode metadata; user identifiers retain NFC/XID/security rules, and Fault spans remain original zero-based half-open UTF-8 byte ranges.

## Unresolved alternatives

- A hidden environment pointer or serialized host closure was rejected because it would expose implementation layout and bypass independent verification.
- Capturing every visible binding was rejected because it makes irrelevant lexical state affect artifacts and resource use; only resolved free immutable bindings are captured.
- A mutable placeholder cell for recursive initialization was rejected because partially initialized state could become observable. The verifier-proved `Self` operand expresses the only 1.1 local cycle atomically.
- Erasing latent Effects from function types was rejected because indirect calls would make Effect closure and Capability preflight unverifiable.
- Requiring exact arity only was rejected because checked Seed evaluation already supports partial application. Partial `CallClosure` preserves that behavior without executing the body.
- General closure groups, mutable captures, aggregate captures, monomorphization, tail-call guarantees, and common logical heap accounting remain separately owned future work. No unresolved alternative prevents VM-1205 implementation.
