# RFC-0031: LSP compiler diagnostic adapter / LSP 编译器诊断适配器

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-23
> 目标版本：v0.1 Experimental
> 作者/Owner role：ide-protocol-design
> 相关缺口：GAP-LSP-TRANSACTION-PROTOCOL-001
> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC defines the deterministic conversion from registered Ling compiler
diagnostics to LSP `Diagnostic` values. It closes `LSP-2201`; publication,
debounce, replacement/clearance, stale compiler results, and error-storm caps
remain owned by later tasks.

本 RFC 定义已注册 Ling 编译器诊断到 LSP `Diagnostic` 值的确定性转换。它关闭
`LSP-2201`；发布、去抖、替换/清除、过期编译结果和错误风暴上限仍由后续任务负责。

## Summary

`ling.lsp.diagnostic/0.1` adapts diagnostics against an immutable set of exact
logical sources and their path-free Ling URIs. Primary and related original
UTF-8 byte spans are projected through the initialize-negotiated position
encoding. Stable codes, bilingual messages, severity, structured Facts,
Semantic IDs, and repair kinds are preserved in explicit fields.

## Status and scope

- Current lifecycle state: `Accepted`
- Stable implementation basis: `yes` for this Experimental/current-writer-only
  adapter
- In scope:
  - exact field mapping for currently emitted registered diagnostics;
  - primary and explicit related-label position projection;
  - canonical diagnostic ordering and deterministic JSON object construction;
  - versioned Experimental `data` containing Facts, Semantic ID, and repairs;
  - strict rejection of missing/mismatched/invalid spans without clamping.
- Out of scope:
  - `publishDiagnostics`, pull diagnostics, document-version publication,
    debounce, cancellation, stale compiler result policy, replacement/clear,
    root-cause grouping, deduplication, omission caps, suppression, quick fixes,
    Workspace Edits, Semantic Transactions, and Stable compatibility.
- Normative dependencies:
  - `SEMANTICS` §26 and `ERROR-CODES` diagnostic identity/localization rules;
  - DEC-0001 stable error-code registry;
  - DEC-0002 original-byte span authority;
  - DEC-0029 negotiated position projection;
  - DEC-0034 canonical diagnostic ordering;
  - DEC-0072 strict diagnostic span projection;
  - RFC-0004 lifecycle position negotiation and RFC-0023 path-free URIs.

## Normative changes

### 1. Adapter source set

The adapter receives one negotiated `PositionEncoding` and one or more unique
source records, each containing an accepted non-temporary Ling document URI and
a validated `SourceFile`. Source records are indexed by exact logical source
name. Duplicate names or URIs are invalid. The adapter performs no filesystem,
path, URI decoding, source normalization, parsing, or compiler query.

### 2. Adapter input

Each input contains exactly one existing `ling_diagnostics::Diagnostic` and
zero or more explicit related labels. A related label contains an existing
`DiagnosticSpan` plus independent Chinese and English messages. The core
`ling.diagnostic/0.1` schema is not changed merely to carry adapter-only labels.

Every adapted diagnostic MUST have a primary span. Every primary and related
span MUST name a source in the adapter set, be ordered, fit the compiler `u32`
byte domain, and project exactly through that source's `SourceMap`. Failure of
any input rejects the complete adapter call and returns no partial result.

### 3. LSP field mapping

For each accepted diagnostic the adapter emits this exact shape:

```json
{
  "code": "L-PARSE-0001",
  "data": {
    "facts": {},
    "repairs": [],
    "semanticId": null,
    "version": "ling.lsp.diagnostic/0.1"
  },
  "message": "中文消息 / English message",
  "range": {
    "end": {"character": 4, "line": 0},
    "start": {"character": 0, "line": 0}
  },
  "relatedInformation": [],
  "severity": 1,
  "source": "ling"
}
```

The mapping is normative:

| Ling value | LSP value |
| --- | --- |
| registered `DiagnosticCode` | string `code` |
| `Error` / `Warning` / `Note` | `severity` 1 / 2 / 3 |
| Chinese and English messages | `message_zh + " / " + message_en` |
| primary original-byte span | negotiated `range` |
| each related label | `relatedInformation` entry with its source URI, range, and bilingual message |
| Facts | `data.facts`, preserving canonical JSON values |
| optional Semantic ID | `data.semanticId` string or null |
| repairs | `data.repairs` entries preserving `kind`, `changes_semantics`, and canonical Facts |

Repair entries retain the existing `Repair` serialization: `kind` and
`changes_semantics` are always present, while an empty repair Facts map is
omitted and a non-empty map is emitted as `facts`.

`source` MUST be `ling`. `relatedInformation` and `data` MUST be present even
when empty. Version 0.1 emits no `codeDescription` because no immutable public
documentation URL is accepted, and emits no `tags` because retired diagnostic
codes cannot be emitted and the current diagnostic model has no independent
deprecated/unnecessary state.

The adapter MUST NOT translate, truncate, substitute, localize selectively, or
derive new diagnostic codes, Semantic IDs, repair kinds, or related messages.

### 4. Ordering and determinism

The result contains exactly one value per input and is sorted by the Accepted
DEC-0034 key `(logical source name, primary start byte, code, primary end byte,
input ordinal)`. Related labels retain their supplied semantic order. BTreeMap
Fact ordering and serde JSON values are retained; host paths, hash-map order,
allocation addresses, debug output, and wall-clock state are unobservable.

### 5. Compatibility and errors

The adapter is an in-process Rust boundary producing JSON values. It is not a
JSON-RPC method and allocates no Ling diagnostic for its own projection errors.
Callers receive typed errors for empty source sets, duplicate source identity,
missing primary spans, unknown/mismatched sources, or invalid offsets/ranges.
The adapter constructs `serde_json::Value` directly and therefore has no
serialization step. A future incompatible field/mapping change requires a new
protocol marker and migration evidence.

## Conformance plan

- Verify exact JSON keys/values and severity mapping for Error, Warning, Note,
  stable codes, both messages, Facts, Semantic IDs, and multiple repairs.
- Cover UTF-8/16/32 primary and related ranges across Chinese text, emoji,
  combining marks, BOM, CRLF, final lines, and multiple logical sources/URIs.
- Verify canonical diagnostic order, preserved related-label order, repeated
  byte-identical serialization, and different input insertion orders where the
  normative key differs.
- Reject empty/duplicate source sets, missing primary spans, unknown/mismatched
  logical names, reversed/out-of-range/scalar/surrogate/CRLF-interior spans,
  and one invalid later input without partial output.
- Run locked offline workspace tests, strict Clippy, CI, governance, support,
  status, RC0, traceability, formatting, and deterministic-diff gates.

## Compatibility impact

- **Protocol:** adds Experimental in-process `ling.lsp.diagnostic/0.1`; there
  is no predecessor or reader migration.
- **Existing diagnostic JSON:** unchanged; related labels are explicit adapter
  input and do not alter `ling.diagnostic/0.1`.
- **Diagnostics:** no code allocation, retirement change, message rewrite, or
  severity change.
- **Language/schema/Semantic ID/runtime/ABI:** none; existing values are only
  projected into a new adapter output.
- **Unicode:** position projection remains on Unicode 17.0.0 source behavior.

## Unresolved alternatives

Embedding related labels into `ling.diagnostic/0.1` was rejected because it
would be an unrelated schema migration. Omitting bilingual text was rejected
because public diagnostics must remain bilingual and offline-complete.
`codeDescription` was deferred until an immutable public documentation URL is
accepted. Fix application is deferred because repairs are metadata, not yet
authorized LSP edits.

Push/pull publication, document versions, stale results, cancellation,
root-cause grouping, caps, omitted-count diagnostics, tags for a future active
deprecation model, Workspace Edits, and Stable lifecycle remain future work.
