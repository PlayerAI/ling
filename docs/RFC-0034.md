# RFC-0034: LSP diagnostic storm control / LSP 诊断风暴控制

> 状态：Accepted
> 类型：Standards Track
> 创建日期：2026-08-23
> 目标版本：v0.1 Preview
> 作者/Owner role：ide-protocol-design
> 相关缺口：GAP-LSP-TRANSACTION-PROTOCOL-001; GAP-SEMANTIC-PROTOCOL-LIFECYCLE-001
> 生命周期记录：`docs/governance/lifecycle.toml`

This RFC defines one deterministic, bounded transformation shared by Ling LSP
push and pull diagnostics. It suppresses repeated roots, applies configurable
per-document and workspace limits, and represents every omission explicitly
without changing compiler diagnostic production or the adapter schema.

## Summary

`ling.lsp.diagnostic-control/0.1` operates on the complete ordered
`ling.lsp.diagnostic/0.2` adapter output. It retains the first diagnostic for
each exact root identity, applies active caps in accepted order, and adds
registered bilingual `L-LSP-0001` summary diagnostics at the first omitted
position. Both publication channels consume the same transformed map, so
their current error sets remain identical.

## Status and scope

- Current lifecycle state: `Accepted`
- Stable implementation basis: `yes` for this Preview protocol
- In scope:
  - root identity and deterministic first-wins duplicate suppression;
  - configurable bounded per-document and workspace limits;
  - explicit per-document and workspace omitted-count diagnostics;
  - shared push/pull transformation, recovery, and version migration;
  - existing syntax-phase precedence and resource-limit root preservation.
- Out of scope:
  - changing parser recovery, compiler phase selection, diagnostic meaning, or
    the production Trait solver integration boundary;
  - severity filters, user code filters, warning policies, configuration

    fixes, Workspace Edits, or Stable compatibility.
- Normative dependencies:
  - `SEMANTICS.md` §26 and DEC-0001 diagnostic identity;
  - RFC-0031 adapter 0.2, RFC-0032 push publication, and RFC-0033 pull reports;
  - RFC-0004 lifecycle and RFC-0023/RFC-0029/RFC-0030 snapshots.

## Normative changes

### 1. Configuration and discovery

The active limits default to 100 retained compiler diagnostics per document
and 1000 per complete workspace snapshot. Initialize MAY contain:

```json
"initializationOptions": {
  "lingDiagnosticControl": {
    "maxPerDocument": 100,
    "maxPerWorkspace": 1000
  }
}
```

Either limit MAY be omitted and then uses its default. `maxPerDocument` MUST be
an integer from 1 through 4096; `maxPerWorkspace` MUST be an integer from 1
through 65536. The two limits are independent. A present
`lingDiagnosticControl` member or known limit with the wrong shape MUST reject
initialize as InvalidParams without lifecycle mutation. Unknown ordinary
initialization fields are ignored. Limits are immutable after initialization.

Every successful initialize MUST advertise the active values exactly under:

```json
"experimental": {
  "lingDiagnosticControl": {
    "maxPerDocument": 100,
    "maxPerWorkspace": 1000,
    "version": "ling.lsp.diagnostic-control/0.1"
  }
}
```

### 2. Input order and root identity

Control consumes the complete RFC-0031 adapter sequence after its accepted
logical-source-name, original UTF-8 start byte, code, end byte, and source
ordinal ordering. It MUST NOT reorder retained compiler diagnostics.

Two adapted diagnostics in the same exact URI have one root identity exactly
when the compact JSON encodings of this tuple are equal: `code`, `range`,
`data.semanticId`, and `data.facts`. All four members MUST have the RFC-0031
shapes. Malformed internal adapter values are an invariant failure, not
best-effort public output.

For repeated root identities, the first diagnostic in accepted order is
retained and every later diagnostic is omitted. The retained value is
byte-for-byte unchanged; messages, severity, repairs, and related information
are not merged. Independent errors with the same code remain distinct.
Lexical-over-parser and syntax-over-semantic precedence remains the compiler
policy from RFC-0032 and occurs before this transformation.

### 3. Per-document and workspace caps

After duplicate suppression, each URI retains at most `maxPerDocument`
compiler diagnostics. The earliest values in accepted order win. The workspace
cap then traverses URI groups in Unicode scalar-value URI order and values in
their retained order, keeping at most `maxPerWorkspace` compiler diagnostics
across the snapshot. Summary diagnostics do not consume either cap.

The implementation MUST use checked counters and MUST NOT depend on hash-map,
filesystem, worker, allocation, clock, or host iteration order. It MUST keep
the complete compiler result immutable; suppression exists only in the LSP
projection.

### 4. Explicit omission summaries

Every URI that omitted at least one duplicate or per-document overflow MUST
receive exactly one document summary after its retained compiler diagnostics.
If the workspace cap omits one or more diagnostics, exactly one workspace
summary MUST be appended to the URI containing the first workspace-omitted
diagnostic. A URI MAY therefore contain both summaries.

Each summary is a standard LSP Diagnostic with:

- code `L-LSP-0001`, source `ling`, severity Warning (`2`), empty repairs
  and related information, and null Semantic ID;
- the exact range of the first diagnostic counted by that summary;
- bilingual message
  `已省略 {omitted} 条诊断 / {omitted} diagnostics omitted`;
- `data.version = "ling.lsp.diagnostic-control/0.1"`;
- facts with exact keys `scope` (`document` or `workspace`), `omitted`,
  `deduplicated`, `capped`, and `maximum`. Counts are non-negative JSON
  integers; `omitted = deduplicated + capped`. A workspace summary has
  `deduplicated = 0` and its `maximum` is the workspace limit.

The registered code describes projection loss rather than a new source error.
No summary exists when its omitted count is zero. Summary placement cannot
hide or replace the retained root cause.

### 5. Resource-limit roots

An upstream registered resource-limit diagnostic remains an ordinary compiler
root and is never suppressed merely because of severity or domain. Repeated
instances with the exact same root identity collapse to one retained diagnostic
and contribute to an omission summary. Distinct resource facts or ranges remain
distinct until a configured cap applies.

This rule applies to a future production Trait/solver resource diagnostic once
that compiler integration has separate Accepted authority. This RFC does not
expose the current crate-private experimental Trait solver, allocate its code,
or manufacture a solver failure when none was emitted by the compiler.

### 6. Push, pull, recovery, and failures

Push and pull MUST invoke the same control transformation for the same current
ticket. Pull result IDs hash the transformed arrays. Pull MUST still leave the
push ledger and pending work unchanged. A later snapshot recomputes control
from scratch: fixed diagnostics and summaries disappear through the existing
replacement/empty-clearance rules; no suppression cache exists.

Transformation failure MUST abort the complete push publication or pull
response without ledger, pending-work, document, or cache mutation. Existing
stale, response-size, and notification-size rules remain unchanged.

### 7. Protocol migration

Push advances compatibly in schema but incompatibly in diagnostic-set behavior
from `ling.lsp.publish-diagnostics/0.1` to `0.2`. Pull advances from
`ling.lsp.pull-diagnostics/0.1` to `0.2`; its provider identifier changes to the
new marker. The stateless `ling.lsp.pull-result/0.1:blake3:` algorithm and
format remain unchanged, while controlled arrays naturally produce their own
IDs. `ling.lsp.diagnostic/0.2` remains unchanged because control is a separate
post-adapter layer.

There is no runtime toggle for legacy 0.1 diagnostic-set behavior. Clients
MUST gate on the advertised exact markers and the diagnostic-control discovery
object. Neither 0.2 protocol is Stable.

## Compatibility impact

- **Protocol:** adds Preview `ling.lsp.diagnostic-control/0.1`; advances push
  and pull diagnostic-set protocols to 0.2; keeps adapter and result-ID
  algorithm markers unchanged.
- **Diagnostic:** allocates Preview `L-LSP-0001` with fixed Facts. No existing
  code, severity, message, Fact, repair, or Semantic ID changes.
- **Language/runtime/data:** no Ling syntax, semantics, Typed Core, interpreter,
  runtime, bytecode, VM, ABI, filesystem/network/cache behavior, or Unicode
  17.0.0 change.

## Unresolved alternatives

Merging repairs or related labels was rejected because first-wins preserves an
existing complete adapter value and avoids inventing an order-independent
merge schema. Severity/user-code filtering and dynamic settings remain future
work because they require a broader configuration and warning-policy contract.

Compiler/parser recovery improvements and production Trait solver resource
diagnostics remain owned by their compiler tasks. This LSP layer only bounds
and reports the complete diagnostic set it receives.
